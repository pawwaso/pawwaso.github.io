Transform data: star schema, SCD, cleansing

How to turn silver data into a gold star schema in a lakehouse or warehouse: fact and dimension design, surrogate keys, slowly changing dimensions (types 0/1/2/3/6) in T-SQL and PySpark, denormalisation, and the data-quality toolbox (deduplication, nulls, type conversion, filtering, joins, aggregation, enrichment), plus Power Query operations and how to choose between T-SQL, PySpark and Dataflow Gen2. Maps to Prepare data → Transform data.

Star schema building blocks

A star schema has a central fact table (events/measurements, many rows, numeric measures + foreign keys) surrounded by dimension tables (descriptive attributes used to filter and group). It is the recommended shape for Power BI semantic models: simpler DAX, better compression, fewer and cheaper joins, easier for users. Relationships go one-to-many from dimension to fact, single direction by default.

Fact table types

TypeGrainExampleBehaviour
TransactionalOne row per event/lineOrder line, payment, web clickInsert-only; fully additive measures; largest tables
Periodic snapshotOne row per entity per periodDaily stock level per product/warehouse, month-end account balanceSemi-additive measures (don't sum balances over time – use last/average)
Accumulating snapshotOne row per process instance, updated as it progressesOrder with OrderDate, ShipDate, DeliveryDate, lag columnsRows are updated (MERGE); several date keys (role-playing date dimension)
Factless factOne row per occurrence/coverage, no measuresStudent attendance, product on promotionAnalysed by counting rows

Declare the grain first ("one row per order line"), then pick dimensions and measures consistent with it. Store data at the grain the business actually needs – if users only analyse by month, summarising a 400-million-row table to monthly grain in gold dramatically cuts cost.

Dimension design

  • Surrogate key: a narrow, meaningless integer (int/bigint) key owned by the warehouse. Needed for SCD type 2 (several versions of one business key), shields you from source key changes, merges keys from several sources, and integers compress and join best. Relationships on text or floating-point keys are allowed but slower and risk matching problems.
  • Business (natural) key: the source identifier (CustomerID) – kept as an attribute for lookups and MERGE matching.
  • Unknown member: a row such as key -1 "Unknown" so facts with missing/late dimension values still join (no blank row in reports, no lost facts).
  • Degenerate dimension: an identifier with no attributes (OrderNumber, InvoiceNo) kept directly in the fact.
  • Conformed dimension: one shared dimension (Date, Customer, Product) used by several facts/models with identical keys and attributes → consistent drill-across. Build it once physically in the lakehouse/warehouse and reuse it everywhere.
  • Date dimension: one row per day, integer key yyyymmdd, attributes (year, quarter, month name/number, week, fiscal periods, holidays, IsWorkingDay). Generate it once (T-SQL, Spark or Power Query) and mark it as a date table in the model.
  • Role-playing dimension: one physical dimension used in several roles (Order Date, Ship Date, Due Date). In the model: one active and other inactive relationships activated with USERELATIONSHIP, or separate role views/tables.
  • Junk dimension: combines several low-cardinality flags/indicators (IsOnline, PaymentType, GiftWrap) into one small dimension with one row per combination – keeps the fact narrow.
  • Bridge table: resolves many-to-many (a customer owns many accounts; an account has many owners). Bridge CustomerAccount(CustomerKey, AccountKey) with one-to-many relationships from both dimensions; let filters flow from the bridge to DimAccount (bidirectional on that relationship or CROSSFILTER in measures). Totals across customers are non-additive.
  • Snowflake vs star: normalised dimension hierarchies (Product → Subcategory → Category) are denormalised into a single wide dimension for the model.

Loading facts: key lookup

-- T-SQL: replace business keys with surrogate keys; unknown member for misses
INSERT INTO gold.FactSales (DateKey, CustomerKey, ProductKey, OrderNumber, Quantity, SalesAmount)
SELECT  CONVERT(int, CONVERT(char(8), s.OrderDate, 112))      AS DateKey,
        COALESCE(c.CustomerKey, -1)                           AS CustomerKey,
        COALESCE(p.ProductKey,  -1)                           AS ProductKey,
        s.OrderNumber,                                        -- degenerate dimension
        s.Quantity,
        s.Quantity * s.UnitPrice                              AS SalesAmount
FROM    silver.Sales AS s
LEFT JOIN gold.DimCustomer AS c
       ON c.CustomerID = s.CustomerID
      AND s.OrderDate >= c.ValidFrom AND s.OrderDate < COALESCE(c.ValidTo, '9999-12-31')   -- SCD2: version valid at order time
LEFT JOIN gold.DimProduct AS p
       ON p.ProductID = s.ProductID AND p.IsCurrent = 1;
Row-level calculated values used as axis/slicer (Margin = SalesAmount − TotalCost, profit bands) belong in the gold table, computed during transformation – especially for Direct Lake models, which should get such columns from the Delta table rather than from DAX calculated columns (calculated columns aren't supported on Direct Lake on SQL endpoint tables, and are only in preview with limitations on Direct Lake on OneLake). Materialise once upstream; every consumer gets the same definition.

Change detection: compare tracked columns directly, or compare a row hash (e.g. sha2(concat_ws('||', Name, City, Segment), 256)) stored on each version – one comparison instead of many, and NULL-safe if you coalesce first.

SCD type 2 in T-SQL (warehouse)

-- Staging: stg.Customer (CustomerID, CustomerName, City, Segment) = today's full extract
BEGIN TRAN;

-- 1) Expire current rows whose tracked attributes changed
UPDATE d
SET    d.ValidTo   = SYSUTCDATETIME(),
       d.IsCurrent = 0
FROM   gold.DimCustomer AS d
JOIN   stg.Customer     AS s ON s.CustomerID = d.CustomerID
WHERE  d.IsCurrent = 1
  AND (   ISNULL(d.City, '')    <> ISNULL(s.City, '')
       OR ISNULL(d.Segment, '') <> ISNULL(s.Segment, ''));

-- 2) Insert new versions (changed rows) and brand-new customers
INSERT INTO gold.DimCustomer (CustomerID, CustomerName, City, Segment, ValidFrom, ValidTo, IsCurrent)
SELECT s.CustomerID, s.CustomerName, s.City, s.Segment, SYSUTCDATETIME(), NULL, 1
FROM   stg.Customer AS s
LEFT JOIN gold.DimCustomer AS d
       ON d.CustomerID = s.CustomerID AND d.IsCurrent = 1
WHERE  d.CustomerID IS NULL;      -- no current row: new customer or just expired

-- 3) Type 1 attribute (name corrections) overwrite on all versions
UPDATE d SET d.CustomerName = s.CustomerName
FROM gold.DimCustomer AS d JOIN stg.Customer AS s ON s.CustomerID = d.CustomerID
WHERE d.CustomerName <> s.CustomerName;

COMMIT;
-- CustomerKey is BIGINT IDENTITY, so new versions get new surrogate keys automatically

Type 1 with MERGE (GA in Fabric warehouse):

MERGE gold.DimProduct AS t
USING stg.Product AS s
   ON t.ProductID = s.ProductID
WHEN MATCHED AND (t.ProductName <> s.ProductName OR t.ListPrice <> s.ListPrice) THEN
     UPDATE SET t.ProductName = s.ProductName, t.ListPrice = s.ListPrice
WHEN NOT MATCHED BY TARGET THEN
     INSERT (ProductID, ProductName, ListPrice) VALUES (s.ProductID, s.ProductName, s.ListPrice)
WHEN NOT MATCHED BY SOURCE THEN
     UPDATE SET t.IsActive = 0;    -- soft delete for products no longer in the full extract

SCD type 2 in PySpark (Delta MERGE, single statement)

A single MERGE can't both update the current row and insert its new version for the same key – so the classic trick stages changed rows twice: once with a real merge key (to expire the old row) and once with a NULL merge key (which never matches, so it is inserted).

from pyspark.sql import functions as F
from delta.tables import DeltaTable

tracked = ["City", "Segment"]
src = (spark.read.table("silver.customers_extract")
         .withColumn("RowHash", F.sha2(F.concat_ws("||", *[F.coalesce(F.col(c), F.lit("")) for c in tracked]), 256)))

dim = DeltaTable.forName(spark, "gold.dim_customer")
cur = dim.toDF().filter("IsCurrent = true")

# rows whose hash changed -> need a NEW version inserted
changed = (src.alias("s").join(cur.alias("d"), "CustomerID")
              .filter("s.RowHash <> d.RowHash")
              .select("s.*"))

staged = (changed.withColumn("MergeKey", F.lit(None).cast("string"))      # will INSERT
          .unionByName(src.withColumn("MergeKey", F.col("CustomerID"))))  # will match / insert new

(dim.alias("d")
   .merge(staged.alias("s"), "d.CustomerID = s.MergeKey AND d.IsCurrent = true")
   .whenMatchedUpdate(
        condition="d.RowHash <> s.RowHash",
        set={"IsCurrent": "false", "ValidTo": "current_timestamp()"})
   .whenNotMatchedInsert(values={
        "CustomerKey": "xxhash64(s.CustomerID, current_timestamp())",   # or max+row_number
        "CustomerID": "s.CustomerID", "City": "s.City", "Segment": "s.Segment",
        "RowHash": "s.RowHash", "ValidFrom": "current_timestamp()",
        "ValidTo": "CAST(NULL AS TIMESTAMP)", "IsCurrent": "true"})
   .execute())
  • Unchanged rows match but fail the RowHash <> condition → no-op. New customers have no current row → inserted via the real-key copy. Changed customers: real-key copy expires the old row; NULL-key copy inserts the new version.
  • Alternative: two steps (UPDATE to expire, then append new versions) inside one notebook – simpler, but not one atomic commit.
  • Rebuild-from-history alternative: when you have every change event with an effective date, compute ValidTo with lead(EffectiveDate) OVER (PARTITION BY CustomerID ORDER BY EffectiveDate) and IsCurrent where the lead is NULL.
  • Facts join to the version valid at the event date (OrderDate BETWEEN ValidFrom AND ValidTo) to get the historically correct surrogate key.
  1. Land today's full customer extract in staging
  2. Compute a row hash of the tracked attributes
  3. Compare staging with current dimension rows on the business key
  4. Expire changed current rows by setting ValidTo and IsCurrent = 0
  5. Insert new versions and brand-new customers with new surrogate keys
  6. Load facts by looking up the version valid at the transaction date

A daily full extract of all customers arrives. dim_customer (Delta, lakehouse) must preserve the history of City and Segment changes. What should you implement in a notebook?

  • mode("overwrite") of the extract into dim_customer
  • A MERGE that compares the extract with current rows, expires changed rows and inserts new versions
  • mode("append") of the full extract every day
  • Enable Delta time travel and query old versions

That is SCD type 2: expire + insert new versions with validity dates and a current flag. Overwrite is type 1 (history lost), appending duplicates every unchanged row, and time travel is limited by retention and isn't a dimensional history.

A silver table must keep the history of changed customer attributes with validity dates and a current flag. Which pattern is this?

  • SCD type 1
  • SCD type 3
  • SCD type 0
  • SCD type 2

Type 2 adds a new row per change with ValidFrom/ValidTo and a current indicator. Type 1 overwrites, type 3 keeps one previous value in an extra column, type 0 never changes.

Denormalisation & shaping for analytics

  • Flatten snowflaked hierarchies (Product–Subcategory–Category) into one dimension with joins in the transformation layer.
  • Move descriptive attributes from header tables into dimensions; header/line structures become one fact at line grain (allocate header-level amounts like freight if needed).
  • Split high-cardinality datetime into a date key and a separate time (or time key) column – drastically better compression in semantic models.
  • Remove columns nobody uses; keep data types narrow; pre-aggregate to the required grain; materialise calculated columns and summary tables as Delta tables (Direct Lake can only use Delta tables – a summary table must exist in OneLake).
  • Expose friendly names through views or in the semantic model; hide technical keys there.

Data quality and cleansing toolbox

Deduplication

-- T-SQL: keep the latest row per business key (deterministic, keeps all columns consistent)
WITH ranked AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY CustomerID ORDER BY ModifiedDate DESC, LoadId DESC) AS rn
    FROM silver.CustomerChanges
)
SELECT * FROM ranked WHERE rn = 1;

-- Same with QUALIFY (supported in Fabric warehouse / SQL endpoint)
SELECT * FROM silver.CustomerChanges
QUALIFY ROW_NUMBER() OVER (PARTITION BY CustomerID ORDER BY ModifiedDate DESC) = 1;
# PySpark
from pyspark.sql import Window, functions as F

exact_dupes_removed = df.dropDuplicates()                  # identical rows
one_per_key_any     = df.dropDuplicates(["OrderID"])       # ANY one row per key – non-deterministic!

w = Window.partitionBy("CustomerID").orderBy(F.col("LoadTimestamp").desc())
latest = (df.withColumn("rn", F.row_number().over(w))
            .filter("rn = 1").drop("rn"))                  # latest row per key – deterministic
dropDuplicates(["key"]) keeps an arbitrary row per key. When "latest" matters, use row_number() over a window ordered by the change timestamp. GROUP BY with MAX() per column is wrong too – it can mix values from different rows.

Missing data and nulls

# PySpark
df = (df.fillna({"Country": "Unknown", "Discount": 0})     # replace nulls per column
        .dropna(subset=["OrderID", "OrderDate"])           # drop rows missing mandatory fields
        .withColumn("City", F.coalesce("City", "BillingCity", F.lit("Unknown"))))
bad = df.filter(F.col("CustomerID").isNull())              # route to a quarantine table instead of losing them
-- T-SQL
SELECT COALESCE(City, BillingCity, 'Unknown') AS City,
       ISNULL(Discount, 0)                    AS Discount,
       NULLIF(TRIM(Email), '')                AS Email      -- empty string -> NULL
FROM   silver.Customer;
  • Decide per column: reject (mandatory keys), default (0 for additive measures only if business-correct; "Unknown" for attributes), derive (from other columns), or keep NULL (unknown measure values should usually stay NULL so averages aren't distorted).
  • Map missing dimension references to the unknown member (-1) rather than dropping facts.
  • Quarantine invalid rows in a separate table for investigation; count them and fail the pipeline if a threshold is exceeded.

The silver table has one row per address change; the gold table needs one row per customer with the latest address. Which logic is required?

  • Rank rows per customer by change date descending and keep rank 1
  • GROUP BY CustomerID with MAX() on each address column
  • SELECT DISTINCT CustomerID, Street, City
  • dropDuplicates(["CustomerID"])

ROW_NUMBER over CustomerID ordered by change date descending deterministically picks the latest complete row. MAX per column can mix values from different rows, DISTINCT keeps all versions, and dropDuplicates keeps an arbitrary row.

A dataflow appends to a lakehouse table, and the source occasionally resends yesterday's rows. What happens and how do you fix it?

  • Delta rejects duplicates automatically
  • Rows are silently overwritten – no fix needed
  • Duplicates accumulate; make the load idempotent by replacing the affected window or merging on keys
  • Switch the destination to a warehouse, which enforces primary keys

Neither Delta nor warehouse constraints (NOT ENFORCED) reject duplicates. Replace the window (delete/insert or replaceWhere) or MERGE on business keys downstream.

Query folding

  • Query folding = Power Query translates steps into the source's native query (e.g. one SQL SELECT … WHERE), so the source does the work and only the result is transferred.
  • Check with step folding indicators in Power Query Online and View data source query (greyed out = that step doesn't fold).
  • Once a step breaks folding, all later steps run in the mashup engine – e.g. a 30-day filter after a non-folding step means the whole 500-million-row table is pulled first. Put foldable steps (filters, column removal, simple joins, group by) before non-foldable ones.
  • Typical folding breakers: custom M functions / complex custom columns, Table.Buffer, some type conversions, merging queries from different sources, index columns, operations on file sources (CSV/Excel never fold).
  • Non-foldable sorts, joins and buffering can use a lot of mashup-engine memory and slow refresh.
  • Incremental refresh in Dataflow Gen2 needs a Date/DateTime/DateTimeZone column to filter on, and the query should fully fold so bucket filters are pushed to the source.

Dataflow Gen2 features that matter for transformations

  • Staging: materialises a query's result in Fabric staging storage (lakehouse/warehouse) so referencing queries read it once and can use the SQL compute engine. Without staging, a referenced query (e.g. BaseOrders used by three other queries) is re-evaluated against the source for each reference. Enable staging on shared, expensive queries; disable it for simple single-use queries to save time.
  • Fast copy: uses the pipeline copy engine for large volumes when source, transformations (e.g. column selection/rename) and destination are supported.
  • Data destinations: Lakehouse, Warehouse, KQL database, Azure SQL database (and others); update method Append or Replace; automatic or manual column mapping.
  • Parameters (public parameters can be passed from pipelines) replace hard-coded server/database names across dev/test/prod.

Scenario: A CRM signals deleted customers by sending rows with IsDeleted = 1. Rows land in bronze; DimCustomer in gold feeds a Direct Lake model. Deleted customers must disappear from reports, but bronze must keep everything for audit. The CRM also occasionally resends rows, and the team wants SCD type 2 on City. Outline the transformation.

Keep bronze append-only (all raw rows, including deletes). In the silver step: (1) deduplicate the batch with row_number() per CustomerID ordered by the change timestamp (keep 1) – required anyway because MERGE fails when several source rows match one target row; (2) cast types, trim/standardise, default missing attributes to "Unknown"; (3) apply a MERGE into the curated customer table: WHEN MATCHED AND s.IsDeleted = 1 → expire/soft-delete (set IsCurrent = 0, IsDeleted = 1, ValidTo) or hard-delete, changed City → expire and insert a new version (type 2 staging trick), new customers → insert with a new surrogate key, name corrections → type 1 update. (4) Build gold DimCustomer (or a view materialised as a Delta table – Direct Lake needs tables, not views) filtered to non-deleted members, plus an unknown member row (-1). (5) Facts look up the version valid at the order date. The delete is applied once in the curated layer, so every consumer is consistent, while bronze keeps the audit trail and allows a rebuild.

Key takeaways & exam tips

  • Star schema = facts (declared grain, measures, surrogate FKs) + denormalised dimensions; one-to-many, single direction.
  • Fact types: transactional, periodic snapshot (semi-additive), accumulating snapshot (updated rows, several dates), factless.
  • Use integer surrogate keys (warehouse: BIGINT IDENTITY); keep the business key; add an unknown member.
  • Conformed date dimension built once physically and reused; role-playing → inactive relationships + USERELATIONSHIP; many-to-many → bridge table; flags → junk dimension.
  • SCD: 0 keep, 1 overwrite, 2 new row with ValidFrom/ValidTo/IsCurrent, 3 previous-value column, 6 = 2 + current-value column. Implement with MERGE (Delta or T-SQL) or UPDATE + INSERT; a row hash simplifies change detection.
  • Latest row per key: ROW_NUMBER() over (PARTITION BY key ORDER BY date DESC) = 1 (or QUALIFY / Spark window). dropDuplicates(["key"]) is non-deterministic.
  • Appending resent data duplicates rows – make loads idempotent (window replace or MERGE on keys).
  • Materialise row-level calculated columns and summary tables in gold (Delta) – especially for Direct Lake.
  • Power Query: merge = join (left anti for orphans, fuzzy for approximate text); append = union; Unpivot other columns for growing column sets; Combine files for folders; profiling uses top 1,000 rows by default.
  • Query folding pushes work to the source; one non-foldable step stops folding for everything after it; check with folding indicators / View data source query.
  • Dataflow Gen2: staging prevents re-evaluating referenced queries; fast copy for big simple loads; parameters for environments.
  • Pick the tool by skills, volume, data shape and destination: T-SQL for set-based warehouse ELT, PySpark for big/complex/semi-structured, Dataflow Gen2 for low-code.
