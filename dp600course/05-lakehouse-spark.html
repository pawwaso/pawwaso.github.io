Analysts connect to Lakehouse1's SQL analytics endpoint from SSMS. Which statement succeeds?

  • UPDATE dbo.Sales SET Amount = 0 WHERE Id = 5
  • CREATE TABLE dbo.Staging (Id int)
  • CREATE VIEW dbo.vSales AS SELECT … FROM dbo.Sales
  • CREATE TABLE dbo.Sales2 AS CLONE OF dbo.Sales

Read-only for data, but metadata objects (views, functions, procedures, security) are allowed. DML, CREATE TABLE and clones need a warehouse.

Deep dive: schemas, metadata sync, shortcuts
  • Lakehouse schemas are on by default in the portal (REST API: "enableSchemas": true). dbo always exists and can't be removed; saveAsTable("marketing.products") writes to schema marketing.
  • Spark four-part name workspace.lakehouse.schema.table enables cross-workspace joins (non-schema: workspace.lakehouse.table). Schema shortcuts map a whole schema; schemas enable schema-level security and are required by materialized lake views.
  • Non-schema lakehouses can't be converted in place. In a notebook, the default lakehouse must be schema-enabled (or none) to use schemas. Schema-enabled lakehouses don't support external table metadata over ADLS directly: use shortcuts.
  • A shortcut under Tables/ pointing to a Delta table appears as a table; under Files/ it's just a folder. External tables are not discovered by the endpoint unless the Delta folder is under Tables/.
  • Metadata sync: a background process reads Delta logs; short lag possible. Force it: Explorer Refresh, the Refresh SQL analytics endpoint metadata REST API, or the pipeline activity. New metadata sync (preview, per workspace) adds sys.sp_dw_refresh_ext_table and is required for T-SQL time travel on endpoints.
  • Type mapping: STRING → varchar(8000) (UTF-8 BIN2), TIMESTAMP → datetime2, DOUBLE → float, LONG → bigint; unsupported types are hidden.

Delta Lake: the transaction log

Every write adds a commit to _delta_log; a version is just a list of active Parquet files.

Delta log simulator
_delta_log · click a version to time travel
🟩 active in latest version · ⬜ dashed = removed from log, still on disk · 🟥 deleted by VACUUM · outlined = read by the selected version

Try: INSERT ×3 → OPTIMIZE → VACUUM → ⏩⏩⏩ → VACUUM → click v0.

DESCRIBE HISTORY sales;                      -- versions + operations
SELECT * FROM sales VERSION AS OF 12;
SELECT * FROM sales TIMESTAMP AS OF '2026-11-03 08:00:00';
RESTORE TABLE sales TO VERSION AS OF 12;     -- roll back

PySpark: .option("versionAsOf", 12) or .option("timestampAsOf", "2026-11-03"). Works only while old files exist.

  • Writes with mismatching columns/types fail by default.
  • mergeSchema = true → add new columns (old rows get NULL).
  • overwriteSchema = true + overwrite → replace the schema.
  • Atomic: visible only once the commit file exists.
  • Optimistic: a conflicting second writer fails and retries; appends rarely conflict.
  • Readers always see one consistent version.

A daily append fails: the source added a column discount_code. Existing data must stay. What do you do?

  • Switch to mode("overwrite")
  • Add .option("mergeSchema", "true")
  • Drop and recreate the table
  • Cast discount_code to string

mergeSchema allows evolution: new column added, old rows NULL. Overwrite/drop lose data.

Two hours ago a notebook wrongly deleted rows from Orders. VACUUM hasn't run since. Least effort to see the old data?

  • VERSION AS OF / TIMESTAMP AS OF
  • Restore the workspace from backup
  • Re-ingest bronze files
  • Create a warehouse restore point

Delta time travel reads the earlier version; RESTORE TABLE can roll back. Restore points are a warehouse feature.

Deep dive: log files, checkpoints, deletion vectors
  • Commits are ordered JSON files (00000000000000000000.json…) listing added/removed files + metadata; periodic checkpoint Parquet files summarise the log.
  • Deletion vectors mark rows deleted without rewriting whole files (faster DELETE/UPDATE/MERGE); OPTIMIZE or "purge deletion vectors" later materialises them.
  • Delta is the format every Fabric engine reads: Spark, warehouse, SQL endpoint, Direct Lake, KQL OneLake availability.

A 2026 workspace writes gold tables with default Spark settings. Direct Lake reports are slow; tables are rarely written. Best fix?

  • VACUUM with 0 hours retention
  • Partition by CustomerID
  • Disable optimize write
  • Enable V-Order and rewrite, e.g. OPTIMIZE … VORDER

New workspaces use writeHeavy (V-Order off). Enable it (table property, session or readHeavyForPBI) and rewrite existing files.

Correct maintenance sequence for a heavily appended Delta table?

  • VACUUM, then OPTIMIZE
  • OPTIMIZE, then VACUUM with appropriate retention
  • VACUUM RETAIN 0 HOURS after every load
  • OPTIMIZE alone deletes old files

OPTIMIZE leaves old files unreferenced; VACUUM removes them after retention.

Deep dive: V-Order controls, partitioning, running maintenance 
SET spark.sql.parquet.vorder.default = TRUE;                                     -- session
ALTER TABLE gold.fact_sales SET TBLPROPERTIES ("delta.parquet.vorder.enabled" = "true"); -- table
OPTIMIZE gold.fact_sales ZORDER BY (CustomerID) VORDER;                          -- rewrite existing
df.write.option("parquet.vorder.enabled", "true").saveAsTable("gold.fact_sales") # per write
spark.conf.set("spark.fabric.resourceProfile", "readHeavyForPBI")               # profile
VACUUM sales RETAIN 240 HOURS;                                                   -- keep 10 days
  • Profiles: writeHeavy (default, V-Order off), readHeavyForPBI (V-Order on, 1 GB bins), readHeavyForSpark, custom. Warehouse V-Order can only be disabled at warehouse level, irreversibly.
  • Partition only large tables on low-cardinality filter columns (year, month, region). Pruning skips folders; Z-Order/V-Order help inside partitions.
  • .option("replaceWhere", "OrderDate >= '2026-11-01'") overwrites just one window: idempotent reloads.
  • No-code: Lakehouse explorer → table → Maintenance (OPTIMIZE ± V-Order, VACUUM, purge deletion vectors), shown as TableMaintenance in Monitoring hub. Pipelines: Lakehouse Maintenance activity (preview), then Refresh SQL analytics endpoint. Also notebooks and REST API.
  • Small files hurt: file-open overhead, slow endpoint sync, slow Direct Lake transcoding (guardrails count files), poor compression. Fix order: batch ingestion, optimize write, auto compaction, scheduled OPTIMIZE, then VACUUM.
  • Aggressive VACUUM breaks time travel and can fail long-running readers.

Spark notebooks

Read → transform → write Delta. PySpark and Spark SQL compile to the same plan: pick by skills.

from pyspark.sql import functions as F
df = (spark.read.format("csv")
        .option("header", "true")
        .schema(schema)
        .load("Files/raw/sales/2026/*.csv"))
clean = (df.dropDuplicates(["OrderID"])
           .filter(F.col("Amount") > 0)
           .withColumn("OrderYear", F.year("OrderDate")))
clean.write.mode("overwrite").saveAsTable("silver.orders")
clean.write.mode("append").saveAsTable("silver.orders")
clean.write.option("path", "Files/ext/orders").saveAsTable("orders_ext")
(clean.write.mode("append")
      .option("mergeSchema", "true")
      .saveAsTable("silver.orders"))
  1. Read raw CSVs from Files/ with an explicit schema (no inference pass, stable types).
  2. Transformations are lazy: nothing runs until an action (write, count, display).
  3. Overwrite a managed Delta table (replace contents).
  4. Append rows (default mode "error" fails if the table exists).
  5. A path makes it an external table.
  6. Allow a new column with schema evolution.
%%sql
MERGE INTO silver.customers AS t
USING staging_customers AS s
  ON t.CustomerID = s.CustomerID
WHEN MATCHED AND s.IsDeleted = 1 THEN DELETE
WHEN MATCHED THEN UPDATE SET
     t.Name = s.Name, t.City = s.City
WHEN NOT MATCHED AND s.IsDeleted = 0 THEN INSERT *;
  1. Magic switches the cell language to Spark SQL.
  2. Match on the business key. Dedupe the source first: MERGE fails if 2 source rows hit one target row.
  3. Apply CDC deletes.
  4. Upsert: update changed rows.
  5. Insert new rows. All in one atomic commit.

Deep dive: notebookutils, magics, performance basics
  • Languages: PySpark, Spark SQL, Scala, SparkR; magics %%pyspark %%sql %%spark %%sparkr %%configure. Python notebooks = single node, no Spark (pandas/polars/DuckDB, cheap for small data).
  • Attach a default lakehouse so Files/…, Tables/… and unqualified names resolve. Full path: abfss://Sales@onelake.dfs.fabric.microsoft.com/LH_Silver.Lakehouse/Tables/customers.
  • notebookutils (legacy alias mssparkutils): fs.ls/cp/mkdirs, notebook.run("NB", 600, {"load_date": …}) (separate run, returns exit value), notebook.runMultiple([...]) (parallel/DAG), credentials.getToken / getSecret.
  • %run NB_Common runs another notebook inline in the same session (its functions become available).
  • Temp views bridge PySpark and SQL: df.createOrReplaceTempView("v_clean"). CTAS: CREATE TABLE … USING DELTA AS SELECT ….

  • DeltaTable API MERGE: DeltaTable.forName(spark, "silver.customers").alias("t").merge(src.alias("s"), "t.CustomerID = s.CustomerID").whenMatchedDelete("s.IsDeleted = 1").whenMatchedUpdateAll().whenNotMatchedInsertAll().execute().

IoT micro-batches every 5 minutes → 60,000 small files; endpoint and Direct Lake are slow. Someone proposes VACUUM RETAIN 0 HOURS after every batch. Your advice?

No. VACUUM ignores the current small files; 0 h breaks time travel (and is blocked below 7 days). Do: batch ingestion → optimize write / auto compaction → scheduled OPTIMIZE (V-Order) → VACUUM 7 days → refresh endpoint/model.
Deep dive: idempotency and layouts
  • "Safe to rerun" = idempotent: overwrite the window or MERGE on keys, advance the watermark only after success, to the max value actually copied (not GETDATE()).
  • Layouts: one lakehouse per layer (separate workspaces for governance) or bronze/silver/gold schemas in one schema-enabled lakehouse.
  • Lakehouse vs warehouse: both store Delta in OneLake (OneCopy). Lakehouse: Spark, any data type, you run OPTIMIZE/VACUUM, OneLake security. Warehouse: T-SQL read/write, automatic maintenance, clones + restore points (1–120 days, default 30), DDM in T-SQL.
  • Exactly-once streaming → Spark structured streaming with a checkpoint location.

Exam traps

  • SQL endpoint: no INSERT/UPDATE, but views, procedures and RLS are fine.
  • OPTIMIZE never deletes files; VACUUM does (and ends time travel past retention).
  • VACUUM below 7 days fails unless the retention check is disabled.
  • V-Order is off for Spark in new workspaces; changing it affects only future writes.
  • DROP on an external (path) table keeps the files.
  • dropDuplicates before MERGE: duplicate source keys make MERGE fail.
  • Partitioning by ID or day-over-years creates tiny files.
