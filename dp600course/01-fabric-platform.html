Fabric platform: OneLake, capacities, workspaces

The foundation every DP-600 question assumes: Fabric as a SaaS platform, its workloads, OneLake, which data store to choose, capacities and F SKUs (CUs, bursting, smoothing, throttling, pause/resume), licensing, the tenant → capacity → workspace → item hierarchy, domains, regions, the admin portal and workspace settings. Maps mainly to "Choose between a lakehouse, warehouse, or eventhouse" and to the platform knowledge behind Domain 1.

Fabric as a SaaS platform

Microsoft Fabric is an end-to-end analytics platform delivered as Software as a Service. You don't deploy clusters, storage accounts or servers: you buy (or try) a capacity, create workspaces on it and create items (lakehouse, warehouse, notebook, pipeline, semantic model, report…) inside the workspaces. All items share one data lake (OneLake), one compute currency (capacity units), one identity system (Microsoft Entra ID) and one governance layer (admin portal, Microsoft Purview integration).

OneLake

OneLake is the single, unified, logical data lake for the whole organization – "OneDrive for data".

  • Exactly one OneLake per tenant, provisioned automatically when Fabric is enabled; nothing to create or license separately.
  • Built on Azure Data Lake Storage (ADLS) Gen2 and compatible with its APIs and SDKs (DFS/Blob endpoints), so tools such as Azure Storage Explorer, Azure Databricks, Synapse or AzCopy can read/write it with Entra ID authentication.
  • Hierarchy: tenant (OneLake) → workspace (container) → item → folders/files/tables. Each workspace behaves like an ADLS container; each data item is a folder.
  • Tabular data is stored in Delta Lake format (Parquet files + transaction log), typically V-Order optimized. Warehouse, lakehouse, mirrored databases, SQL databases and (optionally) eventhouses all land Delta tables in OneLake.
  • OneCopy: Spark, T-SQL, KQL and Direct Lake read the same physical copy – no export between engines.
  • Shortcuts virtualize data from other OneLake locations, ADLS Gen2, Amazon S3 (and S3-compatible), Google Cloud Storage, Dataverse and more without copying (details on Get data).
  • Security in two planes: control plane (workspace roles, item permissions) and data plane (OneLake security roles) – see Security & governance.
  • Storage is billed per GB-month (pay as you go), independently of the capacity size; data stays when a capacity is paused.

A team of SQL developers must load a star schema with stored procedures that update several tables in a single transaction. Which item should they use?

  • Lakehouse, writing through its SQL analytics endpoint
  • Warehouse
  • Eventhouse
  • Semantic model in Import mode

The warehouse supports full T-SQL DML and multi-table transactions. The lakehouse SQL analytics endpoint is read-only for tables; an eventhouse is for streaming/KQL; a semantic model is not a write target.

Capacities and F SKUs

A capacity is a dedicated pool of compute measured in capacity units (CUs). All workloads in all workspaces assigned to the capacity share its CUs: Spark, SQL, KQL, dataflows, pipelines, semantic model queries and refreshes. Throttling happens per capacity – an overloaded capacity doesn't slow down other capacities.

  • Buying: F SKUs are Azure resources (resource type Microsoft Fabric capacity) created in the Azure portal in a subscription and region; you name one or more capacity admins. Billing is per second (1-minute minimum) pay-as-you-go, or cheaper with a one-year reservation.
  • Scale up or down at any time in the Azure portal (no data movement).
  • Pause/resume: an F capacity can be paused to stop compute billing; while paused, workspaces on it can't run anything and content is unavailable. OneLake storage keeps being billed. Pausing settles (bills) any accumulated smoothed future usage.
  • P SKUs (Power BI Premium per capacity) also run Fabric once Fabric is enabled, but Microsoft is retiring P SKU purchases – new customers buy F SKUs. EM and A SKUs do not support Fabric items.
  • Trial: a user starts a 60-day Fabric trial; it creates a trial capacity (64 CUs). Admins can disable trials in tenant settings ("Users can try Microsoft Fabric paid features").

Bursting, smoothing and throttling

Bursting: an operation may temporarily use more compute than the SKU provides so it finishes fast. Smoothing: the CU-seconds consumed are then spread ("smoothed") over future 30-second timepoints:

  • Interactive operations (report queries, DAX queries, most user-triggered requests): smoothed over a minimum of 5 minutes and up to 64 minutes.
  • Background operations (refreshes, pipelines, Spark jobs, almost all warehouse operations): smoothed over 24 hours (2,880 timepoints).

When smoothed usage exceeds 100 % you accumulate overage; unpaid overage becomes carryforward that is paid back (burndown) by idle capacity in later timepoints. Throttling is progressive, based on how much future capacity is already consumed:

Future capacity already usedPolicyEffect
≤ 10 minutesOverage protectionNo throttling – you may borrow up to 10 minutes of future capacity.
10 – 60 minutesInteractive delayNew interactive operations are delayed by 20 seconds at submission.
60 minutes – 24 hoursInteractive rejectionNew interactive operations are rejected; background jobs still start.
> 24 hoursBackground rejectionAll new requests, interactive and background, are rejected until burndown.
  • Operations already running when throttling starts are not stopped.
  • Real-Time Intelligence skips the 20-second delay stage (it starts at rejection).
  • Error text users see: CapacityLimitExceeded / "Your organization's Fabric compute capacity has exceeded its limits".
  • Ways out: wait (self-healing), scale up temporarily (faster burndown), pause and resume (bills the carryforward, then starts at zero), enable capacity overage billing (pay extra instead of throttling), move workspaces to another capacity, reschedule/optimize heavy jobs.
  • Surge protection (capacity setting) can reject new background jobs above a configured threshold to protect interactive users.
  • Autoscale Billing for Spark moves Spark jobs to separate pay-as-you-go billing; bursting/smoothing don't apply to that Spark usage.
  1. Overage protection – borrow up to 10 minutes of future capacity
  2. Interactive delay – 20-second delay for new interactive requests
  3. Interactive rejection – new interactive requests rejected
  4. Background rejection – all new requests rejected

Spark compute and CUs

  • 1 CU = 2 Spark VCores (an F64 gives 128 Spark VCores), with a burst factor that allows more concurrent Spark VCores for queued/concurrent jobs.
  • The starter pool (pre-warmed, medium nodes) starts sessions in seconds; custom pools let you choose node size, autoscale range and dynamic executor allocation but start slower.
  • High concurrency mode lets several notebooks (and pipeline notebook activities) share one Spark session, reducing start time and CU usage.

An overnight Spark job on an F8 briefly uses far more compute than the capacity provides, and the cost is accounted over the next 24 hours. Which two behaviors are described?

  • Autoscale and throttling
  • Smoothing and interactive delay

Using more compute than the SKU provides is bursting; spreading the consumption of a background operation over 24 hours is smoothing. No throttling stage is mentioned.

Regions and data residency

  • Data at rest lives in the region of the capacity the workspace is assigned to. To keep a business unit's data in a country, put its workspaces on a capacity created in a region in that country (multi-geo).
  • Tenant metadata lives in the home region chosen when the tenant was created.
  • Moving a workspace to a capacity in a different region is restricted when it contains non-Power BI Fabric items (lakehouse, warehouse, etc.) – those items must be removed or recreated; plan regions up front.
  • To reassign a workspace to another capacity you need the workspace Admin role plus assignment (contributor) permission on the target capacity – or be a capacity/Fabric admin.

A regulator requires that a business unit's data never leaves Switzerland. How do you satisfy this in Fabric?

  • Create a separate OneLake for the business unit in Switzerland
  • Assign the business unit's workspaces to a capacity created in a Swiss region
  • Apply a "Swiss" sensitivity label to all items
  • Assign the workspaces to a domain named Switzerland

Data residency follows the region of the capacity. There is only one OneLake per tenant; labels and domains are governance metadata and don't move data.

Admin portal and tenant settings

The admin portal (Settings → Admin portal) is available to Fabric administrators; capacity admins see their capacity settings. Main sections: Tenant settings, Usage metrics, Users, Premium Per User, Audit logs (opens Microsoft Purview), Domains, Capacity settings, Refresh summary, Embed codes, Organizational visuals, Azure connections, Workspaces, Custom branding, Fabric identities, Featured content.

  • Each tenant setting can be Enabled for the entire organization, enabled for specific security groups, and/or except specific security groups, or disabled.
  • Some settings can be delegated so capacity admins, domain admins or workspace admins can override them for their scope.
  • Changes apply going forward and can take several minutes to propagate; existing content keeps working (e.g. restricting workspace creation doesn't affect existing workspaces).

Data engineers complain that notebook sessions start slowly in their workspace and consume capacity because every notebook starts its own session. Which workspace-level configuration helps most?

  • Switch the workspace type to PPU
  • Create a custom pool with a larger node size
  • Use the starter pool and enable high concurrency mode in the Spark settings
  • Assign the workspace to a domain

The pre-warmed starter pool starts in seconds, and high concurrency lets several notebooks share one session. Custom pools start slower; PPU doesn't provide Spark; domains are governance only.

Scenario

Contoso runs all Fabric workloads on one F32 capacity. Every weekday at 09:00 a pipeline starts copying 200 tables in parallel, and report users then see slow visuals and occasional "capacity limits" errors. Executives (2,000 people with free licenses) will soon need to view the reports. The CFO wants the cheapest fix. What do you recommend?

  1. Diagnose with the Capacity Metrics app: confirm interactive delay/rejection on the Throttling chart and find the items (pipeline, refreshes) in the items matrix/timepoint drill-through.
  2. Reduce the load: move heavy background ingestion outside business hours and bound its parallelism (ForEach batch count), use incremental loads.
  3. Licensing forces sizing: 2,000 free-license viewers can only view Power BI content on F64 or larger (on F32 they'd each need Pro). Compare F64 against 2,000 Pro licenses – F64 is usually far cheaper and also adds CUs.
  4. Optionally separate workloads: a smaller capacity for data engineering and an F64 for reporting, so ETL bursts can't throttle report users (throttling is per capacity).
  5. Pause dev/test capacities when idle; keep production running.

Key takeaways & exam tips

  • One OneLake per tenant, automatic, ADLS Gen2-compatible APIs, Delta Parquet, OneCopy; discover with the OneLake catalog, sync files with OneLake file explorer.
  • Choose stores by language and pattern: Spark/files → lakehouse; T-SQL writes & multi-table transactions → warehouse; streaming/logs/KQL → eventhouse; OLTP → SQL database; BI layer → semantic model.
  • F SKU = CUs; F2…F2048; F64 is the threshold for free-license viewers; trial = 64 CUs for 60 days; PPU is not a Fabric capacity.
  • Smoothing: interactive 5–64 minutes, background 24 hours. Throttling: 10 min protection → 20 s interactive delay → interactive rejection (60 min) → background rejection (24 h).
  • Fix throttling by optimizing/rescheduling, scaling up, pausing/resuming (bills carryforward) or splitting capacities; diagnose with the Capacity Metrics app.
  • Hierarchy: tenant → capacity (region) → workspace (one capacity, one domain) → item. Data residency = capacity region.
  • Tenant settings can be scoped to security groups and delegated; they don't break existing content when tightened.
  • Workspace settings to remember: workspace type/capacity, Git, workspace identity, Spark pool/environment/high concurrency, network security, monitoring.
