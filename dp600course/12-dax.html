Column (ideally materialized upstream). Values that react to slicers → measure.
When is a calculated column computed?
At refresh, row by row. It is stored, uses memory and ignores slicers.
What does "Discourage implicit measures" do?
Stops dragging numeric columns as auto-sums; forces governed explicit measures. Turned on by calculation groups.

Ignore any Region slicer, keep all other filters. Which is correct?

  • CALCULATE([Sales Amount], ALL(Sales))
  • CALCULATE([Sales Amount], REMOVEFILTERS(Region))
  • CALCULATE([Sales Amount], ALLSELECTED(Region))
  • CALCULATE([Sales Amount], KEEPFILTERS(Region))

ALL(Sales) also clears dimension filters (expanded table); ALLSELECTED keeps the slicer.

Deep dive: evaluation order, AND/OR filters, USERELATIONSHIP and CROSSFILTER code
  1. Filter arguments are evaluated in the original filter context.
  2. Inside a row context, context transition turns the current row into a filter.
  3. Modifiers (ALL/REMOVEFILTERS, USERELATIONSHIP, CROSSFILTER, KEEPFILTERS) are applied.
  4. Filters apply: same column → replace (unless KEEPFILTERS); different columns → AND.
-- Boolean filter = FILTER ( ALL ( Product[Color] ), Product[Color] = "Red" )
Red Sales   = CALCULATE ( [Sales Amount], Product[Color] = "Red" )
Red Bikes   = CALCULATE ( [Sales Amount], Product[Color] = "Red", Product[Category] = "Bikes" )  -- AND
Red or Blue = CALCULATE ( [Sales Amount], Product[Color] IN { "Red", "Blue" } )             -- OR, same column
Red or Bikes = CALCULATE ( [Sales Amount],                                                  -- OR, two columns
    FILTER ( ALL ( Product[Color], Product[Category] ),
             Product[Color] = "Red" || Product[Category] = "Bikes" ) )
% of Category = DIVIDE ( [Sales Amount],
    CALCULATE ( [Sales Amount], ALLEXCEPT ( Product, Product[Category] ) ) )
Sales by Ship Date = CALCULATE ( [Sales Amount],
    USERELATIONSHIP ( Sales[ShipDateKey], 'Date'[DateKey] ) )
Customers Buying Selection = CALCULATE ( DISTINCTCOUNT ( Customer[CustomerKey] ),
    CROSSFILTER ( Sales[CustomerKey], Customer[CustomerKey], BOTH ) )

CROSSFILTER directions also include OneWay_LeftFiltersRight / OneWay_RightFiltersLeft.

Scenario: someone wants Sales–Product and Sales–Customer bidirectional for a "customers who bought the selected products" visual. Keep single-direction relationships. Use CROSSFILTER(…, BOTH) inside the one measure, or simply DISTINCTCOUNT(Sales[CustomerKey]), which Product already filters through Sales and is fastest. Model-wide bidirectional filters add ambiguity, slow every query and interact badly with RLS.

Avg Sales per Customer = AVERAGEX ( Customer, [Sales Amount] )
Wrong Avg = AVERAGEX ( Customer, SUM ( Sales[SalesAmount] ) )
Right Avg = AVERAGEX ( Customer, CALCULATE ( SUM ( Sales[SalesAmount] ) ) )
  1. ✓ Each customer row becomes a filter: per-customer sales.
  2. ✗ Row context does not filter SUM: grand total every row.
  3. ✓ Explicit CALCULATE fixes it.
Context transition = ?
Row context → filter context, done by CALCULATE (explicit or around a measure).
Why avoid it on the fact table?
One filter per row = many SE queries; duplicate rows multiply values. Iterate a dimension or VALUES(col).
VAR x = [Sales]; CALCULATE(x, …) returns?
The same value: a variable is evaluated once, where it is defined.

Which statement about context transition is TRUE?

  • CALCULATE in a row context turns the row into a filter; measure references do it implicitly
  • Every iterator does it, even without CALCULATE
  • It turns filter context into row context
  • Only in calculated tables

That is why SUMX(Customer, [Sales Amount]) works per customer.

Deep dive: iterator family, variables and cost
  • AVERAGEX, MINX, MAXX, COUNTX (counts non-blank results), FILTER (returns a table), CONCATENATEX (text list, e.g. titles), ADDCOLUMNS / SELECTCOLUMNS / GENERATE are iterators too.
  • RANKX(table, expr, [value], [order], [ties]): default DESC, ties SKIP; use ALL/ALLSELECTED; ISINSCOPE to blank totals.
  • Best Month Sales = MAXX ( VALUES ( 'Date'[YearMonth] ), [Sales Amount] ). Distinct customers: DISTINCTCOUNT(Sales[CustomerKey]).
  • Expensive: measure reference over a huge fact, IF/DIVIDE/text inside SUMX (SE callbacks), nested iterators, FILTER over whole tables.
  • Variables: readable, evaluated once (faster), easy debugging (RETURN an intermediate VAR); can hold tables, e.g. VAR Top = TOPN(10, …).
YoY % =
VAR CurrentSales  = [Sales Amount]
VAR PreviousSales = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
RETURN IF ( NOT ISBLANK ( CurrentSales ) && NOT ISBLANK ( PreviousSales ),
            DIVIDE ( CurrentSales - PreviousSales, PreviousSales ) )

Window functions

OFFSET, WINDOW, INDEX and RANK find the current row in a sorted relation and return rows relative to it.

Window function visualizer (Sales by month, 2026)
Click a bar to change the current month.
  1. Start with CALCULATE and the base measure [Sales Amount]
  2. Add OFFSET with delta -1 as the filter argument
  3. Define the relation: ALLSELECTED('Date'[YearMonth])
  4. Add ORDERBY('Date'[YearMonth], ASC)
  5. Optionally add PARTITIONBY to restart per year
  6. Test in DAX query view with EVALUATE SUMMARIZECOLUMNS

A running total must start at the first date selected in a slicer. Which is correct?

  • CALCULATE([Sales Amount], FILTER(ALL('Date'[Date]), 'Date'[Date] <= MAX('Date'[Date])))
  • CALCULATE([Sales Amount], FILTER(ALLSELECTED('Date'[Date]), 'Date'[Date] <= MAX('Date'[Date])))
  • CALCULATE([Sales Amount], DATESYTD('Date'[Date]))
  • SUMX(Sales, [Sales Amount])

ALL starts at the first date in the table; DATESYTD restarts every year.

Deep dive: signatures, helpers and gotchas
  • OFFSET(delta, [relation], [orderBy], [blanks], [partitionBy], [matchBy], [reset]) · INDEX(position, …) · WINDOW(from, ABS|REL, to, ABS|REL, …) · RANK([DENSE|SKIP], …) · ROWNUMBER (unique; ties must be broken by ordering).
  • Helpers: ORDERBY (default ASC), PARTITIONBY, MATCHBY (columns that uniquely identify a row). RANKX defaults to DESC, RANK to ASC.
  • If the visual sorts Month by MonthNumber, include both columns in the relation, or the wrong rows come back.
  • Window functions return blank on subtotals where no current row exists: often what you want for rankings.
Brand Rank = RANK ( DENSE, ALLSELECTED ( Product[Brand] ),
    ORDERBY ( [Sales Amount], DESC, Product[Brand], ASC ) )
Sales MA3 = AVERAGEX ( WINDOW ( -2, REL, 0, REL, ALLSELECTED ( 'Date'[YearMonth] ),
    ORDERBY ( 'Date'[YearMonth] ) ), [Sales Amount] )

Years don't add up to the grand total. Why?
Fact keys (e.g. 2027 orders) have no match in the Date table → "(Blank)" row. Fix the date range.

  
DIVIDE vs IFERROR?
DIVIDE returns BLANK (or an alternate) on zero and is optimized. IFERROR forces row-by-row checks.

A Category → Brand matrix shows rank 1 on every subtotal. Which function blanks the rank except at brand level?
  • HASONEVALUE(Product[Category])
  • ISFILTERED(Product[Brand])
  • ISINSCOPE(Product[Brand])
  • SELECTEDMEASURE()
ISINSCOPE is FALSE on subtotals; ISFILTERED can be TRUE via a slicer.


Which statement about DIVIDE vs the / operator is TRUE?
  • DIVIDE returns BLANK (or an alternate) on zero; / can error or return infinity
  • DIVIDE is slower than / with IFERROR
  • / returns BLANK on division by zero
  • DIVIDE only works in calculated columns
BLANK, not 0, keeps visuals from showing empty combinations.

Exam traps


    
  
  • ALL(Sales) removes dimension filters too (expanded table). Use REMOVEFILTERS(Dimension).
    • 
  
  • CALCULATE replaces a slicer on the same column; KEEPFILTERS intersects it.
    • 
  
  • SUM inside AVERAGEX without CALCULATE = no context transition = wrong result.
    • 
  
  • PARALLELPERIOD returns the whole year, not the same period.
    • 
  
  • RANK's ORDERBY defaults to ASC; RANKX defaults to DESC.
    • 
  
  • Running total from the slicer start needs ALLSELECTED, not ALL.
