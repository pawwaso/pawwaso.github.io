    Delegated identity (default)

    • Data read as the item owner
    • OneLake roles don't apply

    VS

    User identity mode

    • User identity passed to OneLake
    • OneLake security decides access
    • No DDM
    Deep dive: DefaultReader, limitations, shortcuts
    • DefaultReader exists in every lakehouse and gives everyone with ReadAll all data: edit or delete it to restrict access.
    • Limitations: no dynamic RLS (no USERPRINCIPALNAME), no multi-table RLS, no DDM, table renames break roles.
    • Enforced in Spark, Lakehouse explorer, OneLake APIs, shortcuts (source security applies), SQL endpoint in user identity mode, Direct Lake on OneLake.
    • Two paths, two locks: in delegated mode secure the SQL endpoint separately, or ReadData users see everything. Warehouse SQL RLS/CLS/DDM is bypassed by anyone with ReadAll reading Delta files via OneLake.

    SQL granular security

    T-SQL secures objects, columns, rows and values, on the SQL path only.

    GRANT SELECT ON SCHEMA::sales TO SalesReaders;
DENY  SELECT ON dbo.Payroll TO SalesReaders;
GRANT SELECT ON dbo.Employee (EmployeeID, Name) TO SalesReaders;  -- CLS allow-list
DENY  SELECT ON dbo.Employee (Salary) TO SalesReaders;            -- CLS deny
    • DENY beats GRANT. Users already reading via db_datareader need a column DENY.
    • With a denied column, SELECT * fails; a view is a friendly alternative.
    CREATE FUNCTION Security.fn_rls(@Rep AS varchar(256))
  RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS allowed
  WHERE @Rep = USER_NAME() OR IS_MEMBER('SalesManagers') = 1;
GO
CREATE SECURITY POLICY Security.SalesFilter
  ADD FILTER PREDICATE Security.fn_rls(SalesRepEmail) ON dbo.Sales
  WITH (STATE = ON);
    1. Inline table-valued function, WITH SCHEMABINDING.
    2. Row allowed when it belongs to the signed-in user, or the user is a manager.
    3. The security policy binds the function as a FILTER predicate (block predicates aren't supported).
    4. Turn it on. Enforced for every T-SQL query.
    ALTER TABLE dbo.Customer ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()');
GRANT UNMASK TO [FraudTeam];

    Masks results, not storage. Weak boundary: WHERE can infer values.

    Masking simulator
    Deep dive: roles, effects on Direct Lake, DDM limits
    • Custom roles: CREATE ROLE, ALTER ROLE … ADD MEMBER; fixed roles db_owner, db_datareader, db_datawriter, db_ddladmin. GRANT EXECUTE on procedures.
    • Users first need control-plane access (role or Read on the item) to connect.
    • SQL RLS applies to DirectQuery and Direct Lake fallback with SSO. Tables with SQL RLS make Direct Lake on SQL endpoint fall back to DirectQuery.
    • DDM isn't available through OneLake security and isn't applied via Spark/OneLake. Combine with RLS/CLS for real protection.
    1. Create a schema for security objects
    2. Create a predicate function WITH SCHEMABINDING using USER_NAME()
    3. Create a security policy with a FILTER PREDICATE
    4. Turn the policy on (STATE = ON)
    5. Test as a restricted user (e.g. a Viewer)

    Deep dive: RLS rules for the exam
    • Create roles in Desktop (Modeling → Manage roles), Tabular Editor/TMDL or web modeling; add members (preferably groups) in the service (model → Security).
    • Mapping table relates one-to-many to the dimension; mapping changes arrive with the next refresh, no model change.
    • USERNAME() returns DOMAIN\user in Desktop: prefer USERPRINCIPALNAME(). CUSTOMDATA() is for embedding.
    • Filters flow one → many; across bidirectional relationships enable "Apply security filter in both directions".
    • Test with View as (Desktop, "Other user" for dynamic) and Test as role (service).
    • Composite model over another model (DirectQuery): source RLS enforced; users need Build on the source.

    Deep dive: Direct Lake security details
    • DL on SQL endpoint: SQL RLS or SQL views → DirectQuery fallback; SQL CLS/OLS on a used column → error. DirectLakeOnly makes such queries fail.
    • DL on OneLake: enforces OneLake security in memory, never falls back; denied access → visual errors. OneLake roles are unioned, then intersected with model roles.
    • The model owner needs read access to source tables, or framing fails.
    • With SSO, users who can query the lakehouse directly bypass model RLS.
    • Defense in depth: Import model over a SQL endpoint → CLS in SQL and OLS in the model.

    Deep dive: more governance facts
    • One endorsement badge per item; endorsed items are filterable in the OneLake catalog. Pattern: certify the enterprise model + grant Build.
    • DLP policies scan models and lakehouses for sensitive info types and raise alerts/policy tips. Purview protection policies can restrict access by label.
    • Purview hub: tenant-wide insights for admins (label coverage, endorsement), item insights for owners. Purview Unified Catalog can scan the Fabric tenant.
    • Domains: a workspace belongs to ≤ 1 domain; assign by name, admin or capacity; subdomains exist; filter the catalog by domain.
    • Monitoring: report usage metrics; Monitoring hub (runs); workspace monitoring (KQL logs); Capacity Metrics app; OneLake diagnostics (data access audit).
    • Workspace identity is created/deleted by a workspace Admin, deleted with the workspace; trusted access needs an F SKU and a resource instance rule. Use non-personal identities so refreshes survive staff leaving.

    • Contributors bypass model RLS, OLS and OneLake security: test with a Viewer.
