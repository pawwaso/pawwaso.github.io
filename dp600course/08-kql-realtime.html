Eventhouse & KQL

Real-Time Intelligence in Fabric: how streaming data flows from an eventstream into an eventhouse / KQL database, how it is kept (update policies, materialized views, retention, caching, OneLake availability) and, above all, how to read and write the Kusto Query Language (KQL) the exam expects. Maps to the DP-600 skills Prepare data → Get data (real-time ingestion) and Query and analyze data → select, filter and aggregate data by using KQL.

DP-600 does not test KQL management commands in depth, but it does show you short KQL queries and asks which one returns a given result, which operator is faster (has vs contains), what the default join kind is, and which Fabric item to use for streaming telemetry. Learn to read a pipe from top to bottom.

Real-Time Intelligence at a glance

Real-Time Intelligence (RTI) is the Fabric workload for event-based, time-stamped data: telemetry, logs, IoT signals, clickstreams, security events, CDC feeds. Its building blocks are separate Fabric items that you chain together:

Eventhouse vs KQL database

An eventhouse is the workspace item you create first. Creating it also creates a KQL database with the same name inside it; you can add more databases later. The eventhouse is the unit of compute and monitoring; the database is the unit of schema, policies and permissions.

You create an eventhouse named TelemetryEH in a workspace. Without any further action, what does the workspace contain?

  • Only the eventhouse; databases must be created before tables can be added
  • The eventhouse and a lakehouse used as its storage
  • The eventhouse and a KQL database named TelemetryEH
  • The eventhouse, a KQL database and a default semantic model

Update policies (ingest-time transformation)

An update policy on a target table runs a KQL query (usually a stored function) whenever data is ingested into a source table, and appends the result to the target. Classic medallion-in-KQL pattern: raw (bronze) table with a dynamic column → update policy → typed silver table.

// 1. raw landing table
.create table RawEvents (Payload: dynamic)

// 2. function that shapes the raw data
.create-or-alter function ParseRaw() {
    RawEvents
    | project Timestamp   = todatetime(Payload.ts),
              DeviceId    = tostring(Payload.deviceId),
              Temperature = toreal(Payload.temp)
}

// 3. typed target table + update policy
.create table Telemetry (Timestamp: datetime, DeviceId: string, Temperature: real)

.alter table Telemetry policy update
@'[{"IsEnabled": true, "Source": "RawEvents", "Query": "ParseRaw()", "IsTransactional": false}]'

Commands that change metadata start with a dot (.create, .alter, .show); queries do not. Set IsTransactional to true if a failure of the policy must also fail the ingestion into the source table. A short retention (even 0) on the raw table is common once the policy has done its job.

Materialized views

A materialized view is an always-up-to-date summarize over a source table. The engine stores the already-aggregated part and aggregates only the new delta at query time, so the result is always fresh and cheap to query. Typical uses: latest record per key (arg_max), deduplication (take_any), hourly/daily rollups.

.create materialized-view with (backfill = true) DeviceLatest on table Telemetry
{
    Telemetry
    | summarize arg_max(Timestamp, *) by DeviceId
}

// query it like a table (or force the materialized part only)
DeviceLatest | where Temperature > 8
materialized_view("DeviceLatest")
Update policyMaterialized viewStored function
When it runsAt ingestion time, per batchContinuously in the background + delta at query timeAt query time

Use forParsing, enrichment, routing, filteringLatest value, dedup, rollupsReusable query logic, parameterised queries

Retention and caching policies

  • Retention policy (soft-delete period): data older than the period is removed automatically from the table or materialized view. In Fabric the default is 3,650 days (minimum 1 day, maximum 36,500 days, or Unlimited).
  • Caching policy (hot cache): how much recent data is kept on local SSD/memory for fast queries; older data stays queryable from cold storage, only slower. Default 3,650 days; the cache period must be ≤ retention.
  • Set in the UI (database → Manage → Data policies) or with commands. Policies can be set at database level and overridden per table.
.alter-merge table Telemetry policy retention softdelete = 90d
.alter table Telemetry policy caching hot = 14d
.show table Telemetry policy retention
Rule of thumb: retention answers "how long do I keep it?" (cost of storage, compliance); caching answers "how much do I query fast?" (performance vs premium storage cost).

OneLake availability

Turn on OneLake availability at database or table level to expose KQL tables as Delta tables in OneLake (a logical copy, no extra storage charge). Then lakehouses and warehouses can reference them through shortcuts, Spark notebooks can read them, a SQL analytics endpoint can query them, and Power BI can use Direct Lake (Direct Lake on OneLake supports KQL databases).

  • Database level: applies to new tables; tick Apply to existing tables to backfill historic data.
  • The database retention policy also applies to the OneLake copy.
  • Data is batched into well-sized Parquet files; write latency is adaptive, by default up to 3 hours or until files are big enough (configurable 5 min–3 h via the mirroring policy TargetLatencyInMinutes).
  • While enabled you cannot rename tables, alter a column type, apply RLS to the table, or delete/truncate/purge data — turn it off, make the change, turn it on again. Adding or dropping columns is allowed.
  • The Delta copy is read-only.

Data engineers must analyze tables of a KQL database from a lakehouse notebook and from a Direct Lake semantic model, without building a copy process. What should you do?

  • Schedule a pipeline that exports the KQL tables to Parquet nightly
  • Turn on OneLake availability for the KQL database and create shortcuts in the lakehouse
  • Mirror the KQL database into a warehouse
  • Create a materialized view for each table

OneLake availability publishes the KQL tables as Delta in OneLake; shortcuts make them visible to Spark, the SQL analytics endpoint and Direct Lake. Exports add a copy process, "mirroring a KQL database" is not a feature, and materialized views stay inside the KQL database.

KQL fundamentals

A KQL query is a data flow: start with a table (or function, or let variable) and pass the rows through operators separated by the pipe |. Each operator receives the output of the previous one. Order matters — filter early, project early, aggregate late.

Telemetry                                   // source table
| where Timestamp > ago(1h)                 // filter rows (time first!)
| where DeviceId startswith "TRK"
| summarize AvgTemp = avg(Temperature),     // aggregate
            Readings = count()
            by DeviceId
| where AvgTemp > 8                         // filter on aggregated value (= HAVING)
| top 10 by AvgTemp desc                    // sort + limit
  • Case sensitivity: table, column and function names are case-sensitive; operator keywords are lower case (where, not WHERE). == is case-sensitive, =~ is case-insensitive.
  • Comments use //. Strings use double or single quotes. Datetime literals: datetime(2026-11-04); timespans: 30s, 5m, 1h, 7d.
  • Equality is == (single = is assignment, e.g. in extend). Logical operators: and, or, not().
  • Several statements in one query are separated by ; (needed after let).

Filtering rows: where, time functions, between

Telemetry | where Timestamp > ago(24h)                         // last 24 hours
Telemetry | where Timestamp between (datetime(2026-10-01) .. datetime(2026-10-31))
Telemetry | where Timestamp >= startofday(now()) and Temperature > 8
Telemetry | where DeviceId in ("TRK-01", "TRK-02")           // case-sensitive list
Telemetry | where isnotempty(DeviceId) and isnotnull(Temperature)
Telemetry | where Temperature between (2.0 .. 8.0)            // inclusive range

ago(timespan) = now() - timespan (UTC). between is inclusive on both ends and uses ... Other handy date functions: startofday/week/month/year(), endofday(), datetime_part(), format_datetime(), dayofweek(), datetime_add(), datetime_diff().

String predicates: has vs contains (the term index)

KQL splits string values into terms — maximal sequences of alphanumeric characters — and indexes every term of three or more characters. Operators with has in their name use this term index; contains, startswith, endswith scan the values.

ExpressionResultWhy
"North America" has "america"truewhole term, case-insensitive
"KustoExplorerQueryRun" has "Explorer"false"Explorer" is not a separate term
"KustoExplorerQueryRun" contains "Explorer"truesubstring match (scan)
"North America" hasprefix "ame"trueprefix of a term
"Fabrikam" startswith "fab"truestart of the whole string
"abc" =~ "ABC"truecase-insensitive equality
  • Prefer has / in / == when you search for a whole word — has is faster than contains.
  • Prefer case-sensitive variants (== over =~, has_cs over has, in over in~) when possible; suffix _cs = case-sensitive.
  • has_any("a","b"), has_all(...), matches regex, negations with ! (!has, !contains).

A Logs table has billions of rows. You need rows whose Message contains the word timeout (always surrounded by spaces or punctuation). Which predicate is MOST efficient?

  • where Message contains "timeout"
  • where Message matches regex "timeout"
  • where Message like "%timeout%"
  • where Message has "timeout"

has looks up a whole term in the term index; contains and regex scan every value. like is SQL, not KQL.

Shaping columns: project, extend and friends

Telemetry
| project Timestamp, DeviceId, TempC = Temperature        // keep / rename / compute columns
| extend TempF = TempC * 9 / 5 + 32,                      // add computed columns, keep the rest
         Band  = case(TempC < 2, "Too cold", TempC > 8, "Too warm", "OK")
| project-away TempC                                      // drop columns
| project-rename Device = DeviceId                        // rename only
| project-reorder Timestamp, Device                       // reorder
  • project = SQL SELECT col list (only listed columns remain). extend adds columns and keeps all existing ones.
  • iff(cond, a, b) for if/else, case() for multiple branches, coalesce(), strcat(), tostring(), toint(), toreal(), todatetime(), round().

Time buckets: bin()

bin(value, size) rounds down to a multiple of size — the KQL way to group by minute/hour/day (also works on numbers: bin(Price, 10)).

Telemetry
| where Timestamp > ago(7d)
| summarize AvgTemp = avg(Temperature) by DeviceId, bin(Timestamp, 1h)
| render timechart
Rows that do not exist produce no bin. If you need a value (e.g. 0) for every empty hour, use make-series instead of summarize ... by bin().

Sorting and limiting: sort/order, top, take

Telemetry | sort by Timestamp desc            // order by = alias of sort by
Telemetry | sort by Temperature                // DEFAULT IS DESCENDING!
Telemetry | top 5 by Temperature               // sort + take in one operator (desc by default)
Telemetry | take 100                           // any 100 rows, no order (limit = alias)
Telemetry | distinct DeviceId, Region          // unique combinations
sort by and top default to descending (nulls last for desc) — the opposite of SQL ORDER BY. take returns arbitrary rows; it is not "the first N" unless you sort first (use top).

Which query returns the five devices with the highest average temperature over the last day?

  • Telemetry | where Timestamp > ago(1d) | summarize Avg = avg(Temperature) by DeviceId | top 5 by Avg
  • Telemetry | take 5 | summarize Avg = avg(Temperature) by DeviceId
  • Telemetry | where Timestamp > ago(1d) | top 5 by Temperature | summarize avg(Temperature) by DeviceId
  • Telemetry | summarize Avg = avg(Temperature) by DeviceId | sort by Avg asc | take 5

Filter, aggregate, then top 5 by Avg (descending by default). Option 2 samples 5 arbitrary rows first; option 3 takes the 5 hottest single readings before aggregating; option 4 sorts ascending (lowest) and ignores the time window.

Combining tables: join, lookup, union

Telemetry
| where Timestamp > ago(1h)
| join kind=inner (Devices | project DeviceId, Site, Owner) on DeviceId

// different column names on each side
Telemetry
| join kind=leftouter Devices on $left.DeviceId == $right.Id
kindReturns
innerunique (default!)Deduplicates the left side on the join key (keeps one arbitrary row per key), then inner-joins. Can silently drop left rows with duplicate keys.
innerStandard inner join: every matching combination (like SQL INNER JOIN)
leftouter / rightouter / fullouterOuter joins; unmatched columns are null/empty
leftanti (anti) / rightantiRows of one side with no match (SQL NOT EXISTS)
leftsemi / rightsemiRows of one side that have a match, only that side's columns (SQL EXISTS)
  • When you omit kind, you get innerunique. If you need SQL semantics, write kind=inner explicitly.
  • Put the smaller table on the left; filter and project both sides before joining. Hints: hint.strategy=broadcast (small left side), hint.shufflekey=Key (high-cardinality keys).
  • lookup is an optimized join for enriching a large fact with a small dimension (right side is loaded in memory; default leftouter).
  • union Table1, Table2 stacks rows (like SQL UNION ALL, columns matched by name; withsource=SourceTable adds the source name; wildcards such as union Logs_* allowed).

A query uses Orders | join Customers on CustomerId without a kind. Orders has many rows per customer. Analysts notice that only one order per customer is returned. Why?

  • KQL joins are always left semi joins
  • The default join kind is innerunique, which deduplicates the left side on the key
  • KQL joins return only the first matching row of the right side
  • The on clause must use $left and $right

With no kind, KQL uses innerunique: left rows are deduplicated by key before the inner join. Put the smaller table (Customers) on the left, or specify kind=inner.

Variables and reuse: let

let threshold = 8.0;
let window    = 1h;
let hotDevices =
    Telemetry
    | where Timestamp > ago(window) and Temperature > threshold
    | distinct DeviceId;
Devices
| where DeviceId in (hotDevices)            // tabular let used as a list
| project DeviceId, Site, Owner

let binds a scalar, a tabular expression or a function (let f = (x:real) { x * 2 };). Each let ends with a semicolon. To persist a function in the database, use .create-or-alter function.

Parsing and semi-structured data: parse, extract, mv-expand

// "Device TRK-07 reported 9.4C at dock 12"
Logs
| parse Message with "Device " DeviceId " reported " Temp:real "C at dock " Dock:int
| project Timestamp, DeviceId, Temp, Dock

// JSON payload in a dynamic column
RawEvents
| extend ts = todatetime(Payload.ts), tags = Payload.tags     // dot or ['x'] access
| mv-expand tag = tags to typeof(string)                        // one row per array element
| summarize count() by tag
  • parse extracts columns from a string using a pattern of literals and typed column names; extract(regex, group, text) pulls a regex group; parse_json() (alias todynamic()) turns a JSON string into dynamic.
  • mv-expand turns each element of an array (or property bag) into its own row — like SQL CROSS APPLY OPENJSON or Spark explode(). The reverse is summarize make_list().
  • bag_unpack() plugin spreads a property bag into columns: | evaluate bag_unpack(Payload).

Visualising and time series: render, make-series

// regular time series with zero-filled gaps, one series per device
Telemetry
| where Timestamp > ago(7d)
| make-series AvgTemp = avg(Temperature) default = 0
    on Timestamp from ago(7d) to now() step 1h
    by DeviceId
| extend (anomalies, score, baseline) = series_decompose_anomalies(AvgTemp, 1.5)
| render anomalychart with (anomalycolumns = anomalies)
  • render must be the last operator: timechart, linechart, columnchart, barchart, piechart, areachart, scatterchart, anomalychart, card… It is a hint to the client (queryset, dashboard) and doesn't change data.
  • make-series creates arrays (one per group) on a fixed time axis with a default for empty steps — required input for series functions: series_decompose_anomalies() (anomaly detection), series_decompose_forecast() (forecast), series_fir() (moving average filter), series_stats(), series_fit_line() (trend).
  • summarize ... by bin() → table rows; make-series → arrays per group. Use mv-expand to turn series back into rows.

Let the engine translate: explain

KQL databases accept a read-only subset of T-SQL. To see the KQL equivalent of a SQL query, prefix it with a comment line -- and the keyword explain:

--
explain
SELECT COUNT_BIG(*) AS C FROM StormEvents

// Output:
// StormEvents
// | summarize C=count()
// | project C

Great for learning, and for SQL-savvy analysts; but write production queries in KQL — T-SQL support is limited (no DML, many KQL-only features such as bin, make-series, render).

Exercise: build a pipe in the right order

Requirement: for the last 24 hours, show the hourly average temperature of the 3 devices that had the most readings above 8 °C, as a time chart.

  1. let hot = Telemetry | where Timestamp > ago(24h) and Temperature > 8 | summarize n = count() by DeviceId | top 3 by n | project DeviceId;
  2. Telemetry
  3. | where Timestamp > ago(24h)
  4. | where DeviceId in (hot)
  5. | summarize AvgTemp = avg(Temperature) by DeviceId, bin(Timestamp, 1h)
  6. | render timechart
Why this order?

The let must come first and end with ;. Then start from the table, filter by time first (cheap, uses the time index), then by the device list, aggregate into hourly bins, and render last. Swapping summarize before where DeviceId in also works but aggregates devices you throw away.

  1. Telemetry
  2. | where Region == "North"
  3. | summarize arg_max(Timestamp, *) by DeviceId
  4. | project DeviceId, Timestamp, Temperature
  5. | sort by Timestamp desc

KQL querysets, Real-Time dashboards and Copilot

KQL queryset

  • A standalone Fabric item holding KQL (and T-SQL) queries in tabs, each tab connected to a data source: a KQL database in Fabric, an Azure Data Explorer cluster, or Azure Monitor (Log Analytics / Application Insights).
  • Every KQL database also has an embedded queryset for quick exploration.
  • Run the query under the cursor (Shift+Enter) or selected text; view results as table or chart; export to CSV; pin a query to a Real-Time dashboard; create a Power BI report from the query (DirectQuery to the KQL database); set an Activator alert on results.
  • Share the queryset like any item; readers need access to the underlying database to run queries.

Real-Time dashboards

  • Each tile is a KQL query plus a visual. Dashboards support parameters (time range, multi-select dropdowns fed by a query), base queries reused by tiles, cross-filtering and drill-through, conditional formatting, auto refresh (editor sets a minimum interval; viewers pick their own above that), and JSON export/import.
  • Queries hit the eventhouse directly on every refresh — no semantic model, no refresh schedule. Ideal for operational, seconds-fresh monitoring; a Power BI report is better for curated business KPIs over a governed model.
  • Tiles can be created from a queryset (Pin to dashboard), and an Activator rule can be set on a tile.

Copilot for Real-Time Intelligence

  • Copilot in the KQL queryset turns natural language into KQL ("show the average temperature per device in the last hour as a timechart"), explains and refines queries. It uses the database schema as context; always review the query (check time filters and join kinds).
  • Copilot can also help create Real-Time dashboard tiles. Requires a paid Fabric capacity with Copilot enabled in tenant settings.

Scenario. A logistics company streams refrigerated-truck telemetry from Azure IoT Hub (50,000 events/s, 30% are heartbeat messages). Requirements: (1) operations staff see per-truck temperatures with < 30 s latency; (2) a Teams message goes to the dispatcher when a truck stays above 8 °C for 5 minutes; (3) data scientists analyze 2 years of history in Spark; (4) only 13 months must be queried fast, older data rarely; (5) finance builds a monthly Power BI report in a Direct Lake model. Design the solution.

  • Eventstream with IoT Hub source; a Filter operation drops heartbeats before storage (cheapest place). Destination: eventhouse (KQL database table Telemetry). Optionally an update policy parses raw JSON into a typed table.
  • (1) Real-Time dashboard with tiles such as Telemetry | where Timestamp > ago(15m) | summarize arg_max(Timestamp, *) by TruckId, auto refresh every 30 s; a materialized view arg_max(Timestamp,*) by TruckId makes "latest per truck" cheap.
  • (2) Activator rule on the eventstream (or on the dashboard tile) with a condition "Temperature > 8 for 5 minutes" → Teams message action.
  • (3) + (5) Turn on OneLake availability; create a shortcut in a lakehouse for Spark; build a Direct Lake model (or aggregate monthly in a gold Delta table first). Retention applies to the OneLake copy too, so set retention to at least 2 years.
  • (4) Retention policy 730 days (2 years) and caching policy hot = 395 days (≈13 months); cache ≤ retention.

You need queries over the last 30 days to be fast, while keeping one year of data queryable at lower cost. Which configuration should you apply to the table?

  • Retention 30 days, caching 365 days
  • Retention 30 days, caching 30 days, plus OneLake availability
  • Retention 365 days, caching 30 days
  • Retention 365 days, caching 365 days

Retention controls how long data is kept (365 d); the caching policy keeps the most recent 30 d in hot cache. Caching cannot exceed retention, and caching everything costs more than required.

You must always return the most recent reading per device from a table that receives millions of rows per hour, with minimal query cost for a Real-Time dashboard that refreshes every 10 seconds. What should you create?

  • An update policy that deletes old rows per device
  • A materialized view with summarize arg_max(Timestamp, *) by DeviceId
  • A stored function with top 1 by Timestamp
  • A caching policy of 1 hour

A materialized view keeps the aggregation pre-computed and only processes the new delta at query time. A function recomputes on every refresh; top 1 returns one row overall, not per device; caching does not aggregate.

An analyst who knows only SQL wants to learn the KQL equivalent of a T-SQL SELECT ... GROUP BY query against a KQL database. What is the quickest way?

  • Run the SQL in the queryset prefixed with -- and explain
  • Run the SQL through the warehouse SQL query editor with a cross-database query
  • Use the visual query editor of the KQL database
  • Convert it with the DAX query view

explain returns the KQL translation of a supported T-SQL query. KQL databases have no visual query editor, and DAX query view targets semantic models.

Which statement about Telemetry | summarize count() by bin(Timestamp, 5m) is TRUE?

  • It returns a row for every 5-minute interval, including intervals without data (count 0)
  • It returns arrays of counts, one per device
  • It fails because bin() works only with numbers
  • It returns one row per 5-minute interval that contains at least one row

summarize ... by bin() only produces groups that exist. Use make-series ... default=0 to fill gaps with zeros and get arrays.

Key takeaways & exam tips

  • Chain: sources → eventstream (filter/route) → eventhouse / KQL database → KQL queryset, Real-Time dashboard, Power BI → Activator for actions. Discover streams in the Real-Time hub.
  • Creating an eventhouse creates a KQL database with the same name. Eventhouse = container + shared compute; database = schema + policies.
  • Filter unwanted events in the eventstream before storing. Parse raw data at ingest with an update policy; keep "latest per key" or rollups with a materialized view.
  • Retention = how long data is kept (default 3,650 days); caching = how much is hot (default 3,650 days, must be ≤ retention).
  • OneLake availability exposes KQL tables as Delta → shortcuts, Spark, SQL endpoint, Direct Lake; retention applies to the copy; no rename/column-type change while it is on.
  • KQL reads top to bottom: T | where | extend/project | summarize ... by bin() | top/sort | render. Names are case-sensitive; == compares, = assigns.
  • has (term index, ≥ 3-char terms) is faster than contains (substring scan). between is inclusive with ... ago(1h) = now minus one hour.
  • dcount is approximate; arg_max(Timestamp, *) returns the latest row per group; percentiles() returns several percentiles.
  • sort by and top default to descending; take is unordered.
  • Default join kind is innerunique (left side deduplicated) — use kind=inner for SQL semantics; smaller table on the left.
  • let statements end with ;. render is always last. make-series + series_* functions for gap-filled time series, anomalies and forecasts.
  • T-SQL → KQL: prefix with -- and explain. Copilot in the queryset writes KQL from natural language — still check the time filter and join kind.
