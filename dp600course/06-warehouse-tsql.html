Warehouse & T-SQL

The Fabric Data Warehouse: architecture, the T-SQL surface area (what works, what doesn't), data types, loading with COPY INTO / CTAS / pipelines / Dataflow Gen2, zero-copy clones, time travel, restore points, programmability, statistics, transactions, caching and query insights – and how it differs from a lakehouse SQL analytics endpoint. Maps to Prepare data (get, transform and query data with T-SQL) and Maintain a data analytics solution (monitoring, recovery).

Architecture

  • Delta under the hood: every warehouse table is stored as Delta Parquet in OneLake (written with V-Order by default). Spark, Direct Lake, other warehouses and shortcuts can read the same files – no export needed (OneCopy).
  • Distributed, serverless engine: compute is separated from storage and scales automatically within your Fabric capacity; there are no distributions, indexes or pools for you to manage. The same engine powers every SQL analytics endpoint.
  • Read-write T-SQL: full DML (INSERT, UPDATE, DELETE, MERGE, TRUNCATE), DDL, multi-table ACID transactions, stored procedures, views, functions.
  • Automatic maintenance: data compaction and garbage collection run in the background – no OPTIMIZE/VACUUM to schedule.
  • Cross-database queries with three-part names (database.schema.table) across warehouses and SQL analytics endpoints in the same workspace, without copying data. In the query editor, add the other item to the Explorer (+ Warehouses) first. Data in other workspaces: create a lakehouse shortcut and query it through that endpoint.
  • Connect with the Fabric query editor, visual query editor, SSMS, VS Code (mssql), any TDS client via the SQL connection string; Spark via the synapsesql connector.

The surface area changes often. When migrating, check the current "T-SQL surface area" and "Limitations" pages on Microsoft Learn. As of late 2026: IDENTITY (BIGINT) and MERGE are supported; triggers are not, so auditing logic has to move into load procedures or pipelines.
CREATE TABLE dbo.DimCustomer
(
    CustomerKey    BIGINT IDENTITY,          -- surrogate key generated by the engine
    CustomerID     VARCHAR(20)  NOT NULL,    -- business key

ALTER TABLE dbo.DimCustomer
  ADD CONSTRAINT PK_DimCustomer PRIMARY KEY NONCLUSTERED (CustomerKey) NOT ENFORCED;

ALTER TABLE dbo.FactSales
  ADD CONSTRAINT FK_FactSales_Customer FOREIGN KEY (CustomerKey)
  REFERENCES dbo.DimCustomer (CustomerKey) NOT ENFORCED;

Declared (unenforced) keys still help: tools read them (e.g. relationship detection) and the optimizer can use them. But a duplicate key is not rejected – validate in the load.

COPY INTO examples

-- Parquet from OneLake (lakehouse Files) – caller's Entra identity is used, no CREDENTIAL needed
COPY INTO dbo.FactSales
FROM 'https://onelake.dfs.fabric.microsoft.com/<workspaceId>/<lakehouseId>/Files/sales/2026/*.parquet'
WITH (FILE_TYPE = 'PARQUET');

-- Gzipped CSV from ADLS Gen2 with SAS, skip header, capture rejected rows
COPY INTO dbo.StageCustomer (CustomerID 1, CustomerName 2, City DEFAULT 'Unknown' 3)
FROM 'https://contosolake.dfs.core.windows.net/raw/customers/*.csv.gz'
WITH (
    FILE_TYPE       = 'CSV',
    CREDENTIAL      = (IDENTITY = 'Shared Access Signature', SECRET = '<sas-token>'),
    COMPRESSION     = 'Gzip',
    FIELDTERMINATOR = ',',
    ROWTERMINATOR   = '0x0A',
    FIRSTROW        = 2,
    MAXERRORS       = 10,
    ERRORFILE       = '/rejected'          -- writes a _rejectedrows folder
);

-- Firewalled storage: authorize with the workspace identity (+ trusted workspace access)
COPY INTO dbo.Orders
FROM 'https://securelake.blob.core.windows.net/raw/orders/'
WITH (FILE_TYPE = 'PARQUET', CREDENTIAL = (IDENTITY = 'Workspace Identity'));
  • Authentication: Entra ID of the executing user (default – no CREDENTIAL), SAS (needs Read + List), storage account key, or Workspace Identity. Firewalled storage: Entra ID or workspace identity, with the workspace added as a resource instance rule. OneLake sources: Entra ID or workspace identity.
  • For Parquet, column names must match exactly (non-matching target columns get NULL); type conversion errors fail the load regardless of MAXERRORS. ERRORFILE applies to CSV and JSONL.
  • COPY INTO runs in the caller's SQL security context – a low-privileged loader doesn't need CONTROL on the warehouse.

CTAS and INSERT…SELECT

-- Build a gold table in one set-based step
CREATE TABLE gold.FactSalesDaily
AS
SELECT  d.DateKey, p.ProductKey, c.CustomerKey,
        SUM(s.Quantity)              AS Quantity,
        SUM(s.Quantity * s.UnitPrice) AS SalesAmount
FROM    silver.Sales     AS s
JOIN    gold.DimDate     AS d ON d.[Date] = CAST(s.OrderDate AS date)
JOIN    gold.DimProduct  AS p ON p.ProductID = s.ProductID
JOIN    gold.DimCustomer AS c ON c.CustomerID = s.CustomerID AND c.IsCurrent = 1
GROUP BY d.DateKey, p.ProductKey, c.CustomerKey;

-- Idempotent reload of one day
DELETE FROM gold.FactSalesDaily WHERE DateKey = 20261103;
INSERT INTO gold.FactSalesDaily (DateKey, ProductKey, CustomerKey, Quantity, SalesAmount)
SELECT … WHERE CAST(s.OrderDate AS date) = '2026-11-03' …;

Zero-copy table clone

-- Current state
CREATE TABLE dbo.FactSales_Test AS CLONE OF dbo.FactSales;

-- Point in time (UTC) within the retention period
CREATE TABLE test.FactSales_0101 AS CLONE OF dbo.FactSales AT '2026-11-01T00:00:00.000';
  • Copies only metadata; the clone references the same Parquet files → near-instant, minimal storage (extra storage only as the tables diverge).
  • Clone and source are independent: later DML/DDL on either isn't reflected in the other. Either can be dropped freely.
  • Within or across schemas of the same warehouse; groups of tables can be cloned at the same point in time. Not across warehouses or workspaces, not on the SQL analytics endpoint, and no warehouse/schema-level clone.
  • Inherits object-level security, RLS, dynamic data masking and PK/unique constraints of the source.
  • Permissions: Admin/Member/Contributor workspace role (Viewer can't), SELECT on all source rows/columns, CREATE TABLE in the target schema.
  • Uses: dev/test copies of production, stable reporting snapshots, recovery after a bad release, archiving month-end state.

Time travel, retention and restore points

Time travel with FOR TIMESTAMP AS OF

SELECT c.Country, SUM(f.SalesAmount) AS Sales
FROM dbo.FactSales AS f
JOIN dbo.DimCustomer AS c ON c.CustomerKey = f.CustomerKey
GROUP BY c.Country
OPTION (FOR TIMESTAMP AS OF '2026-11-03T18:00:00.000');   -- UTC, max 3 fractional digits
  • Applies to the whole statement (all joined tables) and can appear only once; queries must begin with SELECT; results are read-only.
  • Timestamps are UTC in format yyyy-MM-ddTHH:mm:ss[.fff]. Can be used inside stored procedures and to query a view as of a time, but a view definition can't contain it.
  • Returns the latest schema; querying before a schema change only works for columns that existed then. Dropping and recreating a table loses its history.
  • Any workspace role (Admin, Member, Contributor, Viewer) can time travel; RLS/CLS/DDM still apply.
  • On a lakehouse SQL analytics endpoint, time travel is bounded by the Delta VACUUM retention (and requires the new metadata sync).

Data retention

Warehouse history is retained for a configurable 1–120 days, default 30 calendar days. This window bounds time travel, point-in-time clones and restore points.

Restore points and restore in-place

  • System-created restore points every 8 hours while the warehouse is active (RPO 8 h); can't be deleted. User-defined restore points can be created any time (e.g. before a big release) by Admin/Member/Contributor.
  • Restore points copy metadata only; at least 20 are kept with ≥30-day retention.
  • Restore in-place replaces the entire warehouse (same name) with its state at the restore point – including objects, Query Insights and modelling. Only workspace Admins can restore. You can't restore to a new warehouse with a different name.
  • Deleted warehouse items can be recovered with the tenant's item recovery (dropped item retention) feature.
  • Report on yesterday 18:00 UTC while ETL is running
  • Compare today's totals with last week's without creating objects
  • Testers need a modifiable copy of a 2 TB table in seconds
  • Keep a month-end snapshot table for auditors
  • A failed release corrupted many tables; roll back the whole warehouse
  • Reset a dev warehouse to its state before a migration test

-- Inline table-valued function
CREATE FUNCTION dbo.fn_SalesByYear (@Year INT)
RETURNS TABLE
AS RETURN
    SELECT ProductKey, SUM(SalesAmount) AS Sales
    FROM dbo.FactSales WHERE YEAR(OrderDate) = @Year
    GROUP BY ProductKey;
GO

-- Stored procedure called by a pipeline Stored procedure activity
CREATE PROCEDURE etl.usp_LoadSales @LoadDate DATE
AS
BEGIN
    BEGIN TRY
        BEGIN TRAN;
        DELETE FROM dbo.FactSales WHERE OrderDate = @LoadDate;
        INSERT INTO dbo.FactSales (OrderDate, ProductKey, CustomerKey, SalesAmount)
        SELECT s.OrderDate, p.ProductKey, c.CustomerKey, s.Amount
        FROM LH_Silver.dbo.sales AS s
        JOIN dbo.DimProduct  AS p ON p.ProductID  = s.ProductID
        JOIN dbo.DimCustomer AS c ON c.CustomerID = s.CustomerID AND c.IsCurrent = 1
        WHERE s.OrderDate = @LoadDate;
        UPDATE etl.Watermark SET LastLoaded = @LoadDate WHERE TableName = 'FactSales';
        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;
        THROW;
    END CATCH
END;
  • Run procedures nightly from a pipeline Stored procedure activity chained on success after a Copy activity, mapping a pipeline expression (e.g. @formatDateTime(pipeline().TriggerTime,'yyyy-MM-dd')) to @LoadDate.
  • Views are also created by the visual query editor (no-code: drag tables, join, filter, Save as view) – ideal for analysts who don't write T-SQL.
  • Views over warehouse tables used in Direct Lake on SQL endpoint models cause DirectQuery fallback – materialise with CTAS instead for Direct Lake. See Direct Lake.

Statistics

  • The optimizer uses statistics to estimate row counts. Fabric creates histogram statistics automatically at query time for columns used in JOIN, WHERE, GROUP BY, ORDER BY, DISTINCT (names start _WA_Sys_), plus average-column-length and table-cardinality stats.
  • Stale stats are refreshed automatically (synchronously during the query, or by proactive/incremental statistics refresh in the background).
  • Manual: CREATE STATISTICS / UPDATE STATISTICS / DROP STATISTICS – single-column histogram only (no multi-column). Inspect with DBCC SHOW_STATISTICS, sys.stats, STATS_DATE.
  • After a large load, if a plan shows estimates far from actuals, UPDATE STATISTICS on join/filter columns first – the cheapest targeted fix.
CREATE STATISTICS st_FactSales_CustomerKey ON dbo.FactSales (CustomerKey) WITH FULLSCAN;
UPDATE STATISTICS dbo.FactSales (st_FactSales_CustomerKey) WITH FULLSCAN;
DBCC SHOW_STATISTICS ('dbo.FactSales', 'st_FactSales_CustomerKey');

Transactions and concurrency

  • ACID transactions with BEGIN TRAN / COMMIT / ROLLBACK; can span tables, schemas and warehouses in the same workspace (reading SQL analytics endpoints too). DDL such as CREATE/DROP/TRUNCATE TABLE, CTAS and supported ALTER TABLE can run inside a transaction.
  • Snapshot isolation always – other isolation levels are ignored. Readers don't block writers and vice versa.
  • Locking is table-level: two transactions that UPDATE/DELETE/MERGE the same table can conflict even on different rows → the later committer fails with an update-conflict error (24556/24706) and must retry. INSERTs create new files and rarely conflict. Avoid concurrent UPDATE/DELETE/MERGE on one table; add retry logic.
  • DDL takes schema-modification locks that block concurrent reads – run DDL in maintenance windows. Inspect with sys.dm_tran_locks.
  • Not supported: distributed transactions, savepoints, named and marked transactions.

Caching

  • In-memory and SSD (disk) cache: fully automatic and transparent; data read from OneLake is transcoded into a columnar in-memory format and also kept on SSD. Can't be cleared or disabled manually; consistent with DML.
  • Result set caching: persists final results of eligible SELECTs; enabled by default for warehouses and SQL analytics endpoints; disable per item with ALTER DATABASE <item> SET RESULT_SET_CACHING OFF or per query with OPTION (USE HINT ('DISABLE_RESULT_SET_CACHE')). Not used for cross-database queries, time travel, RLS/DDM, non-deterministic functions, results over ~10,000 rows, or if a referenced table changed; unused caches expire after 24 h.

Workload management

  • The engine isolates workloads into separate SELECT and non-SELECT (ingestion/DML) pools so heavy loads don't starve reports; resources scale automatically with the capacity SKU and burst within capacity limits. sql_pool_insights shows pool pressure.
  • Throttling and smoothing follow Fabric capacity rules – a busy capacity slows or delays warehouse queries (see Fabric platform).
  • Performance hygiene: right-sized data types (no oversize varchar), integer keys, avoid many small trickle INSERTs (batch them), keep stats fresh, filter early, avoid SELECT *.

Scenario: A finance team migrates its SQL Server warehouse to Fabric. Requirements: (1) nightly load of Parquet extracts from ADLS Gen2 behind a firewall; (2) surrogate keys for dimensions; (3) audit trail previously implemented with triggers; (4) testers need a copy of production fact tables each sprint; (5) a bad release must be reversible within hours. Design the solution.

(1) COPY INTO with CREDENTIAL = (IDENTITY = 'Workspace Identity'), the workspace identity granted Storage Blob Data Reader and the workspace added as a resource instance rule (trusted workspace access) – or a pipeline Copy activity. (2) BIGINT IDENTITY columns (values unique but not sequential) or keys computed in the load. (3) Triggers aren't supported – write audit rows inside the load stored procedures (in the same transaction) or from the pipeline. (4) Zero-copy clones (CREATE TABLE … AS CLONE OF, optionally AT a timestamp) – within the same warehouse; across workspaces they'd need deployment + reload instead. (5) Create a user-defined restore point before each release (system ones exist every 8 h); a workspace Admin can restore in-place. For single tables, use time travel or a point-in-time clone. Keep retention (default 30 days, up to 120) long enough. Orchestrate with a pipeline: Copy/COPY INTO → Stored procedure activity (MERGE/SCD) → semantic model refresh, with on-success dependencies.

Key takeaways & exam tips

  • Warehouse = read-write T-SQL with multi-table ACID transactions over Delta Parquet in OneLake; SQL analytics endpoint = read-only data (views/functions/procs/security allowed).
  • Cross-database queries: three-part names within the same workspace; no copying.
  • Supported: IDENTITY BIGINT, MERGE (GA), #temp tables, TRUNCATE, CTAS, sp_rename, PK/FK/UNIQUE only NOT ENFORCED. Unsupported: triggers, materialized views, synonyms, recursive CTEs, multi-column stats, CREATE USER, indexes.
  • Types: datetime → datetime2(≤6), nvarchar → varchar (UTF-8), money → decimal, tinyint → smallint.
  • COPY INTO = CSV/Parquet/JSONL from ADLS Gen2, Blob, OneLake; Entra ID/SAS/key/workspace identity; target table must exist.
  • CTAS = most efficient way to create + fill a table from a query; also the fix for views that make Direct Lake fall back.
  • Clone = metadata-only, independent, same warehouse, Contributor+; point-in-time with AT.
  • Time travel = OPTION (FOR TIMESTAMP AS OF 'UTC'), whole statement, read-only; retention 1–120 days (default 30).
  • Restore points: system every 8 h + user-defined; restore in-place replaces the whole warehouse; Admin only.
  • Stale estimates → UPDATE STATISTICS; slowest queries → queryinsights.exec_requests_history.
  • Snapshot isolation; table-level write-write conflicts → avoid concurrent UPDATE/MERGE on one table, retry.
  • Result set caching on by default; in-memory/SSD cache automatic.
  • Choose SQL database in Fabric for OLTP app data that must also be analysed in OneLake without ETL.
