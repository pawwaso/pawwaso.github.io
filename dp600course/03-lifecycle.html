Lifecycle: Git, PBIP, deployment pipelines, XMLA

How analytics content moves from a developer's laptop to production in Microsoft Fabric: version control with Git integration, Power BI Desktop projects (PBIP, TMDL, PBIR), deployment pipelines and their rules, the XMLA endpoint, warehouse database projects, reusable assets, automation (REST APIs, fabric-cicd, variable libraries) and impact analysis. Maps to the exam domain Maintain a data analytics solution → Maintain the analytics development lifecycle (25–30% of the exam together with security and governance).

The big picture in one sentence: Git integration gives you versioning, branching and code review; deployment pipelines give you controlled promotion between workspaces (Dev → Test → Prod) with per-stage configuration; the XMLA endpoint lets enterprise tools read and change published semantic models. They are complementary, not alternatives.

Git integration in Fabric

Git integration works at the workspace level: a workspace is connected to one Git branch and (optionally) one folder in a repository. Supported item definitions are serialized as folders of text files; the workspace folder structure (up to 10 levels) is mirrored in the repo.

Supported providers and prerequisites

  • Azure DevOps (Azure Repos) – cloud only.
  • GitHub and GitHub Enterprise – cloud only (no GitHub Enterprise Server on a private network or custom domain).
  • Not supported: on-premises Git servers, Bitbucket, GitLab, Subversion, TFVC, submodules, sovereign clouds, My workspace, and workspaces with template apps installed.
  • A Fabric administrator must enable the tenant setting Users can synchronize workspace items with their Git repositories (and, for Azure DevOps repos in another geography, the cross-geo export setting). Exporting items that carry sensitivity labels needs a separate admin setting.
  • The Git connection uses each user's own credentials: in a shared connected workspace every developer signs in to their own Git account (GitHub: personal access token; Azure DevOps: Microsoft Entra SSO, configured automatically where possible).

What gets versioned

Only item definitions (metadata), never data. Examples of supported items: notebooks, Spark job definitions, environments, lakehouses (metadata such as shortcuts – not the tables or files), warehouses (as a SQL database project), SQL databases, pipelines, Copy jobs, Dataflow Gen2, mirrored databases, eventhouses, KQL databases and querysets, eventstreams, Activator, Real-Time dashboards, variable libraries, semantic models and reports (both preview), paginated reports (preview).

  • Semantic models: not supported for push datasets, live connections to Analysis Services, or model v1 (non-enhanced metadata).
  • Reports: not supported if connected to AAS/SSAS models.
  • Unsupported items in the workspace are simply ignored – not saved, not synced, not deleted. They show in the source control pane but can't be committed.

Connect, commit, update

  1. Connect (Workspace settings → Git integration): choose provider, organization/project/repo (or GitHub repo URL), branch and Git folder. Only a workspace Admin can connect or disconnect.
  2. Initial sync: if either side is empty, content is copied from the non-empty side. If both have content you must choose the direction – commit workspace to Git (overwrites Git) or update workspace from Git (overwrites the workspace; you're asked to confirm because a workspace can't be restored like a Git branch).
  3. Commit: the Source control pane lists Changes (workspace → Git). You can select which items to commit and add a commit message. Commit is disabled while there are incoming updates – update first.
  4. Update: the Updates section lists items changed in the branch. Update always applies the entire branch (latest commit); you can't pick individual items. Fabric does not sync automatically – someone must press Update (or call the API).
  5. Undo: discards uncommitted workspace changes back to the last synced commit.

Conflict resolution

  • In the Fabric UI: start Update all; for each conflicting item choose which version to keep – the incoming (Git) version or the current (workspace) version. Alternatively Undo your workspace changes and then update.
  • In Git (when you need a real merge): use Checkout new branch (admin) to create a branch from the last synced commit and connect the workspace to it, commit your workspace state there, merge the two branches with a pull request in Azure DevOps/GitHub, then switch back / update.

Conflict resolution is partly done in Git. For semantic models, TMDL makes merges practical because each table, role, perspective and culture is its own small text file; a single huge model.bim JSON is painful to merge.

Branching strategies: branch out

The recommended developer pattern is one workspace per branch (a workspace can be connected to only one branch at a time):

  • Branch out to another workspace (Source control → Branches; Contributor or higher, plus Git Create branch): creates a new Git branch from the last commit of the current workspace and a new (or existing) workspace connected to it – an isolated sandbox. You need permission to create workspaces / assign capacity.
  • Work and commit in the feature workspace (or in Power BI Desktop / VS Code against a cloned repo), open a pull request to main, review, merge; then Update the shared Dev workspace from Git.
  • Switch branch overwrites all workspace items with the selected branch (Admin, or Member/Contributor when the workspace setting Allow users with at least Contributor role to change Git branch is on).
  • Checkout new branch (Admin) changes the connection of the current workspace to a new branch without changing content.

Limits worth knowing

  • Max 1,000 items per workspace sync; max file size 25 MB; max path length 250 characters; branch name 244 characters; folder depth 10.
  • Commit size: Azure DevOps 125 MB (user SSO) / 25 MB (service principal); GitHub 50 MB per commit.
  • Duplicate item names (same type) make commit/update fail.
  • Downloading a report or semantic model as .pbix from the service after it was created via Git is not recommended (unreliable) – open the PBIP in Desktop instead.
  • Items re-created by Git get a new item ID (definition only, no data); restoring from the workspace recycle bin keeps the original ID and data.

Analysts in a workspace connected to an Azure DevOps branch have the Viewer, Contributor and Admin roles. A Contributor wants to connect the workspace to a different repository. What happens?

  • It works, because Contributors can manage all Git settings
  • It works only if the Contributor is also a project administrator in Azure DevOps
  • It fails; connecting or disconnecting a workspace requires the workspace Admin role
  • It fails, because a workspace can never be reconnected once it has been synced

Only workspace Admins manage the Git connection (connect, disconnect, connection settings). Contributors and Members can commit, update and branch out once connected; Viewers see nothing Git-related. Reconnecting is allowed – by an Admin.

A colleague merged a pull request into the branch your Dev workspace is connected to. Your workspace shows two items with Update required and one with Uncommitted changes (a different item). You want only one of the two incoming items. What is true?

  • You can select a single incoming item and update just that one
  • Update always applies the whole branch; you can't cherry-pick incoming items, and commits are blocked until you update
  • The workspace updates automatically every 15 minutes, so you only need to wait
  • You must disconnect and reconnect the workspace to receive the changes

Commit is selective, Update is not: it syncs the workspace to the latest commit of the branch. While incoming updates exist, commit is disabled. There is no automatic sync.

Power BI Desktop projects (PBIP)

File → Save as → Power BI project (*.pbip) saves the report and semantic model as folders of human-readable text files instead of one binary .pbix. That makes Git diffs, code review, merges, programmatic edits and CI/CD possible. You can convert back with Save as .pbix (only in Desktop – there's no programmatic converter).

Deployment pipelines

A deployment pipeline promotes content between workspaces that represent release stages. Each stage is backed by one workspace, and a workspace can belong to only one pipeline. Workspaces must be on a Fabric capacity (Power BI-only content can also use PPU).

Structure

  • 2 to 10 stages; the default is 3 (Development, Test, Production). The number and names of stages are fixed after creation; a stage can be marked public or private at any time.
  • Assign a workspace to each stage (requires pipeline admin + workspace Admin of that workspace), or deploy into an empty stage and let Fabric create the workspace (the deploying user becomes its only admin and owner of cloned semantic models).
  • Item pairing: items are paired when a workspace is assigned or on a clean deploy. Paired items stay paired even if renamed and are overwritten on deploy. Items that look identical but are not paired are not overwritten – a duplicate is created (or a first deployment fails if an item with the same name and type already exists).

Compare and deploy

  • Compare shows per item: same, different (with a Review changes schema diff), only in source, or only in target. Comparison already reflects newly created rules.
  • Deploy all or selective deployment (pick items; Select related adds the dependencies so deployment doesn't fail). Max 300 items per deployment.
  • Deploy to an adjacent stage in either direction – forward (Dev → Test) or backward (e.g., Prod → Test to seed a pipeline from an existing production workspace). You can't skip a stage.
  • Deployment history shows who deployed what and when (pipeline admin).
  • Deployments can be automated with the Power BI / Fabric deployment pipelines REST APIs; an optional deployment plan (preview) can enforce order and pre/post actions.

What is and isn't copied

Copied (overwrites target)Not copied (stays as configured in the target stage)
  • Item metadata / definitions (model metadata, report pages and visuals, dashboard tiles, pipeline JSON, notebook code…)
  • Data sources and parameters (overridable by rules)
  • Relationships between items
  • Sensitivity labels – only for new items, deployment to an empty stage, or when the source label is protected and the target has none
  • Incremental refresh policy
  • Data (lakehouse tables, warehouse rows, imported model data) – refresh after deployment
  • Item ID and URL, workspace settings
  • Permissions (workspace and item)
  • App content and settings – update the app manually per stage
  • Semantic model: RLS role membership, refresh schedule, data source credentials, endorsement, query caching
  • Gateway mapping (configure once after first deployment)

Where possible the target keeps its data: small changes (add a measure, add a table) keep data; breaking schema or connection changes require a full refresh. Incremental refresh data and partitions are retained. You can't download a .pbix from a stage after deployment.

Deployment rules

Rules make an item behave differently per stage, e.g., Prod points at the production database. A rule is defined on the target stage, for a specific item, and takes effect on the next deployment into that stage.

ItemData source ruleParameter ruleDefault lakehouse rule
Semantic modelYesYes–
Dataflow Gen1YesYes–
Paginated reportYesNo–
Mirrored databaseYesNo–
Notebook––Yes
Pipelines, Copy job, Dataflow Gen2, shortcuts…No rules – use a variable library (active value set per stage)
  • You must be the owner of the item (and contributor+ on the target workspace) to create a rule. Rules can't be created in the first (development) stage.
  • Data source rules only switch to a source of the same type (e.g., SQL Server → SQL Server) and are supported for a fixed list of connectors (Azure SQL, SQL Server, Azure Synapse, AAS, SSAS, OData, Oracle, SAP HANA import, SharePoint, Teradata). For anything else – or for parameterized sources – use parameter rules (parameters used for rebinding must be of type Text).
  • If the source data source/parameter referenced by a rule is removed, the rule becomes invalid and deployment fails. Deleting the item or unassigning the workspace deletes its rules.

Autobinding

  • When a deployed item depends on another item (report → semantic model, model → lakehouse), the pipeline automatically rebinds it to the paired item in the target stage. If the dependency isn't in the target stage, deployment fails – use Select related.
  • Across pipelines, autobinding works when both items are in the same stage position and the pipelines have the same number of stages.
  • To avoid autobinding (e.g., reports in every stage should use the production model): connect to an item not in the corresponding stage, use a parameter rule, or use a proxy model outside the pipeline.
  • Direct Lake semantic models do not autobind – after deployment they still point to the source-stage lakehouse/warehouse. Use a data source rule for Direct Lake on SQL endpoint, or M parameters + parameter rules for Direct Lake on OneLake.
  • Autobinding isn't supported for Dataflow Gen2.

After deploying a Direct Lake on SQL endpoint semantic model and its lakehouse from Test to Production, the Production report still shows Test data. Why?

  • The Production lakehouse needs a refresh schedule identical to Test
  • Direct Lake models can't be deployed with deployment pipelines

Variable libraries, REST APIs and fabric-cicd

Variable library

A variable library is a workspace item that holds variables (string, integer, number, boolean, date-time, GUID, item reference…) plus value sets (one per environment). Exactly one value set is active per workspace, so each pipeline stage resolves its own values at run time. It's supported by Git and deployment pipelines (the library is deployed; each stage keeps its own active value set).

Consumers: pipelines, lakehouse shortcuts, notebooks (NotebookUtils / %%configure), Dataflow Gen2, Copy job, user data functions, eventstreams. This is the modern answer for "different connection/lakehouse per stage" for items that don't support deployment rules. Limits: up to 1,000 variables and 1,000 value sets (fewer than 10,000 cells, item ≤ 1 MB).

Scenario: Five developers edit the same semantic model. Today they publish PBIX files directly to the shared Dev workspace and regularly overwrite each other's measures. Production must only receive reviewed changes, and the Production model must read from the production warehouse. Design the process.

  • Save the model as PBIP with TMDL and put it in Git (Azure DevOps or GitHub); connect the Dev workspace (Admin) to main.
  • Each developer works in a feature branch – either locally in Desktop or via Branch out to another workspace (one workspace per branch).
  • Changes reach main only via pull requests with reviewers (branch policy blocks direct commits); TMDL gives per-table diffs so conflicts are rare and mergeable.
  • After merge, Update the Dev workspace from Git (Update applies the whole branch).
  • A deployment pipeline (Dev → Test → Prod) promotes content; a data source rule (or parameter rule) on the model in the Prod stage points it at the production warehouse; refresh after deployment; set credentials/schedule/RLS members once in Prod (not copied).
  • Deployers need pipeline admin + Contributor on source and target; restrict Prod workspace roles so nobody edits Prod directly.

XMLA endpoint

Every workspace on a Fabric/Premium capacity (or PPU) exposes its semantic models through the XMLA endpoint – the Analysis Services protocol. The workspace looks like an Analysis Services server and each semantic model like a database.

  • Connection URL: powerbi://api.powerbi.com/v1.0/myorg/Sales%20Workspace (tenant name or myorg; workspace name URI-encoded). Copy it from Workspace settings → License info / Premium → Workspace connection. Some tools (Profiler) also need the model name as Initial Catalog.
  • Default: read-only – query data, metadata, events, schema (Excel, DAX Studio, Report Builder, Power BI Desktop live connect).
  • Read-write is enabled per capacity by a capacity/Fabric admin: Admin portal → Capacity settings → (capacity) → Power BI workloads → XMLA Endpoint = Read Write. It applies to all workspaces on that capacity (for PPU: Admin portal → Premium Per User).
  • Tenant setting Allow XMLA endpoints and Analyze in Excel with on-premises semantic models (Integration settings, on by default) must also be enabled.
  • Permissions: workspace Contributor, Member, Admin = write permission = Analysis Services database admin (deploy, script TMSL, process). Build = database reader (query; RLS enforced; Build is required for any XMLA read access). Server-admin operations aren't supported.
  • With the tenant switch Block republish and disable package refresh, only model owners can write via XMLA.

  • XMLA operations are recorded in the audit log (ConnectFromExternalApplication, EditDatasetFromExternalApplication…).

(Downloading .pbix is also not supported after a deployment-pipeline deployment and unreliable after Git sync.)

Database projects for the warehouse

  • A Fabric warehouse is source-controlled as a SQL database project (.sqlproj, one .sql file per table, view, function, procedure, schema). Git integration and deployment pipelines handle the warehouse through this project – schema only, never data.
  • Building the project produces a DACPAC (data-tier application package). Deploying a DACPAC (SqlPackage, VS Code SQL Database Projects extension, SSMS, or a CI/CD task) diffs the model against the target and generates the ALTER/CREATE script.
  • You can download a warehouse as a database project from the Fabric UI, develop in VS Code, and publish to a warehouse connection string. Fabric SQL database works the same way.
  • Watch out: some schema changes (e.g., altering columns) can make a deployment drop and recreate a table – data in the target table is lost. Review the generated script; reload data after deployment.
  • For fast test environments, a zero-copy table clone (CREATE TABLE … AS CLONE OF …) copies metadata only and references the same files.

Impact analysis before changing content

  • Open an item (lakehouse, warehouse, semantic model, dataflow…) → Lineage / Impact analysis. The pane lists downstream (child) items – also in other workspaces – grouped by type and workspace, plus usage information (views/viewers) to judge how critical they are.
  • Notify contacts sends a message to the contacts of all impacted workspaces before you rename a column, remove a table or change a source.

Key takeaways & exam tips

  • Git providers: Azure DevOps and GitHub (incl. GitHub Enterprise cloud) only. Workspace-level connection, one branch per workspace, only workspace Admins connect/disconnect; Viewers can't do anything Git-related.
  • Commit is selective, Update is all-or-nothing; no automatic sync; commit is blocked until incoming updates are applied; conflicts are resolved by choosing workspace vs Git version, or via a new branch + PR in Git.
  • Branch out = new branch + new workspace for isolated development; merge back with a pull request.
  • Git stores definitions, not data (lakehouse tables, warehouse rows and model data stay in OneLake/engine).
  • PBIP = folders of text; TMDL = readable, mergeable model files; PBIR = per-page/per-visual report files; cache.abf and localSettings.json are git-ignored.
  • Deployment pipelines: 2–10 stages (default 3), one workspace per stage, adjacent deploys in either direction, selective deploy with Select related, max 300 items, compare/review changes, history.
  • Deploy needs pipeline admin + Contributor on source and target; assigning a workspace needs workspace Admin; rules need item ownership and live on the target stage, not the first stage; they apply on the next deployment.
  • Rules: data source + parameter (semantic models, Dataflow Gen1), data source (paginated reports, mirrored DB), default lakehouse (notebooks). Everything else → variable library.
  • Not copied: data, credentials, refresh schedule, RLS membership, permissions, app, endorsement. Refresh after deploy. Direct Lake models don't autobind → rules/parameters.
  • XMLA: read-only by default; read-write is a capacity setting; URL powerbi://api.powerbi.com/v1.0/myorg/<workspace>; Contributor+ = write, Build = read; after an XMLA write the model can't be downloaded as PBIX; enable large model format for XMLA writes.
  • Warehouse lifecycle = SQL database project → DACPAC; schema only.
  • .pbit = template without data (with parameters); .pbids = connection only; shared semantic model + Build + endorsement = reuse.
  • Before breaking changes run impact analysis and notify contacts.
  • Automation: Fabric REST APIs (Git, deployment pipelines, item definitions), fabric-cicd Python library, semantic link for automated data tests.
