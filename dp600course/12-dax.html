Filter contextRow context

Created byReport visuals, CALCULATE/CALCULATETABLE filter argumentsCalculated columns, iterators (SUMX, FILTER, ADDCOLUMNS…)

A measure is always evaluated in a filter context. A calculated column is evaluated row by row (row context) at refresh time and stored – it consumes memory and isn't affected by slicers.

-- Calculated column on Sales: row context, RELATED follows many-to-one
Sales[Category] = RELATED ( Product[Category] )

-- Calculated column on Customer: RELATEDTABLE follows one-to-many
Customer[Order Lines] = COUNTROWS ( RELATEDTABLE ( Sales ) )

"Value must be usable on an axis/slicer and is fixed per row" → column (ideally materialized upstream). "Value must react to slicers/filters" → measure. Implicit measures (dragging a numeric column) can be disabled with Discourage implicit measures, forcing authors to use governed explicit measures – required anyway when a model contains calculation groups.

CALCULATE and filter modifiers

CALCULATE(<expression>, <filter1>, …) evaluates the expression in a modified filter context. That's what distinguishes it from a plain aggregation. Evaluation order:

  1. Filter arguments are evaluated in the original filter context.
  2. If CALCULATE is called inside a row context, context transition turns the current row into an equivalent filter.
  3. Modifiers (ALL/REMOVEFILTERS, USERELATIONSHIP, CROSSFILTER, KEEPFILTERS) are applied.
  4. Filter arguments are applied: a filter on a column replaces existing filters on the same column (unless wrapped in KEEPFILTERS); filters on different columns are combined (AND).
-- Boolean filter: shorthand for FILTER ( ALL ( Product[Color] ), Product[Color] = "Red" )
Red Sales = CALCULATE ( [Sales Amount], Product[Color] = "Red" )

-- Multiple filters = AND
Red Bikes = CALCULATE ( [Sales Amount], Product[Color] = "Red", Product[Category] = "Bikes" )

-- OR on the same column
Red or Blue = CALCULATE ( [Sales Amount], Product[Color] IN { "Red", "Blue" } )

-- OR across different columns needs a table filter
Red or Bikes =
CALCULATE (
    [Sales Amount],
    FILTER (
        ALL ( Product[Color], Product[Category] ),
        Product[Color] = "Red" || Product[Category] = "Bikes"
    )
)

-- Ignore any slicer on the Region table, keep everything else
Sales All Regions = CALCULATE ( [Sales Amount], REMOVEFILTERS ( Region ) )

-- Share of the category inside the subcategory/product matrix
% of Category =
DIVIDE (
    [Sales Amount],
    CALCULATE ( [Sales Amount], ALLEXCEPT ( Product, Product[Category] ) )
)

-- Inactive relationship Sales[ShipDateKey] -> 'Date'[DateKey]
Sales by Ship Date =
CALCULATE ( [Sales Amount], USERELATIONSHIP ( Sales[ShipDateKey], 'Date'[DateKey] ) )

-- Count customers who bought the products selected in a Product slicer
-- (Customer and Product both filter Sales; Customer isn't filtered by Product without this)
Customers Buying Selection =
CALCULATE (
    DISTINCTCOUNT ( Customer[CustomerKey] ),
    CROSSFILTER ( Sales[CustomerKey], Customer[CustomerKey], BOTH )
)

-- KEEPFILTERS: with a Color slicer = "Blue", this returns blank instead of red sales
Red Sales (respect slicer) = CALCULATE ( [Sales Amount], KEEPFILTERS ( Product[Color] = "Red" ) )

Prefer USERELATIONSHIP for role-playing dates when one Date table is enough; create a second Date table only when users need two independent date slicers at the same time. Prefer CROSSFILTER inside one measure over setting a relationship to bidirectional for the whole model (ambiguity, performance, RLS surprises).

A measure must always ignore any slicer on the Region table but respect all other filters. Which expression is correct?

  • CALCULATE([Sales Amount], ALL(Sales))
  • CALCULATE([Sales Amount], REMOVEFILTERS(Region))
  • CALCULATE([Sales Amount], ALLSELECTED(Region))
  • CALCULATE([Sales Amount], KEEPFILTERS(Region))

REMOVEFILTERS(Region) clears only that table's filters. ALL(Sales) removes all filters on the expanded fact table (including dimension filters) – far too broad. ALLSELECTED keeps the slicer. KEEPFILTERS doesn't remove anything.

Context transition

When CALCULATE (or CALCULATETABLE) is executed inside a row context, the row context is transformed into an equivalent filter context – a filter on every column of the iterated row. Every measure reference is implicitly wrapped in CALCULATE, so referencing a measure inside an iterator always triggers context transition.

-- Average sales per customer: SUMX/AVERAGEX iterate customers,
-- [Sales Amount] is evaluated per customer thanks to context transition
Avg Sales per Customer = AVERAGEX ( Customer, [Sales Amount] )

-- Same thing WITHOUT a measure reference: no context transition -> wrong
Wrong Avg = AVERAGEX ( Customer, SUM ( Sales[SalesAmount] ) )   -- grand total repeated per row

-- Explicit CALCULATE fixes it
Right Avg = AVERAGEX ( Customer, CALCULATE ( SUM ( Sales[SalesAmount] ) ) )

Context transition is expensive on large tables (one filter per row, many storage-engine requests) and can produce surprises when the iterated table has duplicate rows (the filter selects all identical rows, so values get multiplied). Iterate over a dimension or VALUES(column), not over the fact table, when you need context transition.

Which statement about context transition is TRUE?

  • CALCULATE invoked in a row context converts the current row into an equivalent filter context, and every measure reference does this implicitly
  • Context transition happens in every iterator even without CALCULATE or measure references
  • Context transition converts a filter context into a row context
  • Context transition only happens in calculated tables

Context transition = row context → filter context, triggered by CALCULATE (explicit or the implicit CALCULATE around a measure reference). That's why SUMX(Customer, [Sales Amount]) works per customer.

Variables

YoY % =
VAR CurrentSales = [Sales Amount]
VAR PreviousSales = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
VAR Result = DIVIDE ( CurrentSales - PreviousSales, PreviousSales )
RETURN
    IF ( NOT ISBLANK ( CurrentSales ) && NOT ISBLANK ( PreviousSales ), Result )
  • A variable is evaluated once, in the context where it is defined – later CALCULATE filters don't change it. (CALCULATE(CurrentSales, …) returns the same value – a classic trap.)
  • Variables improve readability, avoid repeated evaluation (performance) and make debugging easy (temporarily RETURN an intermediate variable).
  • Variables can hold scalars or tables: VAR TopProducts = TOPN(10, …).

Time intelligence

Date table requirements (classic time intelligence)

  • A dedicated date table with one row per day, a column of Date data type with unique values and no gaps (contiguous dates; full years recommended) – missing dates cause an error.
  • Mark as date table (Table tools → Mark as date table) on that column. Required when the relationship uses a non-date key (e.g. integer DateKey) so time intelligence removes filters on the date table correctly.
  • Disable Auto date/time for enterprise models (it creates a hidden date table per date column, inflating the model).
Sales YTD        = TOTALYTD ( [Sales Amount], 'Date'[Date] )
Sales YTD (FY June) = TOTALYTD ( [Sales Amount], 'Date'[Date], "6-30" )   -- fiscal year ending 30 June
Sales YTD (alt)  = CALCULATE ( [Sales Amount], DATESYTD ( 'Date'[Date] ) )
Sales MTD        = TOTALMTD ( [Sales Amount], 'Date'[Date] )

Sales PY         = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
Sales PY (DATEADD) = CALCULATE ( [Sales Amount], DATEADD ( 'Date'[Date], -1, YEAR ) )
Sales Prev Month = CALCULATE ( [Sales Amount], DATEADD ( 'Date'[Date], -1, MONTH ) )

-- Whole previous year regardless of the month in context
Sales Full PY    = CALCULATE ( [Sales Amount], PARALLELPERIOD ( 'Date'[Date], -1, YEAR ) )

-- Rolling 3 months ending at the last visible date
Sales R3M =
CALCULATE (
    [Sales Amount],
    DATESINPERIOD ( 'Date'[Date], MAX ( 'Date'[Date] ), -3, MONTH )
)

YoY % =
VAR Cur = [Sales Amount]
VAR Prev = [Sales PY]
RETURN DIVIDE ( Cur - Prev, Prev )

Calendar-based time intelligence (preview)

Newer approach recommended by Microsoft: define one or more calendars on a table (Calendar options in Desktop, or TMDL) by mapping columns to categories (Year, Quarter, Month, Week, Date, Month of Year, Week of Year…), then pass the calendar name instead of a date column:

Sales YTD (fiscal) = TOTALYTD ( [Sales], 'Fiscal Calendar' )
Sales WTD          = TOTALWTD ( [Sales], 'ISO-454' )             -- week-based functions are new
Sales PY (cal)     = CALCULATE ( [Sales], SAMEPERIODLASTYEAR ( 'Fiscal Calendar' ) )

Benefits: any calendar (retail 4-4-5, 13-period, lunar), sparse dates allowed, week-based calculations, often better performance. Limitations (preview): can't author calendars in the service yet, not for live-connected/composite models, no nesting of calendar-based TI functions. Classic TI remains fully valid and is what most exam questions use.

Which expression returns total sales for the same period last year, assuming 'Date' is marked as the date table?

  • CALCULATE([Sales Amount], PREVIOUSYEAR('Date'[Year]))
  • [Sales Amount] - 365
  • CALCULATE([Sales Amount], SAMEPERIODLASTYEAR('Date'[Date]))
  • CALCULATE([Sales Amount], PARALLELPERIOD('Date'[Date], -1, YEAR))

SAMEPERIODLASTYEAR shifts the dates in context back one year. PARALLELPERIOD returns the entire previous year, not the same period. PREVIOUSYEAR needs a date column (and also returns the whole year).

Window functions: OFFSET, INDEX, WINDOW, RANK, ROWNUMBER

Introduced in late 2022, window functions work on a relation (a table, often ALLSELECTED of the axis columns), sorted by ORDERBY, optionally split by PARTITIONBY. The "current row" is found by matching the current filter/row context against the relation (optionally using MATCHBY columns that uniquely identify a row). They return a table (except RANK/ROWNUMBER which return a number) and are typically used as CALCULATE filters.

FunctionSignature (simplified)Returns
OFFSETOFFSET(delta, [relation], [orderBy], [blanks], [partitionBy], [matchBy], [reset])The row delta positions away (−1 = previous, like SQL LAG)
INDEXINDEX(position, [relation], [orderBy], …)The row at an absolute position (1 = first, −1 = last)
WINDOWWINDOW(from, [ABS|REL], to, [ABS|REL], [relation], [orderBy], …)A range of rows – running totals, moving averages
RANKRANK([DENSE|SKIP], [relation], [orderBy], …)Rank number; ties share a rank; can order by several columns
ROWNUMBERROWNUMBER([relation], [orderBy], …)Unique sequential number (ties must be broken by ordering)

Helper functions: ORDERBY(col, [ASC|DESC], …) – default ASC; PARTITIONBY(col, …); MATCHBY(col, …). Note the default difference: RANKX ranks descending by default; RANK's ORDERBY defaults to ascending – specify DESC for "highest = 1".

-- Previous month's sales (works on any visual with Year-Month on rows)
Sales Prev Month (OFFSET) =
CALCULATE (
    [Sales Amount],
    OFFSET ( -1, ALLSELECTED ( 'Date'[YearMonth] ), ORDERBY ( 'Date'[YearMonth], ASC ) )
)

-- Running total from the first visible month to the current one
Sales Running Total =
CALCULATE (
    [Sales Amount],
    WINDOW ( 1, ABS, 0, REL, ALLSELECTED ( 'Date'[YearMonth] ), ORDERBY ( 'Date'[YearMonth] ) )
)

-- Running total that restarts every year
Sales YTD (WINDOW) =
CALCULATE (
    [Sales Amount],
    WINDOW (
        1, ABS, 0, REL,
        ALLSELECTED ( 'Date'[Year], 'Date'[YearMonth] ),
        ORDERBY ( 'Date'[YearMonth] ),
        PARTITIONBY ( 'Date'[Year] )        -- restart the window for each year
    )
)

-- 3-month moving average (current + 2 previous)
Sales MA3 =
AVERAGEX (
    WINDOW ( -2, REL, 0, REL, ALLSELECTED ( 'Date'[YearMonth] ), ORDERBY ( 'Date'[YearMonth] ) ),
    [Sales Amount]
)

-- Rank brands by sales, ties broken by brand name, highest first
Brand Rank =
RANK (
    DENSE,
    ALLSELECTED ( Product[Brand] ),
    ORDERBY ( [Sales Amount], DESC, Product[Brand], ASC )
)

Order by a column that sorts correctly (YearMonth as 202601…, or MonthNumber), not a month name text. If the visual sorts Month by MonthNumber, include both columns in the relation (or they leak into the filter context and the window function returns the wrong rows). Window functions return blank at subtotal rows where no "current row" can be identified – often exactly what you want for rankings.

Running total the classic way

-- Running total starting at the first date selected in a slicer
Sales RT (classic) =
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE (
        [Sales Amount],
        FILTER ( ALLSELECTED ( 'Date'[Date] ), 'Date'[Date] <= LastVisibleDate )
    )

ALLSELECTED keeps the slicer's date range; FILTER keeps the dates up to the current one. Using ALL instead would start the total at the first date in the table.

  1. Start with CALCULATE and the base measure [Sales Amount]
  2. Add OFFSET with delta -1 as the filter argument
  3. Define the relation: ALLSELECTED('Date'[YearMonth])
  4. Add ORDERBY('Date'[YearMonth], ASC)
  5. Optionally add PARTITIONBY to restart per year
  6. Test in DAX query view with EVALUATE SUMMARIZECOLUMNS

Calculation groups

A calculation group is a special table with one column whose rows are calculation items. Each item is a DAX expression that rewrites whichever measure is in scope through SELECTEDMEASURE(). Four items (Current, YTD, PY, YoY %) cover 20 base measures – and every future one – instead of 80 separate measures.

-- Calculation group 'Time Calc', column [Time Calculation]
Current = SELECTEDMEASURE ()
YTD     = CALCULATE ( SELECTEDMEASURE (), DATESYTD ( 'Date'[Date] ) )
PY      = CALCULATE ( SELECTEDMEASURE (), SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
YoY %   =
    VAR Cur  = SELECTEDMEASURE ()
    VAR Prev = CALCULATE ( SELECTEDMEASURE (), SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
    RETURN DIVIDE ( Cur - Prev, Prev )

-- Format string expression on the YoY % item (keeps other items in the measure's own format)
"0.0%"

-- Apply only to some measures
YTD (selective) =
IF (
    ISSELECTEDMEASURE ( [Sales Amount], [Margin] ),
    CALCULATE ( SELECTEDMEASURE (), DATESYTD ( 'Date'[Date] ) ),
    SELECTEDMEASURE ()
)
  • Functions: SELECTEDMEASURE(), SELECTEDMEASURENAME(), ISSELECTEDMEASURE(m1, …), SELECTEDMEASUREFORMATSTRING().
  • Format string expression per item (e.g. "0.0%" for YoY %); otherwise the measure's own format is kept.
  • Ordinal controls item sort order; Precedence (property of the group) controls the order in which multiple calculation groups are applied – the group with the higher precedence is applied first (its item wraps the others).
  • Calculation groups apply only to explicit measures. Creating a calculation group turns on Discourage implicit measures for the model (implicit measures aren't supported).
  • Create them in Power BI Desktop (Model view → Calculation group), TMDL view, web modeling, or Tabular Editor via the XMLA endpoint (no PBIX republish needed). Supported in Direct Lake models too.
  • Selecting a calculation item in a slicer or filter applies it to all measures in the visual; putting the column on columns of a matrix shows each item side by side.
  • Optional items: No selection and Multiple or empty selection expressions handle those cases.

Which statement about calculation items is TRUE?

  • Each calculation item must reference a specific measure by name
  • Calculation items also modify implicit measures created by dragging numeric columns
  • Calculation groups require Import storage mode
  • SELECTEDMEASURE() is a placeholder for the measure in context, so one item can be reused across many measures

SELECTEDMEASURE makes items generic. Implicit measures aren't supported (creating a calculation group turns on Discourage implicit measures). Calculation groups work in Import, DirectQuery and Direct Lake models.

Field parameters and dynamic format strings

Field parameters

Modeling → New parameter → Fields creates a calculated table (using NAMEOF()) listing columns and/or measures. Add the parameter to a slicer and to a visual's axis or values: users switch the chart's dimension (Product / Region / Channel) or measure from the slicer. It's metadata; no data duplication.

Axis Selector = {
    ( "Product", NAMEOF ( Product[Category] ), 0 ),
    ( "Region",  NAMEOF ( Region[Region] ),    1 ),
    ( "Channel", NAMEOF ( Sales[Channel] ),    2 )
}

Dynamic format strings for measures

Set the measure's Format to Dynamic and write a DAX expression that returns a format string. The value stays numeric (unlike FORMAT(), which returns text that can't be summed or charted).

-- Format string expression of [Sales (converted)]
SWITCH (
    SELECTEDVALUE ( Currency[Code], "USD" ),
    "EUR", "€#,0.00",
    "GBP", "£#,0.00",
    "JPY", "¥#,0",
    "$#,0.00"
)

-- Format string expression of a measure whose meaning depends on a metric selector
IF ( SELECTEDVALUE ( Metric[Name] ) = "Margin %", "0.0%", "#,0" )

Visual calculations (briefly)

A visual calculation is DAX defined on a visual and evaluated over the visual's own result matrix (rows/columns), not over the model. It's stored in the report, not the semantic model. Helpful functions: RUNNINGSUM, MOVINGAVERAGE, PREVIOUS, NEXT, FIRST, LAST, COLLAPSE, EXPAND, with axis parameters (ROWS, COLUMNS) and reset behavior.

Running total = RUNNINGSUM ( [Sales Amount] )
vs previous   = [Sales Amount] - PREVIOUS ( [Sales Amount] )
% of parent   = DIVIDE ( [Sales Amount], COLLAPSE ( [Sales Amount], ROWS ) )

Choose visual calculations for one-off, visual-specific logic by report authors; choose model measures for reusable, governed business logic.

  • Governed Total Sales excluding cancelled orders
  • Distinct customer count used in many reports
  • Margin % used in Excel pivot tables
  • YTD, PY and YoY variants for 20 measures
  • Currency-specific format for all measures in one switch
  • Let users switch a chart axis between Product, Region and Channel
  • Let users pick which measure a line chart shows
  • Difference to the previous row of one specific table visual
  • Running sum over the rows of one matrix only

A matrix shows Category → Brand. A rank measure returns 1 on every category subtotal and the grand total. Which function lets you blank the rank except at brand level?

  • HASONEVALUE(Product[Category])
  • ISFILTERED(Product[Brand])
  • ISINSCOPE(Product[Brand])
  • SELECTEDMEASURE()

ISINSCOPE tests whether the column is a grouping level of the current cell – false on subtotals/totals. ISFILTERED can be true because of a slicer; HASONEVALUE on Category is true at the Brand level too and at the category subtotal.

Error handling: DIVIDE, not IFERROR

Margin % = DIVIDE ( [Margin], [Sales Amount] )          -- returns BLANK when denominator is 0/blank
Margin % (alt 0) = DIVIDE ( [Margin], [Sales Amount], 0 ) -- optional alternate result

-- Avoid:
Margin % (bad) = IFERROR ( [Margin] / [Sales Amount], BLANK () )
  • / returns an error/Infinity on division by zero; DIVIDE handles it safely with an optional alternate result and is optimized by the engine.
  • IFERROR / ISERROR force row-by-row error checking and prevent storage-engine optimizations – avoid them; test the condition instead (e.g. IF(denominator <> 0, …) or DIVIDE).
  • Returning BLANK rather than 0 keeps visuals from showing every empty combination.

Which statement about DIVIDE compared with the / operator is TRUE?

  • DIVIDE returns BLANK (or an optional alternate result) when the denominator is zero or blank, while / can return an error or infinity
  • DIVIDE is always slower than / combined with IFERROR
  • / automatically returns BLANK for division by zero
  • DIVIDE only works in calculated columns

Safe division with an optional alternate result is the purpose of DIVIDE; it's also the recommended, optimizable pattern versus IFERROR.

Common patterns

% of total

% of All Categories =
DIVIDE ( [Sales Amount], CALCULATE ( [Sales Amount], REMOVEFILTERS ( Product[Category] ) ) )

% of Visible Total =
DIVIDE ( [Sales Amount], CALCULATE ( [Sales Amount], ALLSELECTED ( Product ) ) )

% of Grand Total (ignore everything on Product) =
DIVIDE ( [Sales Amount], CALCULATE ( [Sales Amount], ALL ( Product ) ) )

YoY %, moving average, ranking

Sales YoY % =
VAR Cur = [Sales Amount]
VAR PY  = CALCULATE ( [Sales Amount], DATEADD ( 'Date'[Date], -1, YEAR ) )
RETURN IF ( NOT ISBLANK ( Cur ), DIVIDE ( Cur - PY, PY ) )

Sales MA 30 days =
AVERAGEX (
    DATESINPERIOD ( 'Date'[Date], MAX ( 'Date'[Date] ), -30, DAY ),
    [Sales Amount]
)

Product Rank =
IF (
    ISINSCOPE ( Product[ProductName] ),
    RANKX ( ALLSELECTED ( Product[ProductName] ), [Sales Amount], , DESC, DENSE )
)

Measure branching

Build measures on top of other measures (Margin = [Sales Amount] - [Total Cost], Margin % = DIVIDE([Margin],[Sales Amount])). One definition per business rule, easier testing, and the engine can reuse results. Implement business rules (e.g. "exclude cancelled orders") once – in the curated data or the base measure – so every report agrees.

Scenario. A product manager wants a line chart by month showing Sales, the previous month's Sales and a running total that starts at the first month selected in a date-range slicer. The chart must also let her switch between Sales Amount, Margin and Quantity with a slicer. Which DAX features do you use?

Create a field parameter for the three measures (slicer switches the measure). For "previous month" and "running total" either: (a) a calculation group with items Current, Previous month (CALCULATE(SELECTEDMEASURE(), OFFSET(-1, ALLSELECTED('Date'[YearMonth]), ORDERBY('Date'[YearMonth])))) and Running total (WINDOW(1, ABS, 0, REL, ALLSELECTED('Date'[YearMonth]), ORDERBY('Date'[YearMonth]))) – they then work with whichever measure the field parameter selects; or (b) visual calculations PREVIOUS and RUNNINGSUM if the logic is needed only on this visual. ALLSELECTED makes the running total start at the slicer's first month.

Scenario. A measure Customers Buying = CALCULATE(DISTINCTCOUNT(Customer[CustomerKey]), Sales) is slow, and someone suggests making the Sales–Product and Sales–Customer relationships bidirectional to fix a "customers who bought the selected products" visual. What do you recommend?

Keep single-direction one-to-many relationships for the model and enable bidirectional propagation only inside the measure: CALCULATE(DISTINCTCOUNT(Customer[CustomerKey]), CROSSFILTER(Sales[CustomerKey], Customer[CustomerKey], BOTH)) – or simply DISTINCTCOUNT(Sales[CustomerKey]), which is filtered by Product through Sales already and is the most efficient. You need a running total of sales on a line chart that starts at the first date selected in a date-range slicer. Which expression is correct?

  • CALCULATE([Sales Amount], FILTER(ALL('Date'[Date]), 'Date'[Date] <= MAX('Date'[Date])))
  • CALCULATE([Sales Amount], FILTER(ALLSELECTED('Date'[Date]), 'Date'[Date] <= MAX('Date'[Date])))
  • CALCULATE([Sales Amount], DATESYTD('Date'[Date]))
  • SUMX(Sales, [Sales Amount])

ALLSELECTED retains the slicer's range and removes the chart's per-point filter; FILTER keeps dates up to the current point. ALL would start at the very first date in the table; DATESYTD restarts every year; SUMX over Sales with a measure is slow and doesn't accumulate.

Key takeaways & exam tips

  • Filter context propagates through relationships (one → many); row context doesn't – use RELATED/RELATEDTABLE, or CALCULATE for context transition.
  • CALCULATE modifies filter context; filters on a column replace existing ones unless KEEPFILTERS. Modifiers: ALL/REMOVEFILTERS, ALLEXCEPT, ALLSELECTED, USERELATIONSHIP (inactive relationships), CROSSFILTER (direction per measure).
  • Every measure reference triggers context transition; it's powerful but expensive on large tables.
  • Variables are evaluated once where defined – readability + performance; later filters don't change them.
  • Iterators: SUMX/AVERAGEX/MAXX/COUNTX/RANKX/FILTER. Prefer SUM over a materialized column and DISTINCTCOUNT for distinct counts.
  • VALUES includes the blank row; DISTINCT doesn't. Unmatched fact keys → "(Blank)" member and totals that don't add up.
  • Time intelligence needs a contiguous, marked date table; SAMEPERIODLASTYEAR/DATEADD shift, PARALLELPERIOD returns whole periods, DATESINPERIOD for rolling windows, TOTALYTD with a fiscal year-end string. Calendar-based TI (preview) adds custom calendars and week functions.
  • Window functions: OFFSET (previous/next), WINDOW (running/moving), INDEX (first/last), RANK (ties DENSE/SKIP, multi-column ORDERBY, ascending default), ROWNUMBER; relation + ORDERBY + PARTITIONBY + MATCHBY.
  • Calculation groups: SELECTEDMEASURE, format string expressions, precedence, explicit measures only (Discourage implicit measures is turned on).
  • Field parameters = switch fields/measures from a slicer; dynamic format strings keep values numeric; visual calculations live in the report.
  • Use DIVIDE, avoid IFERROR; use ISINSCOPE to handle subtotals; SELECTEDVALUE for single selections; USERPRINCIPALNAME for dynamic RLS.
