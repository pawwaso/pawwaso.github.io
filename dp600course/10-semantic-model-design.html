Semantic model design & storage modes

How to choose a storage mode (Import, DirectQuery, Dual, Direct Lake on OneLake, Direct Lake on SQL endpoint), build composite models, and design a clean star schema in the model: relationships, date table, hierarchies, measures vs calculated columns, field parameters, dynamic format strings, large model format, perspectives, translations and the model's service settings. Storage modes

Storage mode is a property of each table (more precisely, of its partitions). A model whose tables use different modes — or that combines local tables with a remote model — is a composite model.

Choice rules

  • Import — default for most models: fastest queries, full DAX/Power Query, any source. Downsides: data copy, refresh time and memory; latency = refresh schedule. Self-service authors without write access to the lake typically use Import (Power Query lives in the model).
  • DirectQuery — data too large or must be real-time, or must stay in the source (sovereignty, source-side security). Every visual = queries to the source, so performance depends on the source; minimise visuals, avoid bidirectional filters, add aggregations.
  • Dual — for dimension tables shared by Import and DirectQuery facts in a composite model: the engine answers from memory when it can and joins in the source when the query involves the DirectQuery fact (avoids limited relationships and extra source queries).
  • Direct Lake — data already in OneLake as well-maintained Delta (gold layer), large volumes, near-import speed without scheduled data copies; Fabric capacity required. Prepare columns upstream (no Power Query, limited calculated columns).
    • Direct Lake on OneLake: tables from several Fabric items, can add Import tables (composite), never falls back — guardrail breach = failure; SQL endpoint RLS/OLS is not applied (OneLake security is).
    • Direct Lake on SQL endpoint: one source item, can use SQL views and SQL-endpoint security but those cause DirectQuery fallback; property Direct Lake behavior = Automatic / DirectLakeOnly / DirectQueryOnly.

A Direct Lake on SQL endpoint model has a table based on a warehouse SQL view. Reports on it are slow and monitoring shows DirectQuery queries. You must keep the table in Direct Lake. What should you do?

  • Set Direct Lake behavior to DirectLakeOnly
  • Materialize the view's logic into a Delta table (e.g. CTAS) and base the model table on it
  • Change the table to Dual
  • Enable the large semantic model storage format

Direct Lake reads Delta tables; a view always forces fallback in Direct Lake on SQL. DirectLakeOnly would just make the queries fail. Dual is not available for Direct Lake tables, and the large format has nothing to do with fallback.

Composite models

  • Mixed storage modes: e.g. a DirectQuery Sales detail table + an Import aggregation table + Dual dimensions. User-defined aggregations (Manage aggregations, GroupBy on grain columns, Sum etc. on values) answer summary queries from memory; detail falls through to DirectQuery. Not supported for Direct Lake tables.
  • DirectQuery to a published semantic model ("chaining"): in Desktop, connect live to a model and choose Make changes to this model → the remote model becomes a DirectQuery source and you can add local tables, measures, relationships. Needs the tenant setting Allow DirectQuery connections to Power BI semantic models and Build permission on the source model; the source model's RLS still applies to each user; maximum chain length is three models.
  • Direct Lake on OneLake + Import: in web modeling, use OneLake catalog to add Direct Lake tables to an Import model, or Get data to add Import tables (any Power Query connector) to a Direct Lake model.
  • Source groups: each remote source (and all local Import data together) forms a source group. Relationships that cross source groups are limited relationships.

In a composite model, why would you set a shared Date dimension to Dual?

  • So it can serve both Import aggregation queries from memory and DirectQuery joins in the source
  • To make relationships to the dimension bidirectional
  • To store the table both in OneLake and in the source
  • To allow incremental refresh of the dimension

Dual lets the engine behave as Import or DirectQuery per query, avoiding limited relationships and unnecessary source queries.

Star schema in the model

The VertiPaq engine and DAX are optimized for a star schema: narrow fact tables (keys + numeric measures at a declared grain, many rows) surrounded by denormalized dimension tables (descriptive attributes, fewer rows), related with one-to-many, single-direction relationships from dimension to fact on integer surrogate keys. Benefits: simpler DAX, predictable filter propagation, better compression, easier self-service. Snowflakes (Product → Subcategory → Category) should usually be flattened into one dimension.

  • Fact tables answer "how much / how many"; dimensions answer "by what / who / when / where".
  • Avoid one giant flat table (poor compression, ambiguous totals) and avoid fact-to-fact relationships (relate both facts to shared, conformed dimensions instead).
  • Hide key columns and fact columns that are only used through measures.
  • Unmatched fact keys go to the dimension's blank row: totals include them, but no listed member shows them — extend the dimension (e.g. date table covering all years) or map unknowns to an "Unknown" member.

)

Role-playing dimensions

One dimension used in several roles (Order date, Ship date, Due date). Two options:

  • One table + inactive relationships + USERELATIONSHIP measures — fewer tables, but users can't slice by two roles at once with independent slicers.
  • Duplicate the dimension per role (e.g. Order Date, Ship Date as separate tables/views, or calculated tables in Import) — each with an active relationship; clearer for self-service, more memory.

Bridge tables for many-to-many

Example: a bank account can belong to several customers and a customer can own several accounts. Model: DimCustomer 1─* BridgeCustomerAccount *─1 DimAccount 1─* FactBalance. Filters must flow from the bridge to DimAccount — set that relationship to Both (or use CROSSFILTER in measures). Totals across customers are non-additive (a joint account counts once in the grand total but under each owner) — validate and document this.

Date table

  • Use one conformed date dimension (ideally built in the lakehouse/warehouse so every model and storage mode can use it) with Year, Quarter, Month, MonthNumber, Week, fiscal columns, IsWorkingDay, etc.
  • Mark as date table (Table tools → Mark as date table, pick the date column). The column must be of date type, unique, no blanks, no gaps (contiguous days); covering whole years is best practice. Marking lets time-intelligence functions work reliably even when relationships use an integer DateKey.
  • Turn off Auto date/time (File → Options → Data load, for the current file and globally). It creates a hidden date table per date column, wasting memory and bypassing your conformed dimension. It's also not available for Direct Lake on SQL tables.
  • Set Sort by column (MonthName by MonthNumber), hide the key, and build a Year → Quarter → Month → Date hierarchy.

Which statement about the Auto date/time option in an enterprise model is MOST accurate?

  • It should be enabled so that time-intelligence functions work
  • It only affects DirectQuery tables
  • It creates one shared date table for all date columns
  • It should be disabled, because it creates hidden date tables per date column and bypasses the conformed date dimension

Auto date/time adds a hidden table for every date column. Use one marked date dimension instead; time intelligence works with it.

Rule: "Can I slice by it?" → column (preferably upstream). "Is it an aggregate that must react to filters?" → measure.

Implicit vs explicit measures

  • Implicit: dragging a numeric column into a visual (Sum/Count/Average via Summarize by). Explicit: a DAX measure.
  • Prefer explicit measures: they carry governed business logic, can be formatted, documented and reused, work in calculation groups and in Excel PivotTables (Analyze in Excel/MDX clients can't use implicit aggregations).
  • Model property Discourage implicit measures stops report authors from aggregating columns directly. It's switched on automatically when you add a calculation group.
  • Set Summarize by = None for numeric attributes like Year or keys.

Making the model friendly

  • Hide keys and technical columns; descriptions on tables/columns/measures (shown as tooltips, used by Copilot/Q&A).
  • Display folders group measures/columns (nest with \, e.g. Sales\Time intelligence); a dedicated, otherwise empty measures table is a common convention.
  • Hierarchies: an ordered drill path from columns of the same table (Category → Subcategory → Product); metadata only. (Not supported for Direct Lake tables in Excel/MDX clients.)
  • Data category (City, Country, Web URL, Image URL), Sort by column, consistent naming (business names, no prefixes like dim_).
  • Synonyms/linguistic schema help Q&A and Copilot.

Field parameters, calculation groups, dynamic format strings

Field parameters

Modeling → New parameter → Fields. Creates a calculated table listing fields (columns and/or measures); a slicer on it lets report users switch the axis or value of a visual (Product / Region / Channel, or Sales / Margin / Quantity). Supported in Import, DirectQuery and Direct Lake models.

Axis Selector = {
    ( "Product", NAMEOF ( Product[Category] ), 0 ),
    ( "Region",  NAMEOF ( Geography[Region] ), 1 ),
    ( "Channel", NAMEOF ( Sales[Channel] ),    2 )
}

Calculation groups (intro)

A calculation group is a table whose calculation items rewrite whatever measure is in context via SELECTEDMEASURE(): e.g. items Current, YTD, PY, YoY % applied to 20 measures = 4 items instead of 80 measures. Created in Power BI Desktop model view, TMDL view or Tabular Editor (XMLA). Details and DAX patterns: DAX for the exam.

Dynamic format strings

A measure's Format can be set to Dynamic: a DAX expression returns the format string, while the value stays numeric (unlike FORMAT(), which returns text and breaks sorting/charts). Typical uses: currency symbol from a selected currency, K/M/B scaling, % vs absolute. Calculation items can also have a format string expression.

-- Format string expression of measure [Sales (selected currency)]
SELECTEDVALUE ( Currency[FormatString], "#,0.00" )

-- Scale to K / M
VAR v = SELECTEDMEASURE ()            -- or [Total Sales] for a measure
RETURN SWITCH ( TRUE (),
    ABS ( v ) >= 1E6, "#,0.0,,"" M""",     -- "" = escaped quote in DAX
    ABS ( v ) >= 1E3, "#,0.0,"" K""",
    "#,0" )

Report users must switch a chart's axis between Product, Region and Channel with a slicer, without bookmarks. What should you create?

  • A calculation group with three items
  • A hierarchy Product → Region → Channel
  • A field parameter
  • Three inactive relationships

Field parameters let users choose which field a visual uses. Calculation groups modify measures, not axes; a hierarchy needs columns from one table and is a drill path, not a switch.

Model size, perspectives, translations

Large semantic model storage format

  • Required for an Import model to grow beyond 10 GB in the service; with it, the limit becomes the capacity's max memory (or the admin's Max offline semantic model size). The upload from Power BI Desktop is still limited to 10 GB — the model grows in the service through refresh (typically with incremental refresh).
  • Recommended also for smaller models managed with XMLA write operations (partition refresh, deployments) — it improves XMLA write performance — and it is a prerequisite for query scale-out.
  • Available on Fabric F SKUs, Premium P, Embedded A, PPU. Enable per model (Settings → Large semantic model storage format) or set it as the workspace's Default storage format. Don't assume it is on: check the model setting (many capacity workspaces now default to it, but it is a setting).
  • Comes with on-demand load (pages of data loaded as needed) and an 8-million-row default segment size.

Perspectives

A perspective is a named subset of tables/columns/measures to simplify the field list for an audience (finance vs operations) in one governed model. It is not security — hidden objects are still queryable. Created with Tabular Editor or TMDL; used in Power BI for personalize visuals and by clients that support perspectives.

Translations

Metadata translations (object captions, descriptions, display folders) per culture, defined with Tabular Editor/TMDL or Translations Builder. The service shows them according to the user's language setting; Desktop shows the default culture. Data values aren't translated (use translated columns/tables for that).

Security reminders (details in Security & governance)

  • RLS filters rows via roles (filters propagate one-side → many-side), OLS hides tables/columns from metadata. Members with write access (Admin/Member/Contributor) are not restricted by RLS.
  • Bidirectional relationships and RLS: use Apply security filter in both directions only when required.

Scenario. A company has a 3-billion-row FactSales Delta table and conformed dimensions in a gold lakehouse (F64), a small budget Excel file maintained by finance on SharePoint, and an on-premises SQL Server with live inventory levels that must be current to the minute. Requirements: one model for all; sales by order date and by ship date; finance wants a currency selector with correct currency symbols; report authors must only use governed measures; analysts in another workspace want to extend the model with their own tables. Design it.

  • Sales and dimensions: Direct Lake on OneLake (large, already Delta, near-import speed; supports composite with Import). Direct Lake on SQL could not be combined with other storage modes in the same model.
  • Budget: Import table added through Get data (Power Query) in web modeling — composite Direct Lake + Import.
  • Live inventory: needs DirectQuery through a gateway. Direct Lake on OneLake + DirectQuery can be combined only with XMLA tools and Direct Lake can't use a gateway, so the cleaner options are: replicate inventory into OneLake (mirroring/eventstream) and read it via Direct Lake, or build a separate DirectQuery model / composite on top. Discussing this trade-off is the point.
  • Dates: one marked date table, active relationship on OrderDateKey, inactive on ShipDateKey, measure with USERELATIONSHIP. Auto date/time off.
  • Currency: dynamic format string from a Currency table (SELECTEDVALUE(Currency[FormatString])) — values stay numeric.
  • Governed measures: explicit measures in display folders, Discourage implicit measures, hide numeric fact columns, certify the model.
  • Extension by analysts: grant Build; they create a composite model with DirectQuery to the published model (tenant setting enabled), RLS of the source still applies.

Which statement about relationships in a star schema is MOST accurate?

  • Dimension-to-fact relationships should be one-to-many with single-direction filtering by default
  • All relationships should be bidirectional so slicers always work
  • Fact tables should be related directly to each other on shared keys
  • Many-to-many cardinality is preferred because it avoids blank rows

1:* from the dimension with single direction is the pattern the engine optimizes and the easiest to reason about. Bidirectional everywhere creates ambiguity and cost; facts should share dimensions, not relate to each other.

When should you enable the large semantic model storage format?

  • Only for DirectQuery models over 1 TB
  • Whenever a model uses Direct Lake
  • When an Import model must grow beyond 10 GB, or when you manage the model with XMLA write operations
  • To allow the model to be edited in the web

The format is required beyond 10 GB and recommended for XMLA-based write operations. It is unrelated to Direct Lake and web editing.

Key takeaways & exam tips

  • Import = speed + flexibility, data copy and refresh; DirectQuery = real-time/source-resident, slower; Dual = shared dimensions in composite models; Direct Lake = Delta in OneLake, framing instead of copy, Fabric capacity, prepare data upstream.
  • Direct Lake on OneLake: multiple items, composite with Import, no fallback (fails on guardrails), no SQL views, SQL-endpoint RLS not applied. Direct Lake on SQL endpoint: one item, views/SQL security → DirectQuery fallback, controlled by Direct Lake behavior.
  • Composite on a published model needs Build, the tenant setting, max chain of 3; source RLS still applies. Cross-source-group and many-to-many relationships are limited (no blank row, no RELATED).
  • Star schema: 1:* single-direction from dimension to fact, integer surrogate keys, flattened dimensions, no fact-to-fact relationships.
  • One active relationship between two tables; USERELATIONSHIP for role-playing dates (or duplicate the dimension for independent slicers). CROSSFILTER(…, BOTH) in a measure beats a model-wide bidirectional relationship.
  • Many-to-many entities → bridge table with controlled bidirectional filtering; totals are non-additive.
  • Mark a date table (unique, no blanks, contiguous); turn Auto date/time off.
  • Calculated column = static, sliceable, uses memory (prefer upstream); measure = dynamic aggregate. Prefer explicit measures; set Discourage implicit measures.
  • Field parameters switch fields in visuals; calculation groups apply logic to any measure via SELECTEDMEASURE(); dynamic format strings change formatting while keeping numbers numeric.
  • Large model format: > 10 GB, XMLA writes, scale-out. Perspectives = convenience, not security. Translations = metadata per culture.
  • Service settings: credentials/gateway, scheduled refresh (8/day Pro, 48/day capacity), failure notification contacts, Q&A, endorsement (Promoted by writers, Certified by designated groups), sensitivity labels, Build permission.
  • Edit in Desktop, web modeling (workspace setting + Write), TMDL view for scripted changes, Tabular Editor via XMLA for calculation groups/perspectives/translations.
