A Direct Lake on SQL endpoint table is based on a warehouse view; reports are slow and show DirectQuery queries. You must stay in Direct Lake. What do you do?

  • Set Direct Lake behavior to DirectLakeOnly
  • Materialize the view into a Delta table (e.g. CTAS) and use that
  • Change the table to Dual
  • Enable large semantic model storage format

Views always fall back. DirectLakeOnly would just make queries fail; Dual isn't available for Direct Lake.

Deep dive: more storage mode facts
  • Storage mode is really a property of each partition. Calculated tables in DirectQuery become Import; in Direct Lake on SQL only calc groups and field/what-if parameters are allowed.
  • Direct Lake on OneLake sources: lakehouse, warehouse, SQL database, mirrored DB, KQL DB with OneLake availability, shortcuts. Use materialized lake views or Delta tables instead of SQL views.
  • Guardrail exceeded: DL on OneLake fails; DL on SQL falls back (if behavior = Automatic).
  • Self-service authors without lake write access usually use Import (Power Query lives in the model).
  • Details on framing and fallback: Direct Lake in depth.

Why set a shared Date dimension to Dual?
It serves Import queries from memory and joins in the source with DirectQuery facts: no limited relationship.
User-defined aggregations?
Import agg table answers summaries; detail falls through to DirectQuery. Not for Direct Lake tables.
Direct Lake on OneLake + Import?
Yes, in web modeling (OneLake catalog / Get data). DL on SQL can't mix modes.

In a composite model, why set a shared Date dimension to Dual?

  • To serve Import aggregation queries from memory and DirectQuery joins in the source
  • To make its relationships bidirectional
  • To store it both in OneLake and the source
  • To allow incremental refresh

Dual avoids limited relationships and extra source queries.

Star schema & filter direction

Filters flow from the one side to the many side; "both" lets them flow back, which can create ambiguity.

Filter-direction simulator: click a relationship label to toggle single ↔ both
Slicer on:

Try: slicer on Customer, then set Product–Sales to both. Then press Show ambiguity.

"Filters flow downhill: from 1 to many." Going uphill (both) is the exception, done inside one measure with CROSSFILTER.
Single vs Both cross-filter?
Single (default) is recommended. Both risks ambiguity, surprises, slower queries and RLS side effects.
One-to-one relationship?
Always filters both ways; often a sign two tables should be merged.
Assume referential integrity?
DirectQuery only: INNER JOIN instead of OUTER JOIN. Faster, but rows with missing keys vanish.
Unmatched fact keys?
Go to the dimension's blank row: in totals, but under no member. Extend the dimension or add "Unknown".

Which statement about relationships in a star schema is MOST accurate?

  • Dimension-to-fact relationships should be 1:* with single-direction filtering by default
  • All relationships should be bidirectional so slicers always work
  • Fact tables should be related directly to each other
  • Many-to-many is preferred because it avoids blank rows

Facts share conformed dimensions; they don't relate to each other.

Deep dive: star schema rules
  • Facts: narrow, keys + numeric values at a declared grain ("how much / how many"). Dimensions: descriptive, denormalized ("by what / who / when / where").
  • Integer surrogate keys; flatten snowflakes (Product → Subcategory → Category) into one dimension. Avoid one giant flat table and fact-to-fact relationships.
  • Hide keys and fact columns used only through measures.
  • Apply security filter in both directions lets RLS flow from many to one side on a bidirectional relationship: use sparingly.

Role-playing dates, bridges & the date table

Keep relationships simple in the model and switch behavior inside the measures that need it.

Sales by Ship Date =
CALCULATE ( [Total Sales],
    USERELATIONSHIP ( Sales[ShipDateKey], 'Date'[DateKey] ) )

Customers Buying Selected Products =
CALCULATE ( DISTINCTCOUNT ( Sales[CustomerKey] ),
    CROSSFILTER ( Sales[CustomerKey], Customer[CustomerKey], BOTH ) )
  1. Only one relationship between Sales and Date is active (OrderDate). USERELATIONSHIP activates the inactive ShipDate one for this measure.
  2. CROSSFILTER makes one relationship bidirectional only inside this measure, instead of model-wide.

Which statement about Auto date/time in an enterprise model is MOST accurate?

  • Enable it so time intelligence works
  • It only affects DirectQuery tables
  • It creates one shared date table for all date columns
  • Disable it: it creates hidden date tables per date column and bypasses the conformed date dimension

Time intelligence works fine with one marked date dimension.

Deep dive: date table checklist
  • One conformed date dimension, ideally built in the lakehouse/warehouse so every model and storage mode can use it: Year, Quarter, Month, MonthNumber, Week, fiscal columns, IsWorkingDay.
  • Marking lets time intelligence work even when relationships use an integer DateKey.
  • Auto date/time: File → Options → Data load (current file and global). Not available for Direct Lake on SQL tables.
  • Sort MonthName by MonthNumber, hide the key, build Year → Quarter → Month → Date.

Columns, measures & a friendly model

Ask "Can I slice by it?" for a column, and "Must it react to filters?" for a measure.

  • Use on axis, slicer, relationship
  • Static: ignores slicers
  • Better: compute upstream

Implicit vs explicit measure?
Implicit = dragged column (Sum, Count). Explicit = DAX measure: formatted, reusable, works in Excel and calc groups.
Discourage implicit measures?
Model property: authors must use explicit measures. Auto-on when you add a calculation group.
Numeric Year or key column?
Set Summarize by = None.

Users must switch a chart's axis between Product, Region and Channel with a slicer, without bookmarks. What do you create?

  • A calculation group with three items
  • A hierarchy Product → Region → Channel
  • A field parameter
  • Three inactive relationships

Calculation groups change measures, not axes; a hierarchy is a drill path within one table.

VAR v = SELECTEDMEASURE ()
RETURN SWITCH ( TRUE (),
    ABS ( v ) >= 1E6, "#,0.0,,"" M""",
    ABS ( v ) >= 1E3, "#,0.0,"" K""",

Hierarchies are metadata only (not supported for Direct Lake tables in Excel/MDX clients). Implicit aggregations can't be used by Analyze in Excel / MDX clients.

When should you enable the large semantic model storage format?

  • Only for DirectQuery models over 1 TB
  • Whenever a model uses Direct Lake
  • When an Import model must grow beyond 10 GB, or you manage it with XMLA writes
  • To allow editing in the web

It's also a prerequisite for query scale-out. Unrelated to Direct Lake and web editing.

Deep dive: service settings
  • Large format: F, P, A SKUs and PPU; per model or workspace default. Upload from Desktop stays ≤ 10 GB; grow via refresh (incremental). On-demand load, 8-million-row default segments. Check the setting, don't assume it's on.
  • Credentials / gateway: cloud connection or on-prem/VNet gateway (never for Direct Lake); prefer service principal or shared connection.
  • Refresh: better to trigger a semantic model refresh activity in the pipeline after load. Failure notifications to a monitored group mailbox.
  • Take over when the owner leaves (re-enter credentials). Incremental refresh / hybrid tables defined in Desktop (RangeStart/RangeEnd, must fold).
  • Direct Lake: Keep data up to date (automatic reframing). Q&A on/off. Query caching speeds first load at the cost of memory.
  • Discoverable models can be requested in the OneLake catalog. Sensitivity labels flow downstream (encryption travels with exports).
  • Permissions: Read, Build (reports, Analyze in Excel, composite on top), Write, Reshare. RLS doesn't restrict Admin/Member/Contributor.

Scenario. 3-billion-row FactSales Delta in a gold lakehouse (F64), a finance budget Excel on SharePoint, and on-prem live inventory. Needs: one model, sales by order and ship date, currency selector with correct symbols, only governed measures, analysts in another workspace extend it. Design it.

  • Sales + dimensions: Direct Lake on OneLake; budget: Import via web modeling (composite).
  • Inventory: DL can't use a gateway; replicate it into OneLake (mirroring / eventstream) or use a separate DirectQuery model. That trade-off is the point.
  • Marked date table; inactive ShipDate relationship + USERELATIONSHIP; Auto date/time off.
  • Currency: dynamic format string. Governed: explicit measures, folders, Discourage implicit measures, certify.
  • Extension: grant Build; analysts build a composite model on it; source RLS still applies.

Exam traps

  • Direct Lake on SQL falls back on views and SQL security; Direct Lake on OneLake never falls back, it fails.
  • Dual is for shared dimensions in composite models, not for Direct Lake tables.
  • Limited relationships: no blank row, no RELATED().
  • Bidirectional everywhere = ambiguity. Prefer CROSSFILTER in one measure.
  • Only one active relationship per table pair: USERELATIONSHIP for the others.
  • Perspectives are not security.
  • Large model format: beyond 10 GB and for XMLA writes; not related to Direct Lake.
  • Certified needs admin-designated groups; Promoted needs only Write.

Cheat sheet

💾 Storage modes

  • Import: fast, copy, refresh
  • DirectQuery: live, slower
  • Dual: shared dims
  • Direct Lake: Delta, framing

⭐ Star

  • 1:* single, dim → fact
  • Surrogate keys, flat dims
  • Bridge for many-to-many
  • Marked date table, Auto date/time off

🔧 DAX switches

  • USERELATIONSHIP: inactive path
  • CROSSFILTER(…, BOTH): one measure
  • SELECTEDMEASURE: calc groups

🎛️ Features

  • Field parameters: switch fields
  • Dynamic format strings
  • Perspectives, translations, folders

⚙️ Service

  • Large format > 10 GB
  • Refresh 8/day Pro, 48/day capacity
  • Composite on model: Build + tenant setting, chain ≤ 3
