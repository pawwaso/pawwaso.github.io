How content travels from a developer's laptop to Production: versioned in Git, promoted by pipelines, managed over XMLA.

Who can connect / disconnect a workspace to Git?
Only the workspace Admin. Contributors/Members commit, update, branch out. Viewers see nothing Git-related.
Can Update apply just one incoming item?
No. Update always applies the whole branch; Commit is the selective one.
What does a lakehouse put in Git?
Metadata only (shortcuts, settings). Tables and files stay in OneLake.

Two items show Update required, one shows Uncommitted changes. You want just one incoming item. What is true?

  • Select one incoming item and update only that
  • Update applies the whole branch, and commit is blocked until you update
  • The workspace syncs automatically every 15 minutes
  • Disconnect and reconnect to receive changes

Commit is selective, Update is not; no automatic sync exists.

A Contributor wants to connect the workspace to a different repository. What happens?

  • Works: Contributors manage all Git settings
  • Works only for an Azure DevOps project admin
  • Fails: connect/disconnect needs workspace Admin
  • Fails: a workspace can never be reconnected

Connection settings belong to workspace Admins; reconnecting is allowed for them.

Deep dive: prerequisites, permissions, limits, supported items
  • Not supported: on-prem Git servers, GitHub Enterprise Server, Bitbucket, GitLab, TFVC, submodules, sovereign clouds, My workspace, workspaces with template apps.
  • Tenant setting Users can synchronize workspace items with their Git repositories (+ cross-geo export for ADO in another geography; separate setting for sensitivity-labelled items).
  • Each user signs in with their own Git credentials (GitHub PAT; Azure DevOps Entra SSO).
  • Switch branch overwrites all items (Admin, or Contributor+ if the workspace setting allows). Checkout new branch (Admin) changes the connection without changing content. Branch out needs Contributor+ and Git Create branch.
  • Commit: Contributor+ with write on all items; Azure Repos Read + Contribute, and branch policy must allow direct commit.
  • Limits: file 25 MB, path 250 chars, branch name 244 chars, folder depth 10; commit size ADO 125 MB (user) / 25 MB (service principal), GitHub 50 MB. Duplicate item names (same type) make commit/update fail.
  • Supported items include notebooks, Spark job definitions, environments, lakehouses (metadata), warehouses (SQL database project), SQL databases, pipelines, Copy jobs, Dataflow Gen2, mirrored DBs, eventhouses, KQL DBs/querysets, eventstreams, Activator, Real-Time dashboards, variable libraries, semantic models and reports, paginated reports. Not: push datasets, live connections to AAS, model v1; reports on AAS/SSAS.
  • Every item gets a .platform file (type, display name, logical ID). Notebooks: notebook-content.py, no outputs. Items re-created by Git get a new ID and no data; the recycle bin keeps ID and data.
  • Downloading a .pbix of a Git-created report/model is unreliable: open the PBIP in Desktop.

Deep dive: publishing and PBIP limitations
  • Desktop → Publish uploads metadata and the local cache; Git integration or Fabric APIs deploy metadata only.
  • Convert back with Save as .pbix (Desktop only, no programmatic converter). Desktop detects external TMDL/PBIR edits and offers Apply external changes.
  • Limits: no sensitivity labels in PBIP; Windows 260-char path limit; can't save directly to OneDrive/SharePoint; UTF-8 without BOM; CRLF line endings.

Do Direct Lake models autobind on deploy?
No. They keep pointing at the source-stage lakehouse. SQL endpoint variant → data source rule; OneLake variant → M parameters + parameter rules.
Minimum rights to deploy Dev → Test?
Pipeline admin + Contributor (or higher) on both source and target workspaces.

Model1 reads sql-dev. In Production it must read sql-prod (same connector). Where do you configure this?

  • A parameter in Dev workspace settings
  • A data source rule on Model1 in the Development stage
  • Production workspace settings
  • A data source rule on Model1 in the Production stage, then deploy to Production

Rules live on the target stage (never the first) and apply on the next deployment.

After deploying a Direct Lake on SQL endpoint model and its lakehouse to Prod, the report still shows Test data. Why?

  • Direct Lake models don't autobind: add a data source rule in Prod and redeploy
  • The pipeline copied Test data to Prod
  • Prod needs the same refresh schedule as Test
  • Direct Lake models can't be deployed

No data is ever copied; Direct Lake keeps its original binding until a rule changes it.

Deep dive: pairing, compare, autobinding, permissions, rule fine print
  • Workspaces must be on Fabric capacity (Power BI-only content: PPU too). Stage count and names are fixed after creation; stages can be public/private.
  • Pairing: on assignment or clean deploy. Paired items stay paired when renamed and get overwritten. Unpaired look-alikes → duplicate created (or first deploy fails on same name + type).
  • Compare: same / different (Review changes diff) / only in source / only in target. Selective deploy + Select related adds dependencies. Missing dependency in target → deployment fails. History (pipeline admin). REST APIs; deployment plans (preview).
  • Small changes keep target data; breaking changes need a full refresh. Incremental refresh partitions retained. No .pbix download after deployment. Sensitivity labels copied only for new items/empty stage or protected labels.
  • Autobinding across pipelines needs the same stage position and same number of stages. Avoid it with an item outside the stage, a parameter rule, or a proxy model. Not for Dataflow Gen2.
  • Rules: you must own the item + Contributor on target. Data source rules only switch to the same source type for listed connectors (Azure SQL, SQL Server, Synapse, AAS, SSAS, OData, Oracle, SAP HANA import, SharePoint, Teradata); otherwise parameter rules (Text parameters). Removed source/parameter → rule invalid, deployment fails. Deleting the item or unassigning the workspace deletes rules.
  • Permissions: create pipeline = Pro/PPU/Premium; pipeline admin is the only pipeline role (no M365 groups) and grants no workspace content access. Assign a workspace = pipeline admin + workspace Admin. Deploy to empty stage = pipeline admin + source Contributor + capacity rights. Block republish switch → model owner needed.

Scenario: A pipeline copies from LH_Bronze_Dev and a notebook defaults to LH_Silver_Dev. After deploying to Test both still hit Dev. Fix each.

  • Notebook: default lakehouse rule in Test/Prod, or variable library (NotebookUtils / %%configure).
  • Pipeline: no rules exist → variable library item reference (or per-environment parameters).
  • Redeploy; load Test data separately (shortcut or clone), since no data is copied.
Deep dive: good practice
  • Separate workspaces per stage; one shared workspace removes isolation.
  • Realistic test data cheaply: warehouse zero-copy clone (CREATE TABLE … AS CLONE OF) or shortcuts.
  • Publish an app per stage; deployment doesn't update the app.
  • Five developers overwriting each other's PBIX → PBIP + TMDL in Git, feature branches, PRs with branch policy, Update Dev, pipeline with a Prod data source rule, restrict Prod roles.

Deep dive: XMLA fine print
  • XMLA refresh: no 48/day limit, no scheduled-refresh timeout, single partitions (or REST enhanced refresh). History shows "via XMLA endpoint".
  • Enable large semantic model storage format for XMLA writes (required beyond 10 GB). Credentials can't be set over XMLA.
  • Not reachable: live-connection models, push datasets, Excel workbook models. Server-admin operations unsupported. Audited (EditDatasetFromExternalApplication…).
  • Tools: SSMS (TMSL, process, roles, DMVs), Tabular Editor 2/3 (perspectives, translations, OLS, C# scripts), DAX Studio (VertiPaq Analyzer, read-only), ALM Toolkit (keeps incremental refresh partitions), Visual Studio / PowerShell / TOM, Report Builder and Excel (read).
  • Workspace lineage view shows in-workspace dependencies; deployment pipelines show View lineage and Select related.

Exam traps

  • Git or a deployment never copies data: refresh/load after deploying.
  • Rules are created on the target stage, never in Development, and apply only on the next deployment.
  • Pipelines, Copy job, Dataflow Gen2 have no deployment rules: use a variable library.
  • Direct Lake models don't autobind: rule or parameter needed.
  • Update can't cherry-pick; commit is blocked until you update. No automatic sync.
  • Only workspace Admins connect Git; Viewers can't see Git at all.
  • Pipeline admin alone can't see or deploy content: you also need Contributor on both workspaces.
  • XMLA write failing for a Member → capacity setting Read Write, not Build permission.
  • Bitbucket/GitLab/on-prem Git are not supported.
