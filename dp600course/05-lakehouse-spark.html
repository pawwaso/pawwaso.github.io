Lakehouse, Delta & Spark notebooks

How a Fabric lakehouse is organised, what Delta Lake gives you (ACID, time travel, schema enforcement, MERGE), how to keep Delta tables fast (OPTIMIZE, V-Order, Z-Order, VACUUM, partitioning), and how to write, parameterise and run Spark notebooks on the right compute. Lakehouse structure: Tables vs Files

A lakehouse is a Fabric item that stores data in OneLake and combines a data-lake folder layout with a relational view of Delta tables. Creating a lakehouse automatically provisions a SQL analytics endpoint (read-only T-SQL). There is no automatic default semantic model any more – you create semantic models explicitly.

  • The portal action Load to Tables (right-click a CSV/Parquet file or folder in Files) converts files into a Delta table without code – handy for quick loads, but no transformations.
  • Shortcuts can be created in both areas. A shortcut under Tables/ that points to a Delta table appears as a table (queryable with T-SQL); a shortcut under Files/ is just a folder. See Get data.
  • Store curated data as Delta tables in the Tables section: columnar, compressed Parquet with column pruning and file skipping – the format the SQL analytics endpoint and Direct Lake read. Keep incoming raw files (CSV, JSON, images) in their original form in Files.

Schema-enabled lakehouses

  • Lakehouse schemas are enabled by default when you create a lakehouse in the portal (checkbox Lakehouse schemas). Through the REST API you must pass "enableSchemas": true.
  • Every schema-enabled lakehouse has a dbo schema that can't be renamed or removed. A table written without a schema name lands in dbo: saveAsTable("marketing.products") writes to schema marketing.
  • Spark uses a four-part name workspace.lakehouse.schema.table, enabling cross-workspace joins in a single Spark SQL query. Non-schema lakehouses use workspace.lakehouse.table.
  • Schema shortcuts map a whole schema to another lakehouse's schema or an ADLS Gen2 folder of Delta tables.
  • Schemas enable schema-level security and are required by newer features such as materialized lake views.
  • Existing non-schema lakehouses can't (yet) be converted in place; Spark can query and join both types in the same code. To use schemas in a notebook, the notebook's default lakehouse must be schema-enabled (or there is no default lakehouse).

SQL analytics endpoint

Every lakehouse (and every warehouse, mirrored database and SQL database) has exactly one SQL analytics endpoint. It runs on the same distributed engine as Fabric Data Warehouse and exposes each Delta table in Tables/ as a SQL table.

  • Create views, inline/table-valued functions, stored procedures and custom schemas
  • Security: GRANT/DENY, row-level security (security policies), column-level security, dynamic data masking
  • Cross-database queries with three-part names to other warehouses/endpoints in the same workspace
  • Read shortcuts that point to Delta tables
  • INSERT, UPDATE, DELETE, MERGE, COPY INTO on lakehouse tables (data is read-only; write with Spark, pipelines or Dataflow Gen2)

  • Zero-copy table clone

Metadata sync

  • A background process reads the Delta logs under /Tables and keeps the SQL metadata current: new/dropped tables, data changes, schema changes. There can be a short lag – a table created by a Spark job may not be visible for a brief time.
  • Force a sync with the Refresh button in the endpoint's Explorer, the Refresh SQL analytics endpoint metadata REST API, or the pipeline Refresh SQL analytics endpoint activity (common after a load, before reports run).
  • New metadata sync (preview, 2026): enabled per workspace (Workspace settings → Warehouse settings), applies to new endpoints, keeps data queryable within seconds and adds sys.sp_dw_refresh_ext_table for per-table refresh. T-SQL time travel on SQL analytics endpoints requires it.
  • Delta types map to SQL types: STRING → varchar(8000) (UTF-8 BIN2 collation), TIMESTAMP → datetime2, DOUBLE → float, LONG → bigint. Columns with unsupported types aren't shown.
"Analysts must create reusable views over lakehouse tables" → SQL analytics endpoint (read-only data, but views/functions/procedures/security objects allowed). "Analysts must UPDATE rows with T-SQL" → that needs a warehouse, not the endpoint.

Delta Lake fundamentals

Delta Lake is the open table format used by every Fabric engine (Spark, warehouse, SQL endpoint, Direct Lake, KQL OneLake availability). A Delta table = Parquet data files + a transaction log in _delta_log/.

Transaction log & ACID

  • Each commit writes an ordered JSON file (00000000000000000000.json, …01.json …) listing files added and removed, plus metadata and commit info. Periodic checkpoint Parquet files summarise the log so readers don't replay every JSON.
  • Atomicity: a write is visible only when its commit file is written; failed jobs leave no partial data. Isolation: readers see a consistent snapshot (a specific table version).
  • Optimistic concurrency: concurrent writers both prepare files; the log serialises commits. If the second writer's changes conflict with what the first committed (e.g. same files), it fails with a concurrency exception and can be retried. Appends rarely conflict.
  • Updates/deletes rewrite files (copy-on-write) unless deletion vectors are enabled: they mark rows as deleted without rewriting whole files, speeding up DELETE/UPDATE/MERGE; OPTIMIZE (or the maintenance option to purge deletion vectors) later materialises the changes.

Time travel

-- Spark SQL
DESCRIBE HISTORY sales;                               -- versions, operations, timestamps
SELECT * FROM sales VERSION AS OF 12;
SELECT * FROM sales TIMESTAMP AS OF '2026-11-03 08:00:00';
RESTORE TABLE sales TO VERSION AS OF 12;              -- roll the table back

# PySpark
df = spark.read.format("delta").option("versionAsOf", 12).load("Tables/sales")
df = spark.read.option("timestampAsOf", "2026-11-03").table("sales")

Time travel works only while the old data files still exist – VACUUM removes files older than the retention threshold, which ends time travel to those versions.

Schema enforcement & evolution

  • Schema enforcement (on by default): a write whose columns or types don't match the table fails – protecting the table from bad data.
  • Schema evolution must be requested explicitly:
    • .option("mergeSchema", "true") – adds new columns (existing rows get NULL). Use for an append that brings a new column.
    • .option("overwriteSchema", "true") with mode("overwrite") – replaces the schema (e.g. type changes, dropped columns).
(df.write.format("delta")
   .mode("append")
   .option("mergeSchema", "true")      # accept the new discount_code column
   .saveAsTable("sales"))

MERGE (upsert)

MERGE matches source rows to target rows on a key and performs insert, update and delete in a single atomic, set-based operation – the tool for upserts, CDC application (including soft/hard deletes) and SCD logic.

%%sql
MERGE INTO silver.customers AS t
USING staging_customers AS s
  ON t.CustomerID = s.CustomerID
WHEN MATCHED AND s.IsDeleted = 1 THEN DELETE
WHEN MATCHED THEN UPDATE SET
     t.Name = s.Name, t.City = s.City, t.ModifiedAt = s.ModifiedAt
WHEN NOT MATCHED AND s.IsDeleted = 0 THEN INSERT *;
# PySpark DeltaTable API
from delta.tables import DeltaTable
tgt = DeltaTable.forName(spark, "silver.customers")
(tgt.alias("t")
    .merge(src_df.alias("s"), "t.CustomerID = s.CustomerID")
    .whenMatchedDelete(condition="s.IsDeleted = 1")
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute())
MERGE fails if more than one source row matches the same target row. Deduplicate the source first (e.g. row_number() over the key ordered by timestamp, keep 1) – see Transform data.

Delta enforces the schema by default; mergeSchema explicitly allows evolution so the new column is added and old rows receive NULL. Overwrite or drop would lose data; casting doesn't remove the extra column.

Delta time travel reads an earlier table version while its files are still retained; RESTORE TABLE can then roll back. Restore points are a warehouse feature, and re-ingesting is far more work.

Table maintenance: OPTIMIZE, V-Order, Z-Order, VACUUM

The small-files problem

Every Spark write produces at least one file per output partition. Frequent micro-batches, streaming, over-partitioning or many small appends produce thousands of tiny Parquet files. Effects: more file-open and metadata overhead for every reader, slower SQL endpoint metadata sync, slower Direct Lake transcoding (and Direct Lake guardrails count Parquet files per table), poor compression.

Fixes, in order of preference: batch the ingestion, keep optimize write on, enable auto compaction where appropriate, and run scheduled OPTIMIZE, followed by VACUUM.

V-Order

  • A write-time optimisation of Parquet (special sorting, row-group distribution, dictionary encoding and compression) that makes reads much faster for VertiPaq-style engines – Power BI Direct Lake and the SQL engine – and also helps Spark. Files stay open-source Parquet compliant.
  • Cost: writes are typically ~15% slower; compression can improve up to ~50%.
  • Default in new workspaces: OFF for Spark. New workspaces use the writeHeavy resource profile with spark.sql.parquet.vorder.default=false. (Older workspaces had it on.) The Fabric warehouse writes V-Order by default; it can only be disabled at warehouse level and that is irreversible.
  • Control levels (most specific to broad): write option parquet.vorder.enabled; table property delta.parquet.vorder.enabled; session spark.sql.parquet.vorder.default; or switch resource profile to readHeavyForPBI (V-Order on, 1 GB bin size) / readHeavyForSpark.
  • Changing the setting affects future writes only. To V-Order existing files, rewrite them: OPTIMIZE table VORDER.
  • Use it for read-heavy gold tables feeding Direct Lake/SQL; consider leaving it off for write-heavy bronze/staging tables that are rarely queried.
%%sql
SET spark.sql.parquet.vorder.default = TRUE;                         -- session
ALTER TABLE gold.fact_sales SET TBLPROPERTIES ("delta.parquet.vorder.enabled" = "true");  -- table
OPTIMIZE gold.fact_sales VORDER;                                     -- rewrite existing files

# per write
df.write.format("delta").option("parquet.vorder.enabled", "true").mode("overwrite").saveAsTable("gold.fact_sales")

# resource profile for the session (environment setting takes effect unless overridden at runtime)
spark.conf.set("spark.fabric.resourceProfile", "readHeavyForPBI")

OPTIMIZE (bin compaction) and Z-Order

%%sql
OPTIMIZE sales;                                   -- compact small files into larger ones
OPTIMIZE sales WHERE OrderYear = 2026;            -- only some partitions (partition columns only)
OPTIMIZE sales ZORDER BY (CustomerID);            -- compact + co-locate values of CustomerID
OPTIMIZE sales ZORDER BY (CustomerID) VORDER;     -- Z-Order and V-Order together
  • OPTIMIZE writes new, larger files and marks the small ones as removed in the log; old files remain until VACUUM.
  • Z-Order clusters rows with similar values of the chosen (high-cardinality, frequently filtered) column(s) into the same files, so min/max file statistics let readers skip files (data skipping). If a filtered column's values are spread across all files, min/max ranges overlap and almost nothing can be skipped.
  • Liquid clustering (CLUSTER BY) is a newer, flexible alternative to Hive-style partitioning + Z-Order: it adapts layout to clustering keys without the small-file and skew problems of over-partitioning.

VACUUM and retention

%%sql
VACUUM sales;                       -- default retention: 7 days (168 hours)
VACUUM sales RETAIN 240 HOURS;      -- keep 10 days of history
  • Removes data files no longer referenced by the log and older than the retention threshold. Default and recommended minimum: 7 days.
  • Portal/API maintenance requests with retention under 7 days fail by default; you must set spark.databricks.delta.retentionDurationCheck.enabled=false in the environment to go lower.
  • Risks of aggressive vacuuming (e.g. 1 day after every load): time travel and recovery beyond that window become impossible, and long-running readers still using old files may fail.
  • Correct order: OPTIMIZE first (creates big files, orphans small ones), then VACUUM (deletes orphaned files once the retention allows).

Running maintenance without code

  • Lakehouse explorer → table … → Maintenance: run OPTIMIZE (optionally Apply V-order), VACUUM with a retention threshold, and purge deletion vectors. Runs show as TableMaintenance in the Monitoring hub. Delta tables only.
  • Lakehouse Maintenance activity (pipelines, preview) for scheduled maintenance chained after loads, optionally followed by a Refresh SQL analytics endpoint activity.
  • Also: notebooks (code above) and the lakehouse REST API.

Partitioning guidance

  • Partition only large tables, on low-cardinality columns that queries commonly filter on (year, month, region). Each partition should still hold substantial data (think ≥ 1 GB).
  • Don't partition by high-cardinality columns (customer ID, timestamp, day over many years): 1,800 daily partitions with tiny files make month queries slow. Repartition by month/year or use clustering, then compact.
  • Partition pruning skips whole folders; Z-Order/clustering/V-Order improve skipping inside partitions.
  • Selective overwrite: .option("replaceWhere", "OrderDate >= '2026-11-01'") rewrites just one window – an idempotent reload pattern.
(df.write.format("delta")
   .mode("overwrite")
   .partitionBy("OrderYear", "OrderMonth")
   .saveAsTable("silver.orders"))

Which sequence of maintenance operations on a heavily appended Delta table is correct?

  • VACUUM, then OPTIMIZE
  • OPTIMIZE, then VACUUM with an appropriate retention
  • VACUUM RETAIN 0 HOURS after every load
  • OPTIMIZE alone deletes the old small files

OPTIMIZE writes compacted files and leaves the old ones unreferenced; VACUUM then removes unreferenced files older than the retention period. OPTIMIZE never deletes files itself.

Spark notebooks: PySpark & Spark SQL

Notebooks support PySpark (Python), Spark SQL, Scala and SparkR, plus Python notebooks (single-node, no Spark – cheap for small data with pandas/polars/DuckDB). Attach a default lakehouse so relative paths (Files/…, Tables/…) and unqualified table names resolve to it. Each cell can switch language with a magic: %%pyspark, %%sql, %%spark (Scala), %%sparkr, %%configure (session config), %run (inline another notebook).

PySpark DataFrame code and Spark SQL compile through the same Catalyst optimizer to the same physical plans – choose by team skills and readability, not performance.

Spark performance basics the exam likes

  • Lazy evaluation: transformations (select, filter, join) only build a plan; execution starts on an action (write, count, collect, display).
  • Cache/persist a DataFrame reused by several actions (e.g. three aggregations written from one cleansed DataFrame) to avoid recomputing the source.
  • Broadcast join: fact.join(F.broadcast(dim), "ProductID") ships a small table to every executor – no shuffle of the large table.
  • Data skew: one task running far longer than the others in the Spark UI = one key holds a disproportionate share of rows (salting, AQE skew-join handling).
  • Number of output files = number of output partitions; repartition/coalesce and optimize write influence it.
  • Diagnose with the Spark UI (jobs, stages, tasks, shuffle), reachable from the Monitoring hub or the notebook run.

Parameters cell & running from pipelines

  1. Put default values in one cell, e.g. load_date = "2026-01-01", and use … → Toggle parameter cell to mark it as the parameters cell.
  2. In a pipeline, add a Notebook activity and define base parameters with the same names (e.g. load_date = @formatDateTime(pipeline().TriggerTime, 'yyyy-MM-dd')).
  3. At run time Fabric injects a new cell after the parameters cell that overrides the defaults.
  4. Call notebookutils.notebook.exit(value) to return a value; downstream activities read it from the activity output (exitValue).
  5. Raise an exception (e.g. when a duplicate check fails) to fail the Notebook activity – dependent "on success" activities (gold build, model refresh) then don't run. This is a simple data-quality gate.
# parameters cell
load_date = "2026-01-01"

# later cell – data quality gate
dups = spark.sql(f"""
    SELECT OrderID FROM silver.orders WHERE LoadDate = '{load_date}'
    GROUP BY OrderID HAVING COUNT(*) > 1""").count()
if dups > 0:
    raise ValueError(f"{dups} duplicate OrderID values for {load_date}")

Gold is frequently a warehouse when the team prefers T-SQL. Materialized lake views (schema-enabled lakehouses) can declare silver/gold transformations in Spark SQL with managed refresh.

Watermark pattern (pipeline)

  1. Lookup activity reads the last watermark from a control table (e.g. dbo.Watermark in a warehouse).
  2. Copy data activity extracts WHERE ModifiedDate > @{activity('Lookup').output.firstRow.Watermark}.
  3. Notebook / stored procedure MERGEs into silver.
  4. Only on success, a Stored procedure activity sets the watermark to the highest ModifiedDate actually copied (not GETDATE()). A failed run leaves the old watermark, so the next run re-reads the same window – the load is safe to rerun.
# Notebook version of a watermark load
from pyspark.sql import functions as F
wm = spark.sql("SELECT MAX(ModifiedDate) AS wm FROM silver.orders").first()["wm"] or "1900-01-01"
src = (spark.read.table("bronze.orders_raw")
          .filter(F.col("ModifiedDate") > F.lit(wm)))
# ...dedupe src, then MERGE into silver.orders (see MERGE above)
"Safe to rerun after a mid-run failure" = idempotent: overwrite the affected partition/window or MERGE on business keys, and advance the watermark only after success.

Scenario: A notebook ingests IoT micro-batches every five minutes into a Delta table. After several weeks the table has 60,000 small files; SQL endpoint queries and a Direct Lake report have slowed down, and someone proposes running VACUUM RETAIN 0 HOURS after every batch to "clean up". What do you recommend?

Don't vacuum aggressively – VACUUM only deletes unreferenced files, so it doesn't fix the small files that make up the current version, and 0-hour retention breaks time travel and can make concurrent readers fail (it's blocked below 7 days by default anyway). Instead: (1) batch ingestion where latency allows; (2) ensure optimize write (and optionally auto compaction) is on; (3) schedule OPTIMIZE (with V-Order for the Direct Lake table, possibly Z-Order on the main filter column) via the Lakehouse Maintenance activity or a notebook; (4) then run VACUUM with the default 7-day retention to remove the compacted-away files; (5) refresh the SQL analytics endpoint/Direct Lake model after maintenance. If the stream needs exactly-once semantics, use Spark structured streaming with a checkpoint location.

Specifying a path creates an external (unmanaged) table. Dropping it only removes the metastore entry; the data survives.

A Delta table is partitioned by OrderDate at day level over five years (~1,800 partitions with a few small files each). Month-filtered queries are slow. Which change helps most?

  • Partition by OrderID instead
  • Run VACUUM daily
  • Disable V-Order
  • Partition at month/year level (or cluster on OrderDate) and compact the files

Over-partitioning on a high-cardinality column creates many tiny files. Coarser partitions or clustering plus compaction produce well-sized files while keeping pruning/skipping.

Key takeaways & exam tips

  • Files = raw/landing any format; Tables = Delta tables discovered by the SQL analytics endpoint and used by Direct Lake.
  • Managed table drop deletes data; external (path) table drop removes metadata only.
  • Lakehouse schemas are on by default in the portal; dbo is default; Spark uses workspace.lakehouse.schema.table.
  • SQL analytics endpoint: read-only data, but views, functions, procedures and security (RLS/CLS/DDM, GRANT) are allowed; metadata sync can lag → Refresh button/API/pipeline activity.
  • Delta: transaction log → ACID, optimistic concurrency (conflicting writer fails and retries), time travel (VERSION/TIMESTAMP AS OF, RESTORE) until VACUUM removes files.
  • Schema enforcement by default; mergeSchema to add columns, overwriteSchema to replace the schema.
  • MERGE = atomic upsert/delete; dedupe the source first.
  • V-Order is off by default for Spark in new workspaces (writeHeavy profile) and on by default in the warehouse; enable it for read-heavy gold/Direct Lake tables and rewrite with OPTIMIZE … VORDER.
  • Small files → optimize write, batching, auto compaction, scheduled OPTIMIZE (+ Z-Order on common filter columns). Then VACUUM (default 7 days; under 7 days blocked unless the retention check is disabled).
  • Partition only by low-cardinality filter columns; avoid day-level partitions over years; consider liquid clustering.
  • Notebook parameters: parameters cell + Notebook activity base parameters; notebookutils.notebook.run to call another notebook with parameters; notebook.exit to return values; raise an exception to fail the activity.
  • Compute: starter pool (seconds, Medium nodes) + high concurrency for cheap fast dev; custom pools need workspace Admin; environments package runtime + libraries + Spark properties; NEE accelerates Parquet/Delta with automatic fallback.
  • Medallion: bronze keeps raw history for reprocessing, silver applies cleansing once, gold is consumption-shaped.
  • Incremental loads: Lookup watermark → Copy changed rows → MERGE → update watermark only on success (to the max value copied).
