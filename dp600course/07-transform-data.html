  • Store data at the grain the business needs: monthly analysis of a 400M-row table → summarise to monthly grain in gold.

Slowly changing dimensions

When an attribute changes: keep it (0), overwrite (1), add a row (2) or add a column (3).

SCD simulator: customer C042 moves
MERGE INTO gold.dim_customer AS d
USING (
  SELECT s.CustomerID AS MergeKey, s.* FROM stg AS s
  UNION ALL
  SELECT NULL AS MergeKey, s.* FROM stg AS s
  JOIN gold.dim_customer AS c
    ON c.CustomerID = s.CustomerID AND c.IsCurrent = true
  WHERE c.RowHash <> s.RowHash
) AS u
ON d.CustomerID = u.MergeKey AND d.IsCurrent = true
WHEN MATCHED AND d.RowHash <> u.RowHash THEN
  UPDATE SET d.IsCurrent = false, d.ValidTo = current_timestamp()
WHEN NOT MATCHED THEN
  INSERT (CustomerKey, CustomerID, City, RowHash, ValidFrom, ValidTo, IsCurrent)
  VALUES (xxhash64(u.CustomerID, current_timestamp()), u.CustomerID, u.City,
          u.RowHash, current_timestamp(), NULL, true);
  1. Copy 1 of every staged row, keyed by the real business key: it can match the current row.
  2. Copy 2 only for changed rows (row hash differs), with a NULL key: it never matches.
  3. Match only the current version of each customer.
  4. Changed: expire the old row. Unchanged rows match but fail the hash test → no-op.
  5. NULL-key copies and brand-new customers are inserted as current versions with a new surrogate key.
  1. Land today's full customer extract in staging
  2. Compute a row hash of the tracked attributes
  3. Compare staging with current rows on the business key
  4. Expire changed rows: ValidTo + IsCurrent = 0
  5. Insert new versions and new customers with new surrogate keys
  6. Load facts using the version valid at the transaction date

Deep dive: T-SQL version, type 4, rebuild from history 
BEGIN TRAN;
UPDATE d SET d.ValidTo = SYSUTCDATETIME(), d.IsCurrent = 0
FROM gold.DimCustomer AS d JOIN stg.Customer AS s ON s.CustomerID = d.CustomerID
WHERE d.IsCurrent = 1 AND ISNULL(d.City, '') <> ISNULL(s.City, '');
INSERT INTO gold.DimCustomer (CustomerID, CustomerName, City, ValidFrom, ValidTo, IsCurrent)
SELECT s.CustomerID, s.CustomerName, s.City, SYSUTCDATETIME(), NULL, 1
FROM stg.Customer AS s
LEFT JOIN gold.DimCustomer AS d ON d.CustomerID = s.CustomerID AND d.IsCurrent = 1
WHERE d.CustomerID IS NULL;              -- new customer or just expired
UPDATE d SET d.CustomerName = s.CustomerName   -- type 1 attribute on all versions
FROM gold.DimCustomer AS d JOIN stg.Customer AS s ON s.CustomerID = d.CustomerID
WHERE d.CustomerName <> s.CustomerName;
COMMIT;   -- CustomerKey is BIGINT IDENTITY
  • Type 1 with MERGE (GA in warehouse): WHEN MATCHED AND (…changed…) THEN UPDATE, WHEN NOT MATCHED BY TARGET THEN INSERT, WHEN NOT MATCHED BY SOURCE THEN UPDATE SET IsActive = 0 (soft delete).
  • Type 4: rapidly changing attributes in a separate history table / mini-dimension.
  • Row hash: sha2(concat_ws('||', coalesce(City,''), …), 256): one comparison, NULL-safe.
  • Two-step alternative in a notebook: UPDATE to expire, then append: simpler, but not one atomic commit.
  • Rebuild from change events: ValidTo = lead(EffectiveDate) OVER (PARTITION BY CustomerID ORDER BY EffectiveDate); IsCurrent where lead is NULL.

Silver has one row per address change; gold needs one row per customer with the latest address. Which logic?

  • Rank per customer by change date desc, keep rank 1
  • GROUP BY CustomerID with MAX() on each column

ROW_NUMBER picks the latest complete row. MAX mixes rows, DISTINCT keeps all versions, dropDuplicates is arbitrary.

A dataflow appends to a lakehouse table; the source sometimes resends yesterday's rows. Result and fix?

  • Delta rejects duplicates automatically
  • Rows are overwritten: no fix needed
  • Duplicates accumulate: replace the window or MERGE on keys
  • Use a warehouse: it enforces primary keys

Neither Delta nor NOT ENFORCED warehouse keys reject duplicates. Make the load idempotent.

From silver to gold, step by step

Clean once in silver, then shape gold: dimensions first, facts with key lookups last.

🥉 Append every CRM row as received, including IsDeleted = 1 rows. Bronze = audit trail + rebuild source.

🥇 row_number() per CustomerID by change timestamp, keep 1. Required anyway: MERGE fails on duplicate source keys.

🧼 Cast types, UPPER(TRIM()) codes, default missing attributes to "Unknown", quarantine bad rows.

🔁 Deletes → expire or soft-delete; City change → SCD2 new version; new customers → insert; name fixes → type 1.

⭐ DimCustomer filtered to non-deleted members + Unknown row (-1). Flatten snowflakes. Tables, not views, for Direct Lake.

🔑 Swap business keys for surrogate keys; SCD2 version valid at the order date; misses → -1.

📐 Materialise Margin and bands in gold, split datetime into date key + time, drop unused columns, pre-aggregate to the needed grain.

INSERT INTO gold.FactSales (DateKey, CustomerKey, ProductKey, OrderNumber, SalesAmount)
SELECT CONVERT(int, CONVERT(char(8), s.OrderDate, 112)),
       COALESCE(c.CustomerKey, -1),
       COALESCE(p.ProductKey, -1),
       s.OrderNumber,
       s.Quantity * s.UnitPrice
FROM   silver.Sales AS s
LEFT JOIN gold.DimCustomer AS c
       ON c.CustomerID = s.CustomerID
      AND s.OrderDate >= c.ValidFrom AND s.OrderDate < COALESCE(c.ValidTo, '9999-12-31')
LEFT JOIN gold.DimProduct AS p
       ON p.ProductID = s.ProductID AND p.IsCurrent = 1;
  1. Date → integer key yyyymmdd.
  2. No match? Use the Unknown member -1 instead of losing the fact.
  3. Order number stays in the fact: a degenerate dimension.
  4. SCD2 lookup: the customer version valid on the order date.
  5. Type 1 product dimension: just the current row.
Deep dive: why materialise in gold
  • Row-level calculated values used on axes/slicers (Margin, profit bands) belong in gold Delta tables. Calculated columns aren't supported on Direct Lake on SQL endpoint tables and are preview-only on Direct Lake on OneLake.
  • Summary tables must exist in OneLake as Delta for Direct Lake. Header/line → one fact at line grain (allocate freight if needed).
  • Expose friendly names via views or the semantic model; hide technical keys.

  • Other operations: Pivot (with aggregation), Group by (basic/advanced incl. All rows), Remove duplicates, Keep/Remove rows, Replace values, Fill down/up, Split/Merge columns, Expand list → rows then record → columns (nested JSON), Change type, Remove other columns (renamed source column fails early), conditional/custom/index columns.
  • Join kinds in Merge: left/right/full outer, inner, left anti, right anti.
  • Staging: enable for shared expensive queries (uses SQL compute), disable for simple single-use queries. Fast copy: pipeline copy engine for large simple loads.
  • Destinations: Lakehouse, Warehouse, KQL DB, Azure SQL…; Append or Replace; auto/manual mapping. Public parameters (from pipelines) replace hard-coded server names across environments.
  • Incremental refresh in Dataflow Gen2 needs a Date/DateTime column and a fully folding query.
  • Non-foldable sorts/joins/buffering use lots of mashup memory. Apply cleansing once (silver); don't duplicate logic in dataflow and notebook.

A CRM flags deleted customers with IsDeleted = 1, sometimes resends rows, and needs SCD2 on City. Deleted customers must vanish from a Direct Lake report but bronze keeps everything. Outline?

Bronze append-only. Silver: dedupe with row_number, cast/standardise, MERGE (deleted → expire/soft-delete, City change → new version, new → insert, name → type 1). Gold DimCustomer as a table filtered to non-deleted + Unknown (-1). Facts look up the version valid at order date.

Exam traps

  • dropDuplicates(["key"]) keeps an arbitrary row; GROUP BY + MAX mixes rows.
  • Overwrite = SCD1 (history lost); append of a full extract = duplicates.
  • Type 3 keeps only ONE previous value.
  • Inner join silently drops facts with missing dimension keys: use left join + Unknown member.
  • Unpivot columns hard-codes names; Unpivot other columns doesn't.
  • CSV and Excel sources never fold.
  • Direct Lake needs tables: materialise views and calculated columns in gold.

Cheat sheet

⭐ Star schema

  • Declare grain first
  • Integer surrogate keys + business key
  • Unknown member -1
  • Conformed, role-playing, junk, bridge

🕰️ SCD

  • 0 keep · 1 overwrite
  • 2 new row: ValidFrom/To, IsCurrent
  • 3 PreviousX column · 6 = 2 + current
  • Row hash for change detection

🧼 Quality

  • ROW_NUMBER … = 1 / QUALIFY
  • COALESCE, TRY_CAST, quarantine
  • Idempotent: window replace or MERGE

🔗 Joins

  • Left: lookups · Anti: orphans
  • Semi: EXISTS · Full: reconcile
  • Check fan-out

🧪 Power Query

  • Merge = join, Append = union
  • Unpivot other columns
  • Keep folding; staging for shared queries
