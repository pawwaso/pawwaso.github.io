Query & analyze: SQL, visual queries, DAX queries

How to query data once it is in Fabric: the SQL query editor and the no-code visual query editor of warehouses and SQL analytics endpoints, the T-SQL analytics patterns the exam uses (window functions, CTEs, PIVOT, cross-database queries), DAX queries in DAX query view, profiling data, exploring in notebooks, and choosing between SQL, KQL, DAX and Spark SQL. Maps to Prepare data → Query and analyze data (select, filter and aggregate data by using the visual query editor, SQL, KQL and DAX).

The SQL query editor

  • Opened with New SQL query (or SQL templates for CREATE TABLE/VIEW/PROC…). IntelliSense, syntax highlighting, autosave; queries live in My queries or Shared queries (viewers and shared recipients cannot move queries to Shared queries).
  • Warehouse: full DDL, DML (INSERT/UPDATE/DELETE/MERGE), DCL (GRANT/DENY). SQL analytics endpoint: read-only on tables (data is written by Spark/Delta), but you can create views, functions, procedures and security (GRANT, RLS, CLS).
  • Results preview shows the first 10,000 rows; multiple result sets selectable from a dropdown.
  • From the results bar (select the SELECT statement first): Save as view, Save as table (runs CREATE TABLE AS SELECT), Open in Excel (downloads a workbook that runs the query live), Explore this data, Visualize results (not supported with ORDER BY), Copy.
  • Each Run is its own batch and session: BEGIN TRAN in one run and COMMIT in another fails; session SET options and sp_set_session_context don't persist; GO starts a new batch/session.
  • Cross-database queries with three-part names to other warehouses and SQL analytics endpoints in the same workspace (add them to the Explorer); data is read in place, nothing is copied.
  • Copilot: inline code completion, Explain (Ctrl+Alt+E) and Fix query quick actions, and a chat pane that writes T-SQL from natural language.
-- Join a warehouse fact to a lakehouse dimension without copying data
SELECT  c.Country,
        SUM(f.SalesAmount) AS Sales
FROM    dbo.FactSales            AS f          -- current warehouse (WH_Sales)
JOIN    LH_Gold.dbo.DimCustomer  AS c          -- SQL analytics endpoint of a lakehouse
        ON c.CustomerKey = f.CustomerKey
GROUP BY c.Country
ORDER BY Sales DESC;

In Warehouse1 you must join dbo.FactSales with the Customer table of Lakehouse1 (same workspace) in one T-SQL query, without copying data. What should you do?

  • Create a linked server to the lakehouse SQL analytics endpoint
  • Use OPENROWSET with the lakehouse connection string
  • Add Lakehouse1 to the Explorer and reference Lakehouse1.dbo.Customer
  • Load Customer into Warehouse1 with a Copy job first

Fabric supports cross-database queries with three-part names between warehouses and SQL analytics endpoints in the same workspace. Linked servers do not exist in Fabric warehouse, and copying violates the requirement.

The visual query editor (no code)

The visual query editor uses the Power Query diagram view: drag tables from the Explorer onto the canvas and apply steps (choose columns, filter, sort, group by, merge = join, append = union…). Behind the scenes the steps are translated (folded) into a single T-SQL SELECT.

  • Read-only: only DQL (SELECT); no DDL/DML.
  • Only foldable Power Query operations are supported — if a step can't be translated to SQL, a banner says the query is not supported as a warehouse view.
  • View SQL shows the generated T-SQL; Edit SQL script opens it in the SQL query editor. With merges, only the query with Enable load appears in the script.
  • Save as view (choose schema, review SQL) and Save as table (CTAS into a warehouse) persist the result.
  • Download Excel file and Visualize results from the results pane.
  • Cross-warehouse: drag tables from several added warehouses/endpoints and merge them.

A business analyst who doesn't know T-SQL must join two warehouse tables, filter the result and make it reusable for other analysts as a database object. What should the analyst use?

  • A Dataflow Gen2 writing to a new lakehouse
  • DAX query view with SUMMARIZECOLUMNS
  • The SQL query editor with CREATE VIEW
  • The visual query editor, then Save as view

The visual query editor is the no-code option and can save the result as a view (or as a table). The SQL editor needs T-SQL; DAX query view queries semantic models, not warehouses.

T-SQL analytics patterns for the exam

Aggregation, filtering groups, CASE

SELECT  d.CalendarYear,
        p.Category,
        COUNT(*)                         AS Orders,
        SUM(f.SalesAmount)               AS Sales,
        AVG(f.SalesAmount)               AS AvgOrder,
        SUM(CASE WHEN f.IsReturn = 1 THEN 1 ELSE 0 END) AS Returns
FROM    dbo.FactSales  AS f
JOIN    dbo.DimDate    AS d ON d.DateKey    = f.OrderDateKey
JOIN    dbo.DimProduct AS p ON p.ProductKey = f.ProductKey
WHERE   d.CalendarYear >= 2025                 -- filters rows (before grouping)
GROUP BY d.CalendarYear, p.Category
HAVING  SUM(f.SalesAmount) > 100000            -- filters groups (after grouping)
ORDER BY d.CalendarYear, Sales DESC;

Logical processing order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → TOP/OFFSET. That's why a column alias from SELECT can be used in ORDER BY but not in WHERE.

Window functions (OVER)

A window function computes a value per row over a set of related rows without collapsing them (unlike GROUP BY). PARTITION BY = the groups, ORDER BY = order inside each group, frame (ROWS BETWEEN …) = which rows count.

SELECT  CustomerKey, OrderDate, SalesAmount,
        ROW_NUMBER() OVER (PARTITION BY CustomerKey ORDER BY OrderDate DESC) AS rn,
        RANK()       OVER (ORDER BY SalesAmount DESC)                       AS rnk,
        DENSE_RANK() OVER (ORDER BY SalesAmount DESC)                       AS drnk,
        LAG(SalesAmount, 1, 0) OVER (PARTITION BY CustomerKey ORDER BY OrderDate) AS PrevAmount,
        LEAD(OrderDate)        OVER (PARTITION BY CustomerKey ORDER BY OrderDate) AS NextOrderDate,
        SUM(SalesAmount) OVER (PARTITION BY CustomerKey ORDER BY OrderDate
                               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,
        AVG(SalesAmount) OVER (ORDER BY OrderDate
                               ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS MovingAvg7,
        SalesAmount * 1.0 / SUM(SalesAmount) OVER (PARTITION BY CustomerKey)     AS ShareOfCustomer,
        NTILE(4) OVER (ORDER BY SalesAmount DESC)                                AS Quartile
FROM    dbo.FactSales;

  • ROW_NUMBER: unique sequence, ties broken arbitrarily (add a tie-breaker column to be deterministic). Use for dedup / "latest row per key".
  • RANK: ties share a rank, then gaps. DENSE_RANK: ties share a rank, no gaps.
  • LAG/LEAD(col, offset, default): previous/next row's value — period-over-period differences.
  • Running total: SUM() OVER (ORDER BY … ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). Without an explicit frame, an ORDER BY in the window defaults to RANGE … CURRENT ROW, which treats ties together (and is slower) — specify ROWS.
  • Window functions can't be used in WHERE; wrap them in a CTE or subquery and filter outside.

CTEs: latest row per key (dedup)

WITH ranked AS (
    SELECT  *,
            ROW_NUMBER() OVER (PARTITION BY CustomerID
                               ORDER BY ModifiedDate DESC, LoadId DESC) AS rn
    FROM    stg.CustomerChanges
)
SELECT  *
FROM    ranked
WHERE   rn = 1;          -- one row per customer: the most recent version

A CTE (WITH name AS (...)) is a named, query-scoped result set: improves readability, can be referenced several times in the statement, and can chain (WITH a AS (...), b AS (SELECT ... FROM a)).

A change-history table holds several rows per customer. You need exactly the latest row per customer with all its columns. Which construct is MOST appropriate?

  • SELECT DISTINCT *
  • A CTE with ROW_NUMBER() OVER (PARTITION BY CustomerID ORDER BY ModifiedDate DESC), filtered to rn = 1
  • GROUP BY CustomerID with MAX() on every column
  • TOP 1 without ORDER BY

Ranking within each customer and keeping row 1 is deterministic and keeps the row's columns consistent. MAX per column can mix values from different rows; DISTINCT doesn't remove versions; TOP 1 returns a single arbitrary row.

PIVOT, TOP, OFFSET/FETCH

-- Sales per category as columns per year
SELECT  CalendarYear, [Bikes], [Accessories], [Clothing]
FROM (
    SELECT d.CalendarYear, p.Category, f.SalesAmount
    FROM   dbo.FactSales f
    JOIN   dbo.DimDate d    ON d.DateKey = f.OrderDateKey
    JOIN   dbo.DimProduct p ON p.ProductKey = f.ProductKey
) AS src
PIVOT ( SUM(SalesAmount) FOR Category IN ([Bikes], [Accessories], [Clothing]) ) AS pvt;

-- Top 10 products, with ties
SELECT TOP (10) WITH TIES ProductKey, SUM(SalesAmount) AS Sales
FROM dbo.FactSales GROUP BY ProductKey ORDER BY Sales DESC;

-- Paging
SELECT ProductKey, ProductName FROM dbo.DimProduct
ORDER BY ProductName OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

UNPIVOT does the reverse (columns → rows). TOP without ORDER BY returns arbitrary rows.

Dates, strings, approximate counts

SELECT  DATEFROMPARTS(YEAR(OrderDate), MONTH(OrderDate), 1) AS MonthStart,
        EOMONTH(OrderDate)                                   AS MonthEnd,
        DATEADD(day, -30, CAST(GETDATE() AS date))           AS Minus30,
        DATEDIFF(day, OrderDate, ShipDate)                   AS DaysToShip,
        DATEPART(weekday, OrderDate)                         AS Weekday,
        DATENAME(month, OrderDate)                           AS MonthName,
        CONCAT(FirstName, ' ', LastName)                     AS FullName,
        UPPER(TRIM(City))                                    AS CityClean,
        COALESCE(Region, 'Unknown')                          AS RegionClean
FROM dbo.FactOrders;

-- comma-separated list per group
SELECT CustomerKey,
       STRING_AGG(ProductName, ', ') WITHIN GROUP (ORDER BY ProductName) AS Products
FROM   dbo.vOrderLines GROUP BY CustomerKey;

-- fast distinct count on huge tables (≈ 2% error, HyperLogLog)
SELECT APPROX_COUNT_DISTINCT(CustomerKey) AS ApproxCustomers FROM dbo.FactSales;
APPROX_COUNT_DISTINCT trades a small error for much less memory/time than COUNT(DISTINCT ...) — good for dashboards and exploration on billions of rows, not for financial reconciliation. KQL's equivalent is dcount().

  • Rank products by sales, no gaps after ties
  • Total sales per category, only categories above 1 M
  • Number of orders per year
  • One column per category, one row per year
  • Comma-separated list of products per customer

DAX queries and DAX query view

DAX formulas define measures/columns; DAX queries return a table from a semantic model (they are what every Power BI visual sends). A query has an optional DEFINE block and one or more EVALUATE statements, each optionally followed by ORDER BY (and START AT).

DEFINE
    VAR _Year = 2026
    MEASURE Sales[Total Sales]  = SUM ( Sales[SalesAmount] )
    MEASURE Sales[Margin %]     =
        DIVIDE ( [Total Sales] - SUM ( Sales[TotalCost] ), [Total Sales] )
EVALUATE
    SUMMARIZECOLUMNS (
        'Date'[Year],
        Product[Category],
        TREATAS ( { _Year }, 'Date'[Year] ),          -- filter argument
        "Sales",    [Total Sales],
        "Margin %", [Margin %]
    )
ORDER BY [Sales] DESC

DAX query view features

  • Where: Power BI Desktop (left rail icon) and in the service/Fabric portal via Write DAX queries on a semantic model. Works for Import, DirectQuery, Direct Lake and composite models.
  • Quick queries (Data pane context menu): Show top 100 rows (SELECTCOLUMNS + TOPN), Show column statistics (MIN/MAX/AVERAGE/COUNT/distinct…), Show data preview of a column (DISTINCT), Evaluate a measure (SUMMARIZECOLUMNS), Define and evaluate, Define with references and evaluate, Define all measures in this table / in the model, Define new measure.
  • Update model with changes (command bar) adds or overwrites model measures from the query's DEFINE MEASURE blocks; per measure, CodeLens shows Update model: Add new measure or Update model: Overwrite measure. /// comments above a MEASURE become its description.
  • Light-bulb quick actions Define / Define with references on a measure in EVALUATE (only when the tab has no DEFINE yet).
  • Performance Analyzer → Run in DAX query view to open the exact query a visual sent.
  • Query tabs are saved in the .pbix; in a PBIP project each tab is a .dax file in the DAXQueries folder. In the web, tabs are discarded on close.
  • Limits: 15 MB / 1,000,000 values per query in Desktop; web: max 99,999 rows, requires write permission on the model and the workspace setting Users can edit data models in the Power BI service. Viewers with Build permission use Desktop with a live connection instead.
  • Live connection in Desktop: model measures can't be edited, quick queries are limited to Evaluate, report measures must be defined in DEFINE to run and can't be pushed with Update model.
  • Copilot in DAX query view writes and explains DAX queries from natural language ("top 10 products by margin in 2026") and can explain query results; review before Update model.
  1. Right-click the measure → Quick queries → Evaluate
  2. Select the measure in the query and choose Define with references
  3. Edit the formula in the DEFINE MEASURE block
  4. Run the query and check the results by the group-by columns
  5. Click the CodeLens "Update model: Overwrite measure"

You edit Model1 in Power BI Desktop. You wrote a new measure in a DEFINE MEASURE block, validated it with EVALUATE SUMMARIZECOLUMNS, and now want it saved in the model. What should you do?

  • Select Update model with changes (or the CodeLens "Add new measure")
  • Copy the query into Performance Analyzer
  • Save the file; DEFINE MEASURE blocks are added to the model automatically
  • Publish the query tab to the service

DEFINE MEASURE creates query-scoped measures only. Update model with changes / CodeLens writes them into the model. Saving keeps the query tab, not a model measure.

A workspace Viewer with Build permission on a semantic model wants to run DAX queries against it. The Write DAX queries option in the service is unavailable to them. What should they do?

  • Ask for the Contributor role only to run queries
  • Use the visual query editor of the model
  • Live connect to the model from Power BI Desktop and use DAX query view
  • Use the SQL analytics endpoint of the model

Writing DAX queries in the web requires write permission on the model. With Build permission a user can live connect from Desktop and run queries there. Semantic models have neither a visual query editor nor a SQL endpoint.

Profiling data

Power Query (Dataflow Gen2, Desktop, semantic model web editing)

  • Column quality: % Valid, Error, Empty under each header.
  • Column distribution: mini histogram with distinct and unique counts (distinct = number of different values; unique = values that appear exactly once).
  • Column profile: pane with statistics (count, error, empty, distinct, unique, min, max, average, std dev, NaN, zero…) and the value distribution for the selected column.
  • By default profiling is based on the top 1,000 rows; switch to Column profiling based on entire data set in the status bar (slower).
  • Enable the three options on the View ribbon. Use Keep/Remove errors, Replace values, Change type to fix what you find.

Column quality shows CustomerEmail as 100% valid, but you suspect errors further down the 2-million-row table. Why might the profile miss them, and what should you do?

  • Column quality ignores text columns; use column distribution
  • Profiling uses the top 1,000 rows by default; switch to profiling the entire data set
  • Errors are only shown after the dataflow is published
  • Errors appear only in the Diagram view

Power Query profiles the first 1,000 rows unless you choose "Column profiling based on entire data set" in the status bar.

Scenario. A retail company has: a warehouse WH_Sales (facts), a lakehouse LH_Ref (product master as Delta), an eventhouse with web clickstream, and a certified semantic model Sales Model. Requests: (a) a marketing analyst with no SQL skills wants a reusable joined "orders with product category" object; (b) finance wants to check why a Gross Margin % measure shows 41% for Bikes; (c) the web team wants page views per minute for the last 2 hours; (d) a data scientist needs the distribution of order values across 4 billion rows, and to reuse the model's Total Sales measure in Python. Which tool for each?

  • (a) Visual query editor in WH_Sales: drag FactSales and the lakehouse product table (added to the Explorer — cross-database), merge, filter, Save as view.
  • (b) DAX query view: Quick query Define with references and evaluate on the measure, add Product[Category] to SUMMARIZECOLUMNS, inspect intermediate measures; or Performance Analyzer → Run in DAX query view for the exact visual query.
  • (c) KQL in a queryset: Clicks | where Timestamp > ago(2h) | summarize Views = count() by bin(Timestamp, 1m) | render timechart.
  • (d) Notebook: df.summary() / approx_count_distinct in Spark for the distribution; semantic link evaluate_dax to reuse Total Sales.

Which T-SQL ranking function returns 1, 2, 2, 3 for the sales values 500, 400, 400, 300 ordered descending?

  • ROW_NUMBER()
  • RANK()
  • NTILE(3)
  • DENSE_RANK()

DENSE_RANK gives ties the same rank without gaps. RANK returns 1, 2, 2, 4; ROW_NUMBER returns 1, 2, 3, 4.

In the SQL query editor you run BEGIN TRAN; UPDATE ... and then, in a second run, COMMIT. The commit fails. Why?

  • Fabric warehouses do not support transactions
  • UPDATE statements are auto-committed and cannot be in a transaction
  • Each Run is a separate batch and session, so the second run has no open transaction
  • COMMIT requires the Admin workspace role

Fabric warehouses support transactions, but the portal editor runs each execution in its own session. Put BEGIN TRAN ... COMMIT in one batch (or use SSMS/VS Code).

Key takeaways & exam tips

  • SQL query editor: full T-SQL in a warehouse (DDL/DML/DCL); read-only tables in a SQL analytics endpoint (but views/functions/security allowed). Results preview = first 10,000 rows. Save as view / Save as table (CTAS) / Open in Excel / Visualize results. Each Run = new session.
  • Cross-database queries: three-part names (Lakehouse1.dbo.Customer) within the workspace, no copy, no linked servers.
  • Visual query editor: no-code Power Query diagram that generates one SELECT; only foldable steps; read-only; View SQL; Save as view or table.
  • Window functions: ROW_NUMBER (dedup / latest row with a CTE), RANK (gaps), DENSE_RANK (no gaps), LAG/LEAD (previous/next), SUM OVER with ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (running total). Filter window results in an outer query.
  • HAVING filters groups; WHERE filters rows. APPROX_COUNT_DISTINCT = fast estimated distinct count. STRING_AGG concatenates per group. PIVOT turns rows into columns.
  • DAX queries: EVALUATE required, DEFINE (MEASURE/VAR/TABLE/COLUMN) optional, ORDER BY optional. SUMMARIZECOLUMNS = group by; TOPN needs ORDER BY for a sorted output; CALCULATETABLE applies filters.
  • DAX query view: quick queries, CodeLens / Update model with changes to save DEFINE MEASUREs, Performance Analyzer → Run in DAX query view, saved as .dax in PBIP. Web: needs write permission; viewers with Build use Desktop live connect.
  • Choose T-SQL for relational/warehouse, KQL for streaming/time-series/logs, DAX for the semantic model's logic, Spark for big files, JSON and data science.
  • Power Query profiling = column quality / distribution / profile, top 1,000 rows by default. In notebooks: describe(), summary(), display(df, summary=True), Data Wrangler. Semantic link evaluates DAX from Python.
