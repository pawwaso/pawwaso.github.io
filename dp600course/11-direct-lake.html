Direct Lake in depth

How Direct Lake loads Delta tables into VertiPaq on demand, the two flavours (Direct Lake on OneLake vs Direct Lake on SQL endpoint), framing and automatic updates, DirectQuery fallback, SKU guardrails, file layout, security and monitoring. Maps to the exam skills Implement and manage semantic models → Choose a storage mode / Configure Direct Lake, including default fallback and refresh behavior and Optimize enterprise-scale semantic models.

The big picture: why Direct Lake exists

Before Fabric you had two classic choices for a Power BI table:

  • Import – data is copied into the VertiPaq in-memory column store during a scheduled refresh. Very fast queries, but refreshes cost time, memory and capacity, and data is only as fresh as the last refresh.
  • DirectQuery – no copy; every visual query is translated (e.g. to T-SQL) and sent to the source. Always current, but typically much slower and it loads the source.

Direct Lake is a third table storage mode available only on a Fabric capacity. Because Fabric stores lakehouse and warehouse tables as Delta tables (Parquet column files + a Delta transaction log) in OneLake, and Parquet is also a column store, the semantic model can read the column data directly from OneLake into VertiPaq memory – no Power Query, no scheduled data copy. Queries are then answered by the same VertiPaq engine as Import mode.

Mental model: Direct Lake = Import-mode query speed + DirectQuery-like freshness, with the data preparation moved upstream into OneLake. All shaping (joins, derived columns, aggregations) happens in Spark, T-SQL, Dataflow Gen2 or pipelines – not in Power Query inside the model.

How Direct Lake works: transcoding, residency and temperature

Column loading (transcoding)

Nothing is loaded when the model is created or framed. When a DAX (or MDX) query arrives, the engine determines which columns it needs – columns used directly by the query plus columns needed by relationships and measures. Any of those columns that aren't already in memory are loaded completely (the whole column, across all row groups of the framed version) from OneLake. This on-demand load is called transcoding: Parquet's per-row-group local dictionaries are merged into one global VertiPaq dictionary, and Parquet column chunks are remapped into VertiPaq column segments.

  • Once loaded, a column is resident. Later queries that only touch resident columns need no OneLake reads.
  • Direct Lake loads whole columns, not row ranges. It does not use Delta/Parquet statistics for file or row-group skipping when loading.
  • For queries across tables, join indexes are built for relationships (requires dictionaries of key columns and segments of the one-side key column).
  • If the Delta table uses deletion vectors, they are loaded so deleted rows are excluded.

Eviction (paging out)

A resident column can be removed from memory when:

  • the model/table is reframed after the underlying Delta table changed (affected segments are dropped);
  • no query has used the column for some time (it "cools down");
  • the capacity is under memory pressure (other models, refreshes, concurrent operations).

The SKU's Max memory value is the upper limit for how much data a Direct Lake model can page into memory. It is not a guardrail that triggers fallback – exceeding it means columns are paged in and out repeatedly, which hurts performance.

Temperature and the cold / semiwarm / warm / hot states

A report on a Direct Lake model is slow only for the first user each morning; later queries are fast. Nothing falls back to DirectQuery. What is the most likely explanation?

  • The model is refreshed with a full data copy every morning
  • Fallback to DirectQuery happens silently for the first query
  • Columns must be transcoded (loaded) from OneLake into memory on first use after framing/eviction – a cold-cache effect
  • V-Order is applied at query time on the first request

Direct Lake loads columns on demand. After overnight ETL + reframing, or after columns were evicted, the first query pays the transcoding cost (cold/semiwarm state). Framing never copies data, fallback was ruled out, and V-Order is applied at write time, not query time. Mitigations: V-Order, fewer/larger row groups, fewer columns, non-destructive (append) loads, or a warm-up query after the reframe.

Direct Lake on OneLake vs Direct Lake on SQL endpoint

Direct Lake now has two variants. You must be able to choose between them – this is a favourite exam topic.

  • Direct Lake on OneLake – the model's shared expression uses AzureStorage.DataLake(...) pointing straight at the OneLake location. Schema discovery, security checks and data loading all go through OneLake APIs. Can combine tables from one or more Fabric items. Never falls back to DirectQuery (effectively always DirectLakeOnly). Integrates with OneLake security. Recommended option for new models.
  • Direct Lake on SQL (analytics endpoint) – the original variant. The expression uses Sql.Database(...) (or OneLake.SqlAnalytics()) pointing at the SQL analytics endpoint of a single lakehouse/warehouse. The endpoint is used for table/view discovery and permission checks; column data is still read directly from OneLake. Can fall back to DirectQuery through the SQL endpoint, controlled by the Direct Lake behavior property.

DirectQuery fallback and the Direct Lake behavior property

Only Direct Lake on SQL models can fall back. When a query can't be answered in Direct Lake mode, it's sent as DirectQuery (T-SQL) to the SQL analytics endpoint of the lakehouse or warehouse. Fallback queries always return the latest data (they aren't bound to the framed version) but are usually slower. Even when no fallback occurs, enabling fallback forces hybrid query plans that cost a little performance – another reason Microsoft recommends avoiding it.

Causes of fallback (queries stay in Direct Lake only if ALL are true)

  1. No referenced table has SQL row-level security (security policy) on the SQL analytics endpoint.
  2. No referenced table has dynamic data masking (DDM) on the endpoint.
  3. No referenced table has SQL object-level security defined at the endpoint.
  4. No table is based on a non-materialized SQL view.
  5. No table exceeds the guardrails of the SKU (Parquet files, row groups, rows per table).
  6. The model was framed (refreshed) after the Delta tables were created or modified (an unframed/unprocessed table falls back).

Learn also lists capacity memory pressure and transient errors as reasons. Note the distinction: SQL endpoint RLS (and views) cause fallback, whereas a query touching a column/table blocked by SQL endpoint OLS/CLS returns an error.

DirectLakeBehavior values

ValueBehavior when Direct Lake conditions aren't metTypical use
Automatic (default)Silently falls back to DirectQuery; reports keep working, possibly slowerProduction, when availability matters more than speed
DirectLakeOnlyQuery fails with an error – no fallbackDevelopment/testing to surface fallback causes; production when you'd rather fail than be slow

Set it in Model view → Properties of the semantic model → Direct Lake behavior (Desktop live edit or web modeling), or programmatically via TOM/TMSL:

// C# / TOM: disable fallback
database.Model.DirectLakeBehavior = DirectLakeBehavior.DirectLakeOnly;
database.Model.SaveChanges();

The property is meaningful only for Direct Lake on SQL – Direct Lake on OneLake always behaves like DirectLakeOnly.

Model1 uses Direct Lake on SQL endpoint with the default Direct Lake behavior and SSO. The SQL analytics endpoint of the lakehouse has a security policy (RLS) on the Sales table. A restricted user opens a report. What happens?

  • The query fails because Direct Lake doesn't support RLS
  • The query falls back to DirectQuery and the endpoint filters rows by the user's identity
  • The query runs in Direct Lake mode and ignores the SQL RLS
  • The semantic model automatically converts the SQL RLS into model roles

With Direct Lake on SQL and Automatic behavior, SQL endpoint RLS causes fallback to DirectQuery so the SQL engine can enforce the policy for the SSO user. With DirectLakeOnly the query would fail. With Direct Lake on OneLake, SQL-based RLS isn't applied at all (OneLake security is used instead).

During development you want any table that cannot be served from memory to raise an error so you can fix the design. The model is Direct Lake on SQL endpoint. What should you configure?

  • Turn off "Keep your Direct Lake data up to date"
  • Set Direct Lake behavior to Automatic
  • Set Direct Lake behavior to DirectQueryOnly
  • Set Direct Lake behavior to DirectLakeOnly

DirectLakeOnly disables fallback; anything that would have fallen back produces an error, which surfaces views, SQL RLS or guardrail issues during testing. Automatic hides the problem; DirectQueryOnly forces DirectQuery for every query; the automatic-updates setting controls reframing, not fallback.

Framing, refresh and automatic updates

Framing

A Delta table is a sequence of versions; each commit in the Delta log adds/removes Parquet files. Framing is what a refresh of a Direct Lake model does: it reads the Delta log of each table and pins the model to the latest committed version (the list of Parquet files). It copies no data and usually takes seconds. From then on, all transcoding loads data as of that framed version – later commits are invisible until the next framing.

  • Incremental framing: the engine compares the new version with the previous one and drops only the column segments belonging to removed row groups; dictionaries are usually kept and extended. Append-only loads therefore keep the model semiwarm.
  • Destructive patterns (overwrite mode, deletes/updates that rewrite most files, OPTIMIZE rewrites) invalidate segments → the next queries are cold.
  • Because a framed model references specific Parquet files, VACUUM must not remove files of the framed version before the model is reframed – otherwise queries error with missing files.
  • Framing can fail if a table exceeds guardrails.

Automatic updates – "Keep your Direct Lake data up to date"

Model setting in Semantic model settings → Refresh. Enabled by default. When on, the model reframes automatically whenever it detects changes in the underlying Delta tables (scoped to the changed tables). Recommended for small/medium models and low-latency needs.

Disable it when users must not see partially loaded data – e.g. a multi-step ETL that loads facts before dimensions, or validation steps that must pass first. Then reframe explicitly when the load is complete:

  • manual Refresh in the Fabric portal, or a scheduled refresh;
  • Semantic model refresh activity at the end of a Fabric pipeline (runs only after load activities succeed);
  • Power BI REST API (enhanced refresh), TOM/TMSL via XMLA, or sempy.fabric.refresh_dataset() from a notebook.

If a refresh hits a non-recoverable error, Power BI suspends automatic updates; they resume after a successful on-demand refresh.

  1. Disable "Keep your Direct Lake data up to date" on the semantic model (one-time setup)
  2. Pipeline loads and validates the dimension and fact Delta tables
  3. Pipeline runs the Semantic model refresh activity to reframe the model
  4. Optionally run a warm-up DAX query against key measures
  5. Run table maintenance (OPTIMIZE/VACUUM) in a maintenance window, keeping files the framed version needs, then reframe

Scenario. A retail company loads its gold lakehouse every night in three notebooks: DimProduct, DimStore, then FactSales (90 minutes). Analysts in Asia use the Direct Lake report during that window and complain that sales sometimes appear under "(Blank)" products and totals jump around. Automatic updates are on. What do you change?

With automatic updates on, the model reframes as soon as each Delta table changes, so users see a mix of new dimensions and old/partial facts. Disable Keep your Direct Lake data up to date, orchestrate the three notebooks in a pipeline, and add a Semantic model refresh activity after all of them succeed. The model stays framed on the previous consistent version during the load and switches atomically in seconds. Also make sure VACUUM retention keeps the previously framed files until the reframe.

Refresh in Power BI Desktop live edit vs scheduled refresh

In Desktop live edit, the Refresh button performs a schema refresh (detects new/changed columns in the source) and reframes. A scheduled refresh in the service only reframes – no schema sync. Renaming a source column removes it from the model on the next schema refresh unless you update its SourceLineageTag in TMDL view.

V-Order defaults in 2026

Fabric Spark uses resource profiles. New workspaces default to the writeHeavy profile, in which V-Order is disabled to maximise ingestion throughput. For gold tables served to Direct Lake, enable V-Order (session config spark.sql.parquet.vorder.default=true, a read-heavy resource profile such as readHeavyForSpark, the table property, or the writer option parquet.vorder.enabled) and rewrite existing files with OPTIMIZE ... VORDER. Disabling V-Order is defensible for write-heavy staging tables that are rarely read.

-- Spark SQL in a Fabric notebook
SET spark.sql.parquet.vorder.default = true;           -- V-Order for writes in this session

ALTER TABLE gold.fact_sales
  SET TBLPROPERTIES ('delta.parquet.vorder.enabled' = 'true');   -- table-level property

OPTIMIZE gold.fact_sales VORDER;                      -- compact small files and apply V-Order
VACUUM gold.fact_sales RETAIN 168 HOURS;              -- remove unreferenced files older than 7 days

No-code alternative: Lakehouse explorer → table → Maintenance runs OPTIMIZE (optionally with V-Order) and VACUUM with a retention threshold. Data engineers can also use optimize write to produce well-sized files at write time.

OPTIMIZE replaces Parquet files, so the affected column segments become invalid after the next reframe – a short-term cold penalty for a long-term gain. Schedule compaction in quiet periods (weekends/month end) unless small files accumulate quickly (streaming), in which case optimize daily to stay within guardrails.

A workspace created in 2026 writes gold tables with notebooks using default Spark settings. A Direct Lake model on these tables is slower than expected; the tables are written once a day and read constantly. What should you do?

  • Switch the model to DirectQuery
  • Partition the fact table by OrderDate at day level
  • Enable V-Order for the gold tables (e.g. read-heavy profile or table property) and rewrite the files with OPTIMIZE
  • Disable automatic updates

New workspaces default to the write-optimized profile with V-Order off. V-Order applies VertiPaq-friendly sorting and compression at write time and helps read-heavy Direct Lake tables. Day-level partitioning creates thousands of small files (bad); DirectQuery is slower; automatic updates are about freshness.

Creating and editing Direct Lake models

Ways to create

  1. From a lakehouse/warehouse in the Fabric portal: open the item (or its SQL analytics endpoint) → New semantic model → name, workspace, select tables. Remember: Fabric no longer creates automatic default semantic models – you create models explicitly, which gives full control over relationships, measures and security.
  2. Power BI Desktop: OneLake catalog → select lakehouse/warehouse → Connect → choose name, workspace and tables. Creates a Direct Lake on OneLake model in the workspace. Add tables from other items the same way.
  3. Web modeling (open data model in the browser): edit relationships, measures, RLS, calculation groups; Edit tables; add Import tables (DL on OneLake) via Power Query.
  4. XMLA / code: Tabular Editor, SSMS, notebooks with semantic link labs (e.g. generate a Direct Lake model from lakehouse tables).

Live editing in Power BI Desktop

  • The model lives in the workspace; Desktop edits it live. There's no Publish and no Save – every change is applied immediately. There is no undo; version history creates a version at the start of each live-edit session.
  • Report view is removed while live editing (unless using PBIP); build reports in a separate Desktop file with a live connection.
  • TMDL view and DAX query view are available.
  • To keep metadata in source control: File → Export → Power BI Project (PBIP), then deploy via Git integration / item APIs (PBIP can't be published from Desktop).
  • Requirements: XMLA read-write enabled on the capacity, Write permission on the model, at least Viewer on the lakehouse, not a free license. RLS roles can't be validated from Desktop – test in the service.

Security: identities, permissions and OneLake security

SSO vs fixed identity

Direct Lake checks data access for the effective identity:

  • SSO (Microsoft Entra ID) – default. The identity of the user running the report is checked. Every report user needs read access to the data (DL on SQL: Read on the item + SELECT on tables; DL on OneLake: Read + ReadAll or a OneLake security role).
  • Fixed identity – bind the model to a shareable cloud connection with SSO disabled, authenticated as OAuth 2.0 account, service principal or workspace identity (key/SAS methods aren't supported). The fixed identity's permissions determine what is read; users need only Read on the model/report and no permission on the lakehouse. Data restrictions are then implemented with semantic model RLS/OLS.
  • A connection can have both: SSO for queries and the fixed identity for framing/transcoding at refresh time.

Independently of the effective identity, the semantic model owner must have read access to the source tables, because framing checks the owner's permissions; otherwise refresh fails with "…ensure that the owner of this semantic model does have read access to these tables".

RequirementDesign
Users see only permitted rows in reports and must NOT query the lakehouse/endpoint directlyFixed identity cloud connection (SSO off) + semantic model RLS; grant users nothing on the lakehouse
Same row rules everywhere (Spark, SQL endpoint, Direct Lake)OneLake security roles + Direct Lake on OneLake with SSO
Security already defined as SQL endpoint RLS and must be reusedDirect Lake on SQL with SSO (accept DirectQuery fallback)

Semantic model RLS/OLS is not enforced for users with Write permission on the model – i.e. workspace Admin, Member and Contributor. Test roles with Viewer-level identities. Also: model RLS applies only inside the model – if users also have SQL or OneLake access, they can bypass it, which is why Microsoft "strongly recommends" a fixed identity when using model RLS.

OneLake security interaction

  • With Direct Lake on OneLake and OneLake security on, the effective identity's OneLake roles are resolved and their RLS/OLS applied. If a user is in several OneLake roles and model roles, OneLake roles are unioned, then intersected with the model roles.
  • OneLake security applies to Viewers (and users with explicit Read); Contributors and above have full access.
  • Limitations: no backup for models relying on OneLake security; bidirectional relationships not supported when the source uses OneLake security RLS; refresh models after OneLake security changes.
  • If a lakehouse's SQL analytics endpoint is switched to user identity (SSO) mode, OneLake roles become SQL granular rules and Direct Lake on SQL falls back to DirectQuery 100% of the time – another argument for Direct Lake on OneLake.

Report consumers must see only their region's rows in a Direct Lake model and must not be able to query the lakehouse. Data engineers keep full access. What should you do?

  • Keep SSO, grant consumers ReadAll on the lakehouse and add model RLS
  • Define RLS on the SQL analytics endpoint and keep SSO
  • Bind the model to a cloud connection with a fixed identity (SSO disabled), grant that identity read access, add model RLS roles for consumers and give consumers no lakehouse permissions
  • Give consumers the Contributor role so they can use the model

Fixed identity reads the data on the users' behalf, so consumers need no lakehouse permissions, and model RLS filters their rows. SSO would require consumers to have data access (letting them bypass model RLS). SQL RLS causes fallback; Contributors bypass model RLS entirely.

  2. Materialize calculated columns and calculated tables into the lakehouse (Direct Lake on SQL can't host them; DL on OneLake supports them only in preview).
  3.   5. Check guardrails for your SKU, enable V-Order, decide on automatic updates and fallback behavior, configure the connection (SSO vs fixed identity).

Model1 is Direct Lake on SQL endpoint. A table is based on the view vw_Sales in a warehouse. Reports are slow and Profiler shows DirectQuery events. You need the table served in Direct Lake mode. What should you do?

  • Set Direct Lake behavior to DirectLakeOnly
  • Enable V-Order on the warehouse
  • Turn on automatic updates
  • Materialize the view logic into a Delta table (e.g. CREATE TABLE AS SELECT in the warehouse) and point the model table at it

Direct Lake reads Delta tables, not SQL views – a view-based table always falls back. DirectLakeOnly would just make the queries fail. V-Order and automatic updates don't affect view handling.

Scenario. You must design a Direct Lake model for a company on F64. Requirements: (1) facts in Lakehouse_Sales, the product dimension in Warehouse_MDM; (2) a small budget table maintained in an Excel file on SharePoint; (3) the security team defined row filters once in OneLake security and wants them enforced everywhere; (4) reports must never silently become slow. Which Direct Lake flavour and settings?

Direct Lake on OneLake. (1) It can combine tables from multiple Fabric items. (2) DL on OneLake supports composite models, so the budget can be an Import table added via web modeling (Power Query). (3) DL on OneLake enforces OneLake security roles for the SSO user (keep SSO so the user's roles apply; consumers need Read + a OneLake role). (4) DL on OneLake never falls back – problems surface as errors rather than slow DirectQuery. Also check F64 guardrails (5,000 files/row groups, 1.5 billion rows per table) and enable V-Order on the gold tables.

Key takeaways & exam tips

  • Direct Lake = VertiPaq queries over Delta tables in OneLake; Fabric capacity only; no Power Query for DL tables; prepare data upstream.
  • Transcoding loads whole columns on first use; columns get evicted on reframe, inactivity or memory pressure. States: cold → semiwarm → warm → hot.
  • Framing = metadata-only refresh that pins the latest Delta version; automatic updates ("Keep your Direct Lake data up to date") are on by default; disable them for multi-step ETL and reframe from the pipeline.
  • Direct Lake on OneLake: multiple sources, composite with Import, OneLake security, calculated columns/tables in preview, no fallback – guardrail breaches make refresh fail. Desktop creates this type.
  • Direct Lake on SQL: single source, SQL endpoint permissions, views allowed but always fall back; fallback causes: SQL views, SQL RLS/DDM/OLS, guardrails exceeded, unframed tables. DirectLakeBehavior: Automatic (default) / DirectLakeOnly / DirectQueryOnly.
  • Guardrails: F2–F32 → 1,000 files, 1,000 row groups, 300 M rows; F64 → 5,000 / 5,000 / 1.5 B; F128 → 3 B; F256 → 6 B; F512 → 10,000 / 12 B; F1024+ → 24 B. Max memory is not a guardrail.
  • Performance: V-Order on read-heavy gold tables (off by default in new workspaces' writeHeavy profile), large row groups (1–16 M rows), few files, OPTIMIZE/VACUUM, append-only loads, low-cardinality partitions, only needed columns.
  • Can't do on DL tables: calculated columns (DL on SQL), user-defined aggregations, incremental refresh/hybrid partitions, gateways, complex/binary/GUID types → materialize in the lakehouse.
  • Security: SSO default; fixed identity + model RLS when users must not access the lakehouse; model owner needs read access for framing; Admin/Member/Contributor bypass model RLS.
  • Detect fallback: Performance analyzer "Direct query", Profiler DirectQuery_Begin/End, TABLETRAITS(); test with DirectLakeOnly.
