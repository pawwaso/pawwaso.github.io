How a query is answered

Nothing is loaded until a query needs it; then whole columns move into memory and stay while they are "hot".

📌 Refresh reads the Delta log and pins version N. No data loaded yet; the model is cold.

📊 A visual sends DAX. The engine lists the columns it needs: queried columns + relationship keys + columns used by measures.

🔄 Missing columns are loaded completely (all row groups of version N). Parquet dictionaries merge into one VertiPaq dictionary.

  • No file / row-group skipping by statistics.
  • Deletion vectors are applied.

⚡ Columns are now resident. Later queries touching only resident columns need no OneLake reads: Import-like speed.

🧹 Columns are paged out when: the table is reframed after a change, they are unused for a while, or the capacity is under memory pressure.

🧊 Coldnothing in memory · first-query penalty
🌤 Semiwarmonly changed row groups reload
☀️ Warmall needed columns resident
🔥 Hot+ VertiScan cache hits
Deep dive: inspect residency and temperature

Each column has a temperature that rises with use and decays over time; cold columns are evicted first. Query it with the DMV DISCOVER_STORAGE_TABLE_COLUMN_SEGMENTS or:

EVALUATE
SELECTCOLUMNS ( INFO.STORAGETABLECOLUMNSEGMENTS (),
    "Table", [TABLE_ID], "Column", [COLUMN_ID],
    "Resident", [ISRESIDENT], "Temperature", [TEMPERATURE],
    "LastAccessed", [LAST_ACCESSED] )

Join indexes are built for relationships (key column dictionaries + one-side key segments). Cold = after model load, destructive overwrite or processClear.

A Direct Lake report is slow only for the first user each morning; later queries are fast. No DirectQuery fallback occurs. Why?

  • The model copies all data every morning
  • Fallback happens silently for the first query
  • Columns must be transcoded into memory after framing/eviction (cold cache)
  • V-Order is applied at query time

First query after reframe/eviction pays the transcoding cost. Mitigate with V-Order, larger row groups, fewer columns, append loads or a warm-up query.

Two flavours: on OneLake vs on SQL endpoint

On OneLake reads straight from OneLake and never falls back; on SQL endpoint uses the SQL endpoint for discovery and permissions and can fall back.

Where to set it

Model view → semantic model properties → Direct Lake behavior (Desktop live edit or web modeling), or TOM: database.Model.DirectLakeBehavior = DirectLakeBehavior.DirectLakeOnly; SaveChanges();. Meaningful only on SQL endpoint; OneLake always acts like DirectLakeOnly.

Direct Lake on SQL endpoint, default behavior, SSO. The SQL endpoint has RLS on Sales. A restricted user opens a report. What happens?

  • The query fails: Direct Lake doesn't support RLS
  • It falls back to DirectQuery and the endpoint filters rows for the user
  • It runs in Direct Lake and ignores SQL RLS
  • SQL RLS is converted into model roles

Automatic → fallback so the SQL engine enforces RLS. DirectLakeOnly would error.

F8, on SQL endpoint. FactSales has 420 M rows in 1,600 small files; traces show DirectQuery events. Cause?

  • F8 guardrails exceeded (300 M rows, 1,000 files), so queries fall back
  • F8 doesn't support Direct Lake
  • Max memory 3 GB exceeded, which forces fallback
  • Automatic updates were disabled

Fix: OPTIMIZE, fewer rows, or F64 (5,000 files / 1.5 B rows). Max memory only causes paging.

  • Table based on a SQL view (on SQL)
  • SQL endpoint RLS on a table
  • Rows over SKU limit (on SQL)
  • Dynamic data masking on the endpoint
  • File guardrail exceeded (on OneLake)
  • DirectLakeOnly and a view is used
  • Column denied by SQL endpoint CLS
  • Paged data exceeds Max memory
  • Columns evicted after a reframe

Framing and automatic updates

The model sees exactly one Delta version, the one it was last framed on.

Framing timeline

Nightly ETL writes DimProduct, then FactSales (each = new Delta version). Try one write with automatic updates on, then off.

What does framing copy?
Nothing. It reads the Delta log and pins a list of Parquet files. Seconds.
Append vs overwrite: effect on cache?
Append keeps the model semiwarm (incremental framing). Overwrite / OPTIMIZE rewrites files → cold.
Automatic updates: default?
On. Reframes when Delta tables change (scoped to changed tables).
Refresh hits a non-recoverable error?
Automatic updates are suspended until a successful on-demand refresh.
  1. Disable "Keep your Direct Lake data up to date" (one-time)
  2. Pipeline loads and validates dimension and fact tables
  3. Semantic model refresh activity reframes the model
  4. Optional warm-up DAX query on key measures
  5. OPTIMIZE / VACUUM in a maintenance window, then reframe
Ways to reframe and Desktop live edit
  • Manual or scheduled refresh; pipeline Semantic model refresh activity; enhanced refresh REST API; TOM/TMSL via XMLA; sempy.fabric.refresh_dataset().
  • Desktop live edit Refresh = schema refresh (new/changed columns) + reframe. Scheduled refresh only reframes. Renamed source columns drop out unless you fix SourceLineageTag in TMDL.
  • Live edit: no Publish, no Save, no undo (version history per session); report view hidden; export to PBIP for Git. Needs XMLA read-write, Write on model, Viewer on lakehouse.

A 2026 workspace writes gold tables with default Spark settings once a day; Direct Lake reports read them constantly and are slow. What do you do?

  • Switch to DirectQuery
  • Partition the fact by OrderDate (day)
  • Enable V-Order for the gold tables and rewrite with OPTIMIZE
  • Disable automatic updates

New workspaces default to writeHeavy (V-Order off). Daily partitions create many small files.

Users see "(Blank)" products and jumping totals during a 90-minute, 3-notebook nightly load. Automatic updates are on. Fix?

Disable automatic updates, orchestrate the notebooks in a pipeline, add a Semantic model refresh activity after all succeed. The model stays on the last consistent version and switches in seconds. Keep VACUUM retention long enough for the framed files.

Security: whose identity reads the lake?

SSO checks every user against the data; a fixed identity reads for them so only the model's RLS matters.

👤Report user
🧠Modelpasses user identity
🏞️Lakehousechecks the user

Every user needs data access: on SQL Read + SELECT; on OneLake Read + ReadAll or a OneLake role.

👤Report userRead on model only
🧠Model RLSfilters rows
🤖Fixed identityreads the lake
🏞️Lakehouse

Cloud connection with SSO off. Users get no lakehouse permissions, so they can't bypass model RLS.

Details

Auth: OAuth 2.0, service principal or workspace identity (no key/SAS). Microsoft "strongly recommends" it with model RLS. A connection can use SSO for queries and the fixed identity for framing.

On OneLake + SSO: the user's OneLake roles apply everywhere. OneLake roles unioned, then intersected with model roles. Contributors+ see all.

Limitations

No model backup; no bidirectional relationships with OneLake RLS; refresh after role changes. If the SQL endpoint switches to user identity mode, Direct Lake on SQL falls back 100% of the time.

👑 Ownerneeds read access to the tables, or framing fails
Write ≠ RLSAdmin, Member, Contributor bypass model RLS
🪪 Fixed identity (SSO off) + model RLS; grant consumers nothing on the lakehouse.
🛡️ Direct Lake on OneLake + SSO: OneLake roles enforced for each user.
🏢 Direct Lake on SQL + SSO: accept DirectQuery fallback.

Consumers must see only their region's rows and must not query the lakehouse. Engineers keep full access. What do you do?

  • Keep SSO, grant consumers ReadAll and add model RLS
  • Define RLS on the SQL endpoint and keep SSO
  • Fixed identity (SSO off) with read access, model RLS roles, no lakehouse permissions for consumers
  • Give consumers Contributor

With SSO they'd need data access and could bypass model RLS; Contributors bypass RLS entirely.

More limitations
  • No complex Delta types, binary or GUID; strings max 32,764 characters; no NaN.
  • Related columns need matching types; one-side keys must be unique.
  • Analyze in Excel/MDX: DirectQuery limits; no user hierarchies in MDX clients.
  • Embedding: V2 embed token; service principal → fixed identity.
  • Same table twice only via XMLA (then edits/refresh error). Cross-region workaround (SQL): shortcuts.
  • Deployment pipelines don't rebind: use text M parameters (WorkspaceId, LakehouseId) + parameter rules on OneLake.

Migrating an Import model to Direct Lake
  1. Re-implement Power Query transformations upstream as Delta tables
  2. Materialize calculated columns and tables in the lakehouse
  3. Create a Direct Lake model on the gold tables
  4. Copy measures, relationships, calculation groups and roles
  5. Rebind reports to the new model
  6. Validate results and monitor fallback and guardrails

Export a Power Query template into Dataflow Gen2; copy objects with Tabular Editor or semantic-link-labs migration functions. Quick alternative without migration: OneLake integration for Import models writes Import tables as Delta to OneLake.

Facts in a lakehouse, products in a warehouse, an Excel budget, OneLake security rules, never silently slow. Which flavour?

Direct Lake on OneLake with SSO: multiple items, Import table for the budget, OneLake security enforced, no fallback. Check F64 guardrails (5,000 files, 1.5 B rows) and V-Order.

Exam traps

  • Max memory is not a guardrail: exceeding it causes paging, not fallback.
  • Direct Lake on OneLake never falls back. Guardrail breach = refresh fails.
  • SQL endpoint RLS/DDM/views → fallback; SQL OLS/CLS → error.
  • DirectLakeOnly makes fallback cases fail; it doesn't fix them.
  • Automatic updates control reframing, not fallback.
  • VACUUM can delete files the framed version still needs → errors.
  • Model RLS doesn't apply to Admin/Member/Contributor; with SSO users can bypass it via the lake.
  • No user-defined aggregations, incremental refresh or gateways on Direct Lake tables.

Cheat sheet

⚙️ Mechanics

  • Framing: pin Delta version, seconds
  • Transcoding: whole columns on demand
  • Eviction: reframe, idle, memory pressure
  • Cold → semiwarm → warm → hot

🏞️ vs 🏢

  • OneLake: multi-item, Import mix, OneLake security, no fallback
  • SQL: one item, views, SQL perms, fallback

🔁 Fallback (SQL only)

  • Views, SQL RLS/DDM, guardrails, unframed
  • Automatic / DirectLakeOnly / DirectQueryOnly
  • TABLETRAITS(), DirectQuery_Begin

📏 Guardrails

  • F2–F32: 1,000 / 1,000 / 300 M
  • F64: 5,000 / 5,000 / 1.5 B
  • F128 3 B · F256 6 B
  • F512: 10,000 / 12 B · F1024+ 24 B

🔄 Refresh

  • Automatic updates on by default
  • Multi-step ETL: off + pipeline refresh activity
  • V-Order, 1–16 M row groups, OPTIMIZE/VACUUM, append

🔐 Security

  • SSO default: users need data access
  • Fixed identity + model RLS: no lake access
  • Owner needs read access for framing
