Get data: ingestion, shortcuts, mirroring, real-time

How data gets into (or becomes visible in) Fabric: choosing between pipelines, Copy job, Dataflow Gen2, notebooks, eventstreams, mirroring and OneLake shortcuts; connections and gateways; discovering data in the OneLake catalog and Real-Time hub; and choosing a lakehouse, warehouse or eventhouse as destination. Maps to the exam domain Prepare data → Get data (part of the 45–50% "Prepare data" domain).

Decision mindset for the exam: first ask "must the data move at all?" (shortcut or mirroring may be enough), then "batch or streaming?", then "code or no code?", "how much transformation?", "full or incremental?" and "does it need orchestration with other steps?".

Connections and gateways

Fabric items connect to sources through connections (managed in Settings → Manage connections and gateways). A connection stores the endpoint, authentication method (OAuth/organizational account, service principal, workspace identity, key, SAS, basic…) and privacy level. Connection roles: Owner, User (can use it in items), User with resharing. To bind a shortcut or item to a connection you need permission on the connection.

The VNet data gateway is Microsoft-managed and injected into your subnet, so nothing is installed; it supports pipelines, Copy job, Dataflow Gen2, mirroring and semantic models. An on-premises gateway on a VM would work but requires installation and maintenance; shortcuts don't point to SQL databases.

OneLake shortcuts

A shortcut is an object in OneLake that points to a target path somewhere else. It looks like a folder; every engine (Spark, SQL analytics endpoint, Direct Lake, KQL, external tools using the OneLake ADLS API) reads through it as if the data were local. Nothing is copied.

Where you can create them

  • Lakehouse – in Tables only at the top level (or as a schema shortcut in a schema-enabled lakehouse). If the target is a Delta table, it's auto-discovered as a table and queryable from the SQL analytics endpoint and Direct Lake. Names with spaces aren't recognized as Delta tables.
  • Lakehouse Files – at any folder level, any format, no table discovery (read with Spark; use shortcut transformations or a load to create Delta tables).
  • KQL database / eventhouse – appears under Shortcuts, queried as an external table: external_table('MyShortcut').
  • Not in a warehouse – a warehouse queries lakehouse shortcuts through cross-database queries (three-part names) instead.

Target types

Internal (OneLake)External
Lakehouses, warehouses, KQL databases, mirrored databases, mirrored Azure Databricks catalogs, SQL databases, semantic models (OneLake integration exports) – same item, same workspace or other workspaces; item types don't have to matchADLS Gen2, Azure Blob Storage, Amazon S3, S3-compatible storage, Google Cloud Storage, Dataverse, OneDrive/SharePoint, Iceberg tables; on-premises/network-restricted locations via the on-premises data gateway

Security model

  • Creating a shortcut requires write permission on the item where it's created (Contributor or higher) and access to the target.
  • Internal shortcuts – identity passthrough: OneLake authorizes the calling user against the target; the reader needs Read permission on the target data. (Exception: Direct Lake on SQL endpoint and T-SQL in delegated identity mode pass the item owner's identity; Direct Lake on OneLake and T-SQL user identity mode pass the user.)
  • External shortcuts – delegated: access uses the cloud connection credentials (account key, SAS, service principal, organizational account, workspace identity) bound when the shortcut was created. Anyone who can read the shortcut path reads with those credentials – secure the shortcut path with OneLake security roles/workspace roles.

Caching, deletion and limits

  • Shortcut caching (workspace settings → OneLake): caches files read through S3, S3-compatible, GCS and on-premises gateway shortcuts to cut cross-cloud egress cost. Retention 1–28 days, reset on every access; files > 1 GB aren't cached; newer source versions are fetched automatically; Reset cache clears it.
  • Deleting a shortcut deletes only the pointer – the target data is untouched (no cascading delete).
  • Deleting a file or folder inside a shortcut deletes it in the target if you have write permission there.
  • Moving, renaming or deleting the target breaks the shortcut. Schema changes in the source sync automatically.
  • Limits: 100,000 shortcuts per item; 100 unique external connections per item; up to 10 shortcuts in a single path; max 5 chained (shortcut-to-shortcut) hops; no % or + in names.
  • Shortcuts are created in the UI (Get data → New shortcut or right-click Tables/Files) or with the OneLake shortcuts REST API; their target can come from a variable library for CI/CD.

Mirroring

Mirroring continuously replicates data from an operational system into OneLake as Delta tables – no pipelines, no schedules. It creates a mirrored database item with a SQL analytics endpoint (read-only for data: query with T-SQL, create views, cross-database queries, Direct Lake, shortcuts to Spark).

TypeHow it worksExamples
Database mirroringInitial snapshot, then change capture from the source (transaction log / change feed) merged into Delta; changes can arrive as fast as every ~15 secondsAzure SQL Database, Azure SQL MI, SQL Server (2016–2025, via gateway for on-prem), Azure Cosmos DB, Azure Database for PostgreSQL, Snowflake, Oracle, Google BigQuery, SAP; Fabric SQL database is mirrored automatically
Metadata mirroringSyncs only catalog metadata (catalogs, schemas, tables) and uses shortcuts to the data – nothing is copiedAzure Databricks Unity Catalog, Snowflake (option), Dremio
Open mirroringYou (or a partner tool) write change files into the mirrored database's landing zone per the open mirroring spec; Fabric merges inserts/updates/deletes into DeltaAny source via custom apps or partner solutions

Cost model (frequently tested)

  • Replication compute is free – it doesn't consume capacity units.
  • Storage for replicas is free up to 1 TB per purchased CU (F64 → 64 TB). Beyond that, or while the capacity is paused, normal OneLake storage is charged.
  • Querying mirrored data (SQL, Spark, Power BI) consumes CUs at normal rates.
  • A running capacity is required; while paused, nothing is replicated.
  • Mirrored tables are vacuumed automatically (default retention 1 day for new mirrors; configurable for time travel).

Discover data: OneLake catalog and endorsement

  • The OneLake catalog (successor of the OneLake data hub) is the central place to find, explore and connect to items you can access: Explore tab (filter by item type, workspace, domain, endorsement, owner, tags; open details, lineage, schema), Govern tab (insights and recommended actions for your data estate). It's also embedded in Get data dialogs of Power BI Desktop, dataflows, notebooks and pipelines.
  • Endorsement: Promoted – any user with write permission on the item; Certified – only users/groups authorized by a Fabric admin in the tenant setting; Master data – designated owners of authoritative reference data (admin-authorized). Endorsed items rank higher in discovery.
  • Discoverability: items can be made discoverable to users who don't yet have access so they can request access.
  • To reuse a model: endorse it, make it discoverable, and grant Build permission.

Dataflow Gen2

Dataflow Gen2 is Power Query Online as a Fabric item: connect to 150+ sources, transform with the ribbon or M code (Advanced editor), and write each query to a data destination. It can run on its own schedule or as a Dataflow activity in a pipeline. The current item type is Dataflow Gen2 (CI/CD), which supports Git, deployment pipelines, public parameters and variable libraries.

Data destinations

Fabric Lakehouse (Tables or Files), Fabric Warehouse, Fabric KQL database, Fabric SQL database, Azure SQL database, Azure Data Explorer, ADLS Gen2, SharePoint files, Snowflake, PostgreSQL. Each tabular query can have its own destination.

Staging

  • Staging loads query results into internal staging items (a staging lakehouse/warehouse only dataflows can see) so the SQL compute can process large transformations ("compute engine").
  • Loading to a warehouse requires staging (and the warehouse must be in the same workspace). For lakehouse and other destinations staging is off by default so data is written directly.
  • Split big work: query A (staging enabled) ingests; query B references A, transforms at scale and writes to the destination.

Fast copy

  • Uses the pipeline Copy activity engine instead of the mashup engine for large ingestions; enable Allow use of fast copy connectors (Options → Scale). It kicks in automatically above thresholds: files (CSV/Parquet in ADLS Gen2/Blob) ≥ 100 MB, databases ≥ 5 million rows; Require fast copy forces it (and fails fast if impossible).
  • Only simple transformations on file sources (combine files, select/remove/rename columns, change types); for SQL sources, whatever folds into the native query.
  • Writes directly only to a Lakehouse; for other destinations stage first and reference.
  • Refresh history shows engine CopyActivity when it was used.

Incremental refresh (Dataflow Gen2)

  • Right-click a query → Incremental refresh: choose a DateTime/Date column to filter, how far to extract data from the past, a bucket size (day, month…) and a column whose maximum value indicates changes; optionally only concluded periods.
  • Only buckets whose max value changed are re-extracted and replaced in the destination; older data is untouched.
  • Destinations: Lakehouse, Warehouse, Azure SQL Database; requires fixed schema and Replace; query should fully fold; max 50 buckets per query, 150 per dataflow.
  • Different from a semantic model's incremental refresh policy (RangeStart/RangeEnd parameters).

Query folding

Put selective, foldable steps (filter rows, remove columns, group by) early so the source engine executes them. If the step-folding indicator shows a step isn't folded (and View data source query is unavailable), everything before it is pulled into the mashup engine – a common cause of slow refreshes on large tables.

A Dataflow Gen2 loads 400 GB of Parquet from ADLS Gen2 into a lakehouse; the only steps are selecting and renaming columns. Refresh takes hours. What should you do first?

  • Enable staging and change the destination to a warehouse
  • Enable fast copy so the copy engine performs the ingestion
  • Switch the update method from Replace to Append
  • Add an index column to improve folding

Fast copy uses the pipeline Copy engine for large file and database volumes when the transformations are supported (select/rename are) and the destination is a lakehouse.

Pipelines (Data Factory)

A pipeline orchestrates activities with dependencies, parameters, expressions, retries and schedules.

CategoryActivities
Move & transformCopy data, Copy job, Dataflow (Gen2), Notebook, Spark job definition, Stored procedure, Script, KQL, Semantic model refresh
Control flowForEach, If condition, Switch, Until, Wait, Filter, Set variable, Append variable, Invoke pipeline, Fail
Lookup & metadataLookup (read a row/small result set, e.g., a watermark or control table), Get metadata (file/folder info: child items, last modified, exists…)
External & notifyWeb, Webhook, Azure Function, Office 365 Outlook, Teams

Dependencies, retries, parameters, expressions

  • Dependency conditions between activities: On success, On fail (e.g., send a Teams/Outlook alert only when the load fails), On completion (always – cleanup), On skip.
  • Each activity has retry count, retry interval and timeout – the fix for transient errors such as HTTP 429 throttling.
  • Parameters are inputs fixed for a run (@pipeline().parameters.LoadDate); variables are mutable within the run (Set variable, Append variable). Pipelines can also read a variable library.
  • Expressions use the @ syntax and functions: @concat('raw/', formatDateTime(utcNow(), 'yyyy/MM/dd')); activity outputs: @activity('LookupWatermark').output.firstRow.LastModified (Lookup with First row only), @activity('GetFiles').output.childItems; current ForEach element: @item().TableName.
  • Notebook activity passes base parameters that override the variables in the notebook cell marked as the parameters cell.
  • Invoke pipeline runs child pipelines – chain them with On success for ordered parent/child orchestration.
Lookup (control table: schema, table, watermark column)
  └─ ForEach  items = @activity('LookupTables').output.value
                Sequential = false, Batch count = 20 (max 50)
       └─ Copy data
            source query = SELECT * FROM @{item().SchemaName}.@{item().TableName}
                           WHERE ModifiedDate > '@{item().LastWatermark}'
            sink = lakehouse table @{item().TableName}
       └─ (On success) Stored procedure / Script: update watermark for @{item().TableName}
  • Metadata-driven ingestion: one generic pipeline + a control table → onboarding a new table is a row insert, not new code.
  • ForEach runs in parallel unless Sequential is checked; Batch count limits concurrency (default 20, max 50). Slow loop with iterations one after another → check Sequential; capacity pressure at peak hours → reduce batch count / reschedule.
  • Watermark pattern: Lookup the old watermark → Copy rows where ModifiedDate > watermark → update the watermark only after the copy succeeds (so a failed run is safely re-read next time).
  • "Skip processing when no new files" → Get metadata (child items) + If condition on the count.

Copy activity details

  • Sources/sinks: 100+ connectors incl. SFTP, REST, ODBC, on-prem via gateway; reads compressed files (gzip, zip…) natively; writes to lakehouse Tables (append/overwrite) or Files, warehouse, KQL database, SQL DB…
  • Column mapping (explicit or auto), staging (interim storage when a direct path isn't supported or bulk loading is faster, e.g., loading a warehouse from an on-prem source through a gateway), fault tolerance (skip incompatible rows and log them), parallel copies, partition options.

Triggers and schedules

  • Every schedulable item (pipeline, dataflow, notebook, Copy job, semantic model) has its own schedule with frequency, time and time zone; Copy jobs support multiple schedules.
  • Event-based triggers (e.g., a file arrives in storage / OneLake, job events) are set up through the Real-Time hub / Activator and can start a pipeline.
  • Separate schedules can't guarantee order – if the notebook must start after the dataflow finishes, put both in one pipeline with On success dependencies.

A Lookup activity named LookupWatermark has First row only selected and returns the column LastModified. Which expression inserts the value into the next Copy activity's source query?

  • @activity('LookupWatermark').output.value[0]
  • @pipeline().parameters.LastModified
  • @activity('LookupWatermark').output.firstRow.LastModified
  • @item().LastModified

With First row only, the Lookup output exposes firstRow; without it, the rows are in output.value (an array). @item() only exists inside ForEach.

  1. Lookup the last watermark from the control table
  2. Copy rows whose ModifiedDate is greater than the watermark
  3. On success, update the watermark to the new maximum ModifiedDate
  4. On success, refresh the semantic model
  5. On fail of any step, send an alert to the on-call engineer

Copy job in more detail

  • Copy modes: full or incremental (first run full, then only new/changed rows). Incremental uses a watermark column (ROWVERSION, datetime, date, integer…) or CDC if enabled on the source (CDC also captures deletes).
  • State is managed for you: a failed run resumes from the last successful run; you can reset to full copy per table or job.
  • Write methods: append (default), merge (upsert on key), overwrite, SCD Type 2; can auto-create and optionally truncate destination tables; audit columns.
  • Run once, on one or several schedules, or as a Copy job activity inside a pipeline; supports gateways (on-prem and VNet), Git/deployment pipelines and variable libraries.

Notebooks for ingestion

  • Choose notebooks when you need code: REST APIs with OAuth token refresh and pagination, complex parsing (nested JSON), custom data-quality rules, very large or specialised processing, or structured streaming with checkpoints.
  • Land raw payloads in lakehouse Files (bronze) in a predictable, partitioned folder layout; then write curated Delta tables. Use an explicit schema for CSV reads; enable mergeSchema when the source adds columns.
  • Notebooks can be parameterized (parameters cell), scheduled, called from a pipeline Notebook activity or from another notebook (notebookutils.notebook.run).

OneLake integration for semantic models and KQL databases

  • Semantic model OneLake integration: turn on OneLake integration in the settings of an Import model (P or F capacity). After the next refresh, import tables are written as Delta tables under <Model>.SemanticModel in OneLake; consume them through shortcuts in a lakehouse (Spark, SQL, other models). Measures, DirectQuery/hybrid tables and calculation groups aren't exported; old versions are kept 3 days; data reflects the last successful refresh.
  • Eventhouse / KQL database OneLake availability: enable it on the database or table and the KQL data is exposed as Delta tables in OneLake; create shortcuts in a lakehouse to query it from Spark, the SQL analytics endpoint or Direct Lake without a copy process.
  • Mirrored databases and Fabric SQL databases also land Delta in OneLake – use shortcuts for Spark.

Key takeaways & exam tips

  • Don't move data you only need to read: shortcuts (files/Delta, other workspaces, other clouds) and mirroring (databases) come first. Copy when you need independence from the source, transformation, or a source shortcuts/mirroring don't support.
  • Shortcuts: lakehouse Tables (top level, Delta auto-discovered) or Files (any level), KQL databases; not warehouses. Internal = user identity passthrough (need permission on the target); external = connection credentials. Deleting the shortcut keeps the target; deleting files inside it deletes them in the target. Caching for S3/S3-compatible/GCS/gateway: 1–28 days, files > 1 GB not cached.
  • Mirroring: database / metadata / open; near real-time Delta + read-only SQL analytics endpoint; replication compute free; 1 TB free storage per CU; queries billed; needs a running capacity.
  • Copy job = simplest full/incremental/CDC movement with append/merge/overwrite/SCD2. Copy activity = bulk throughput inside an orchestrated pipeline (staging, fault tolerance, mapping). Dataflow Gen2 = Power Query low-code transformations. Notebook = code. Eventstream = streaming.
  • Gateways: on-premises data gateway for datacenter/network-isolated sources (cluster for HA); VNet data gateway for Azure private networks without installing anything. Firewalled ADLS → trusted workspace access with workspace identity.
  • Dataflow Gen2 destinations: Replace vs Append; automatic settings = replace + managed mapping + drop/recreate; warehouse needs staging and fixed schema; KQL/ADX append only. Incremental refresh: lakehouse/warehouse/Azure SQL, fixed schema, replace per bucket, fold the query. Fast copy: big files/tables, simple steps, lakehouse destination.
  • Pipelines: Lookup (watermark, output.firstRow), Get metadata + If (skip when empty), ForEach (Sequential / batch count), Invoke pipeline, Notebook base parameters, dependency conditions (success/fail/completion/skip), retries for transient errors, schedule per item with time zone; order-dependent steps belong in one pipeline.
  • Discovery: OneLake catalog (Explore/Govern, domains, endorsement), Real-Time hub for streams and events. Promoted = any writer; Certified = admin-authorized reviewers.
  • Destination choice: lakehouse (Spark, files + Delta, read-only SQL endpoint), warehouse (T-SQL DML, transactions, COPY INTO), eventhouse (streaming/time series, KQL), SQL database (OLTP, auto-mirrored).
  • OneLake integration: Import semantic models can export tables to Delta; KQL databases expose tables via OneLake availability – consume both through shortcuts.
