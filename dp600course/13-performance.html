Deep dive: smoothing, throttling and other monitoring sources
  • Smoothing: interactive operations over ≥ 5 minutes; background (refreshes) over 24 hours.
  • Throttling stages: overage protection up to 10 min of future capacity → interactive delay → interactive rejection (after 60 min) → background rejection (after 24 h).
  • Monitoring hub: status/duration of refreshes, pipelines, notebooks. Refresh history, workspace monitoring (Eventhouse logs), Profiler / Log Analytics traces.
  • Power Query diagnostics and View native query / folding indicators: verify filters fold (incremental refresh, DirectQuery).
  • Performance analyzer: clear the cache (or restart) for realistic cold numbers. Fabric portal also offers ready-made BPA and Memory Analyzer notebooks.
  • Typical BPA rules: avoid floating point types, IsAvailableInMDX = false on hidden columns, avoid bidirectional/many-to-many, use DIVIDE, remove auto date/time, hide foreign keys, format strings and descriptions.

Formula engine vs storage engine

Fast DAX lets the multi-threaded storage engine do the work in a few big queries.

🧮 Formula engine (FE)

  • Builds the plan, complex logic
  • Single-threaded
  • Speaks DAX
  • No cache
  • Goal: as little work as possible
VS

⚙️ Storage engine (SE)

  • Scans compressed columns, simple aggregates
  • Multi-threaded segment scans
  • xmSQL (VertiPaq) / SQL (DirectQuery)
  • SE cache reuses identical requests
  • Goal: few, large queries
High FE % + thousands of tiny SE queries?
Row-by-row evaluation: iterator / context transition over a big table. Rewrite set-based.
CallbackDataID in xmSQL?
The SE calls the FE back per row (IF, DIVIDE inside SUMX). Slow and not cached.
SE query returns millions of rows?
Huge materialization sent to the FE. Aggregate earlier, filter columns, not tables.
Why return BLANK instead of 0?
Zeros make visuals evaluate and show every combination (dense results).
-- Slow: FILTER iterates the whole expanded Sales table
High Value (slow) =
CALCULATE ( [Sales Amount], FILTER ( Sales, Sales[Quantity] * Sales[NetPrice] > 1000 ) )
-- Better: filter only the needed columns
High Value =
CALCULATE ( [Sales Amount],
    FILTER ( ALL ( Sales[Quantity], Sales[NetPrice] ), Sales[Quantity] * Sales[NetPrice] > 1000 ) )
-- Slow ratio: per-row DIVIDE = callbacks
Avg Margin % (slow) = AVERAGEX ( Sales, DIVIDE ( Sales[Margin], Sales[SalesAmount] ) )
-- Aggregate first, divide once
Margin % = DIVIDE ( SUM ( Sales[Margin] ), SUM ( Sales[SalesAmount] ) )
  1. FILTER over a fact table = row iteration over the expanded table.
  2. Filtering two columns is SE-friendly. Best: materialize LineTotal upstream.
  3. DIVIDE inside an iterator triggers CallbackDataID per row.
  4. Two SE aggregates + one FE division: fast.

Repeated subexpression✓ VAR, evaluated once✗ repeat CALCULATE

Server Timings: 85% FE time, 2,400 SE queries. Meaning?

  • Scale up the capacity
  • Row-by-row iterator; rewrite set-based
  • SE cache disabled
  • Too many points to render

High FE + many small SE queries is the per-row signature. More capacity doesn't change the plan; rendering shows in Performance analyzer.

Which rewrite is most likely to improve performance?

  • FILTER(Sales, Sales[Channel]="Web") → Sales[Channel]="Web"
  • DIVIDE → IFERROR(a/b)
  • SUM(LineTotal) → SUMX(Sales, Qty*Price)
  • COALESCE(…, 0) everywhere

A column predicate goes to the SE. IFERROR and per-row SUMX add work; COALESCE to 0 densifies results.

Deep dive: more DAX rules of thumb
  • KEEPFILTERS(Product[Color] = "Red") instead of FILTER(VALUES(…)) workarounds: same meaning, SE-friendly.
  • SUM over a materialized column beats SUMX with complex per-row logic.
  • SELECTEDVALUE / ISINSCOPE instead of IF(HASONEVALUE(x), VALUES(x)).
  • Measure branching: build on base measures; one definition, reusable SE results.

Shrink the model

VertiPaq size depends on the number of columns and their cardinality, much less on rows.

Model diet: tick optimizations (illustrative numbers)

Start: 400 M-row fact, 38 GB.

"Columns and cardinality, not rows." Cut what nobody uses, then cut distinct values.
  • Remove a GUID column nobody reports on
  • Split a datetime into date and time
  • Disable auto date/time
  • Replace a text key with an integer key
  • Column predicate, not FILTER(fact)
  • Store a repeated subexpression in a variable
  • Aggregate before DIVIDE
  • Incremental refresh with a 10-day window
  • Trigger refresh from the load pipeline
  • Refresh changed partitions via API

600 M rows; OrderDateTime (seconds) is the largest column. Reports use date and hour. Fix?

  • Convert to text
  • Bidirectional Date relationship
  • Add a calculated date column
  • Split upstream into Date + hour Time; drop the original

Date (thousands of values) + hour (24) is tiny vs a second-precision datetime. Keeping the original or adding a calculated column grows the model.

Deep dive: other model rules
  • Star schema with single-direction one-to-many relationships; avoid bidirectional and many-to-many (use CROSSFILTER per measure).
  • Hide technical columns; avoid numbers stored as text.
  • Find removal candidates with VertiPaq Analyzer (size) + dependency/usage analysis (not used by measures, relationships or reports).

User-defined aggregations

  • You build & map the agg table
  • GroupBy, Sum, Count, Min, Max, Count table rows
  • Detail = DirectQuery, dims = Dual
  • ✗ Not on Direct Lake tables
VS

Automatic aggregations

  • Service trains on the query log
  • DirectQuery models on capacity
  • Training schedule + target query coverage %
  • Less control, no mapping

Billions of rows; fast month × product summaries plus rare drill-through. Design?

  • Direct Lake + user-defined agg
  • DQ detail + Import agg + Dual Date/Product
  • Import the full fact
  • Pure DirectQuery

Agg answers summaries from memory; detail stays for drill-through; Dual serves both. User-defined aggs aren't supported on Direct Lake.

Deep dive: aggregation details
  • Precedence: with several agg tables, the higher value is considered first (coarsest useful agg highest).
  • Dual avoids limited relationships and unnecessary source queries. RLS must be consistent between agg and detail.
  • Verify hits in DAX Studio / Profiler: Aggregate Table Rewrite Query event, no DirectQuery events.
  • Direct Lake: build summary Delta tables in the lakehouse instead.

let

    Fact     = Source{[Schema = "dbo", Item = "FactSales"]}[Data],
    Filtered = Table.SelectRows(Fact, each [OrderDate] >= RangeStart and [OrderDate] < RangeEnd)

  1. A foldable source (SQL) so the filter becomes a WHERE clause.
  2. Inclusive start, exclusive end. Integer keys (yyyymmdd): convert the parameters with a function.

Refresh still takes hours; the source sees full-table queries with no date predicate. Cause?

  • RangeStart/RangeEnd are Date/Time
  • Detect data changes is on
  • The filter doesn't fold, so the full table is read per partition
  • Large model format is on

Incremental refresh depends on folding. Date/Time is the required type.

Which statement about Detect data changes is TRUE?

  • Checks MAX of an audit column per partition; misses hard deletes
  • Uses the RangeStart column
  • Detects deletes by row counts
  • DirectQuery only

A separate audit column (LastUpdateTime) is checked per partition in the window. Deletes don't change the max.

Deep dive: details that get tested
  • Licensing: Pro, PPU, Premium/Fabric capacity, Embedded; real-time hybrid tables need Premium/PPU/Fabric capacity. Enable automatic page refresh for hybrid reports.
  • Service refresh timeout: 2 h (Pro) / 5 h (capacity); XMLA refreshes have no such limit.
  • After publishing you can't download the PBIX; republishing from Desktop replaces partitions. Change metadata with Tabular Editor / ALM Toolkit (metadata-only deployment).
  • Refresh uses UTC unless a time zone is set (XMLA/TMSL always UTC).
  • XMLA read-write: view partitions in SSMS, refresh single (backdated) partitions, bootstrap history partition by partition, override detect-data-changes queries.
  • Same RangeStart/RangeEnd for all tables with policies; all partitions query a single source.
  • Not for Direct Lake tables (partition the Delta table). Dataflow Gen2 has its own incremental refresh with the same folding need.
  • Enable large model format before the first refresh if the model will grow.

  • Refresh types: full, dataOnly, calculate, clearValues, automatic, defragment; also applyRefreshPolicy, effectiveDate, timeout; poll status / cancel.
  • Report: fewer visuals per page (slicers count), Top N on high-cardinality visuals, Apply buttons (query reduction), certified custom visuals, query caching for Import models.
  • DirectQuery: fewer/simpler source queries, aggregations, Dual dims, source indexes, no bidirectional filters.
  • Direct Lake: avoid fallback (test with DirectLakeOnly), V-Order, 1–16 M-row row groups, few files, OPTIMIZE, append loads, stay in guardrails, materialize upstream.
  • Copilot works better on well-prepared models (names, descriptions, synonyms, Prep data for AI). Semantic link: FabricDataFrames, run DAX, functional dependencies, automated checks.

Exam traps

  • Errors + rejected refreshes = capacity throttling → Capacity Metrics app, not Performance analyzer.
  • RangeStart/RangeEnd must be Date/Time, case-sensitive, and the filter must fold.
  • Detect data changes uses an audit column, not the partition date; hard deletes are missed.
  • User-defined aggregations and incremental refresh don't apply to Direct Lake tables.
  • Query scale-out needs large format and doesn't add CUs.
