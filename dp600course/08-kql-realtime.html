Eventhouse & KQL

Streaming data flows into an eventhouse, and you query it with KQL, one pipe at a time.

Domain 2 · Prepare data⏱ 35 min6 lessons
  • Place eventstream, eventhouse, Real-Time dashboard and Activator in one chain
  • Choose an update policy, materialized view, retention or caching policy
  • Read and build KQL pipes: where, extend, project, summarize, top
  • Avoid the traps: has vs contains, innerunique joins, sort defaults
  • Eventstream captures and routes events; eventhouse stores them in KQL databases.
  • A KQL query is a pipe: table | filter | shape | aggregate | sort | render.
  • has beats contains; the default join is innerunique; sort and top default to descending.
  • Retention = how long you keep data; caching = how much stays fast (cache ≤ retention).

"Retention = Remember, Caching = Quick." Retention decides how long data exists; caching decides how much of it is fast (hot on SSD).

Queries over the last 30 days must be fast; one year must stay queryable at lower cost. Which configuration?

  • Retention 30 d, caching 365 d
  • Retention 30 d, caching 30 d + OneLake availability
  • Retention 365 d, caching 30 d
  • Retention 365 d, caching 365 d

Keep 365 days, cache 30. Caching can never exceed retention, and caching everything costs more.

A Real-Time dashboard refreshing every 10 s must show the latest reading per device from a table with millions of rows per hour. What do you create?

  • An update policy that deletes old rows
  • A materialized view with summarize arg_max(Timestamp, *) by DeviceId
  • A stored function with top 1 by Timestamp
  • A caching policy of 1 hour

A materialized view keeps the aggregate precomputed. A function recomputes every time; top 1 gives one row overall.

Deep dive: commands and OneLake availability limits 
.create table RawEvents (Payload: dynamic)
.create-or-alter function ParseRaw() {
    RawEvents
    | project Timestamp = todatetime(Payload.ts), DeviceId = tostring(Payload.deviceId), Temperature = toreal(Payload.temp)
}
.alter table Telemetry policy update
@'[{"IsEnabled": true, "Source": "RawEvents", "Query": "ParseRaw()", "IsTransactional": false}]'

.create materialized-view with (backfill = true) DeviceLatest on table Telemetry
{ Telemetry | summarize arg_max(Timestamp, *) by DeviceId }

.alter-merge table Telemetry policy retention softdelete = 90d
.alter table Telemetry policy caching hot = 14d
  • Management commands start with a dot (.create, .alter, .show); queries don't.
  • Retention range: 1 to 36,500 days or Unlimited. Policies at database level, overridable per table (UI: Manage → Data policies).
  • OneLake availability at database level applies to new tables; tick Apply to existing tables to backfill. The database retention policy also applies to the OneLake copy. Latency configurable 5 min–3 h (TargetLatencyInMinutes).
  • While it is on you cannot rename tables, change a column type, apply RLS or delete/truncate/purge. Adding or dropping columns is allowed.
  • Eventhouse cost: suspends when idle (a few seconds to resume); minimum capacity (formerly "always-on") keeps it active.

Which query returns the five devices with the highest average temperature over the last day?

  • T | where Timestamp > ago(1d) | summarize Avg = avg(Temperature) by DeviceId | top 5 by Avg
  • T | take 5 | summarize Avg = avg(Temperature) by DeviceId
  • T | where Timestamp > ago(1d) | top 5 by Temperature | summarize avg(Temperature) by DeviceId
  • T | summarize Avg = avg(Temperature) by DeviceId | sort by Avg asc | take 5

Filter, aggregate, then top 5 by Avg (descending by default). The others sample, pre-limit or sort ascending.

Deep dive: syntax rules worth knowing
  • Table, column and function names are case-sensitive; keywords are lower case (where, not WHERE).
  • == compares (case-sensitive), =~ is case-insensitive, single = assigns (in extend).
  • Comments //; datetime datetime(2026-11-04); timespans 30s, 5m, 1h, 7d; statements separated by ; (after let).
  • project keeps only listed columns; extend adds columns and keeps all; also project-away, project-rename, project-reorder.
  • iff(), case(), coalesce(), strcat(), tostring(), toreal(), todatetime().
  • let threshold = 8.0; binds scalars, tabular expressions (usable with in (hotDevices)) or functions.
  • parse Message with "Device " DeviceId " reported " Temp:real ... extracts columns from text; extract() uses regex; parse_json() makes dynamic.
  • mv-expand turns array elements into rows (like Spark explode()); evaluate bag_unpack(Payload) spreads a property bag into columns.
  • render timechart (or columnchart, piechart, anomalychart…) is always the last operator; it is a visual hint only.

Operators that trip people up

A handful of KQL defaults differ from SQL; flip each card and test yourself.

has vs contains?
has: whole term via the index (fast). contains: substring scan (slow).
"KustoExplorerQuery" has "Explorer"?
false: terms are maximal alphanumeric runs, so "Explorer" is not a separate term. contains → true.
ago(1h)?
now() - 1h in UTC. Filter on time first: it is cheap.
bin(Timestamp, 5m)?
Rounds down into 5-minute buckets. Empty buckets produce no row; use make-series … default=0 to fill gaps.
Default join kind?
innerunique: deduplicates the left side on the key first. Write kind=inner for SQL semantics.
sort by / top default order?
Descending, the opposite of SQL ORDER BY.
dcount()?
Approximate distinct count (HyperLogLog). Exact: count_distinct().
between (2.0 .. 8.0)?
Inclusive on both ends, written with ..
ExpressionResult
"North America" has "america"✓ true (whole term, case-insensitive)
"KustoExplorerQueryRun" has "Explorer"✗ false
"KustoExplorerQueryRun" contains "Explorer"✓ true (substring scan)

Billions of log rows. You need rows whose Message contains the word timeout (surrounded by spaces). Most efficient?

  • where Message contains "timeout"
  • where Message matches regex "timeout"
  • where Message like "%timeout%"
  • where Message has "timeout"

has uses the term index. like is SQL, not KQL.

Orders | join Customers on CustomerId (no kind) returns only one order per customer. Why?

  • KQL joins are always left semi joins
  • The default kind is innerunique, which dedups the left side
  • KQL returns only the first match on the right
  • The on clause needs $left / $right

Put the smaller table on the left or write kind=inner.

What is true about Telemetry | summarize count() by bin(Timestamp, 5m)?

  • It returns every 5-minute interval, with 0 for empty ones
  • It returns arrays of counts per device
  • It fails, because bin() works only on numbers
  • It returns one row per 5-minute interval that has data

Only existing groups appear. make-series fills gaps.

Deep dive: join kinds, aggregations, time series
  • Join kinds: innerunique (default), inner, leftouter / rightouter / fullouter, leftanti (= NOT EXISTS), leftsemi (= EXISTS). Different key names: on $left.DeviceId == $right.Id.
  • Smaller table on the left; filter and project both sides first. Hints: hint.strategy=broadcast, hint.shufflekey=Key.
  • lookup = optimized join to enrich a large fact with a small dimension (default leftouter). union A, B = UNION ALL (by column name; withsource=, wildcards).
  • Aggregations: count(), countif(), dcount(col, 4) (more accurate), percentile(col, 95), percentiles(col, 50, 95), arg_max(Timestamp, *), take_any(), make_list(), make_set().
  • String rules: terms of 3+ characters are indexed; prefer ==, has_cs, in (case-sensitive is faster); has_any, has_all, !has.
  • "North America" hasprefix "ame" → true; "abc" =~ "ABC" → true.
  • Time: startofday/week/month(), endofday(), datetime_diff(), format_datetime().
  • make-series … on Timestamp from ago(7d) to now() step 1h by DeviceId creates arrays for series_decompose_anomalies(), series_decompose_forecast(), series_fir(), series_fit_line().

Exam traps

  • Default join is innerunique, not inner: left rows with duplicate keys vanish.
  • sort by and top are descending by default; take is unordered.
  • has ≠ contains: has matches whole terms only, and it's faster.
  • summarize … by bin() skips empty buckets; use make-series for zeros.
  • Caching can't exceed retention. Retention also applies to the OneLake availability copy.
  • Creating an eventhouse creates a KQL database with the same name.
  • Filter unwanted events in the eventstream, before they are stored.
  • render is always last; let statements end with ;.
