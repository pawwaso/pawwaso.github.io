The security layers in Fabric

Workspace roles

Four roles: Admin, Member, Contributor, Viewer. Assign them to users, security groups, Microsoft 365 groups, distribution lists or service principals. If someone gets roles through several groups, the highest role wins. Best practice: assign roles to groups.

Typical role questions: "create and run notebooks, publish reports, but must not manage access" → Contributor. "Add other users (but not admins)" → Member. "Reassign capacity, delete the workspace, connect Git" → Admin. "Query with T-SQL and open reports but never create or modify items" → Viewer (or item-level ReadData if they must not see other items).

Viewers can query the SQL analytics endpoint and warehouse (ReadData) but cannot read OneLake files/tables through Spark or the Lakehouse explorer unless a OneLake security role grants it. Contributors and higher always have full data access – granular rules (OneLake security, SQL security, model RLS) target Viewers and item-level users.

A developer must create and run notebooks and publish reports in a workspace but must not add users or move the workspace to another capacity. Which role?

  • Admin
  • Contributor
  • Member
  • Viewer

Contributor can create, edit, delete and run items but can't manage access or capacity. Member can add users; Admin can also change capacity and delete the workspace; Viewer can't create items.

Item permissions and sharing

Sharing an item (or using Manage permissions) gives access to that item only: the user doesn't see other items in the workspace and isn't in any workspace role. Sharing with no extra checkbox grants Read (connect/metadata).

User1 must query only dbo.Sales in Warehouse1 with T-SQL, must not see other workspace items or other tables, and you want least privilege. What do you do?

  • Add User1 to the workspace Viewer role
  • Share Warehouse1 with "Read all data using SQL" checked
  • Share Warehouse1 with "Read all OneLake data" checked
  • Share Warehouse1 with no additional permissions, then run GRANT SELECT ON dbo.Sales TO User1

Plain sharing grants only Read (connect). A granular GRANT then opens exactly one table. The Viewer role exposes the whole workspace; ReadData exposes all tables; ReadAll exposes OneLake files.

An analyst with only Read permission on a certified semantic model cannot connect Excel to it. Which permission is missing?

  • Build
  • Reshare
  • ReadAll

Analyze in Excel and new reports require Build on the semantic model. ReadAll concerns OneLake data, Reshare concerns sharing, and a Contributor role violates least privilege.

OneLake security

OneLake security (formerly OneLake data access roles) is the data-plane, role-based security model for data in OneLake. Roles are defined once on the item (e.g. a lakehouse) and enforced consistently across engines: Spark notebooks, Lakehouse explorer, OneLake APIs, shortcuts, the SQL analytics endpoint (in user identity mode) and Direct Lake on OneLake semantic models.

  • Workspace Admins and Members create and manage roles (Manage OneLake security).
  • A role has: permission (Read or ReadWrite), data (tables, schemas, folders under Tables/ or Files/), optional row-level security (a single-table predicate such as SELECT * FROM dbo.movies WHERE rating <> 'R') and column-level security (remove columns), and members (users, groups, service principals/managed identities).
  • Roles are grant-only (no deny roles); multiple roles are combined (union).
  • Roles affect Viewers and users with Read on the item. Admins, Members and Contributors already have full read/write access and are not limited by them.
  • The DefaultReader role exists in every lakehouse: it gives everyone with ReadAll access to all data. Edit or delete it to restrict access to specific roles only.
  • Limitations to know: no dynamic RLS (no per-user function such as USERPRINCIPALNAME), no multi-table RLS, no dynamic data masking (DDM must be done in SQL), table renames break role definitions.
  • Shortcuts: the security defined at the source item applies when data is read through a shortcut.

A lakehouse has two access paths. Analysts have the Viewer role. They must read only the Tables/sales table and Files/sales folder of a lakehouse from Spark notebooks, not the rest. What should you configure?

  • SQL GRANT SELECT on dbo.sales on the SQL analytics endpoint
  • Promote the lakehouse and share it with ReadAll
  • A OneLake security role on the lakehouse granting Read on those table and folder paths
  • Semantic model RLS

OneLake security roles grant Viewers/Read users access to selected tables and folders and are enforced in Spark. SQL GRANT only affects T-SQL; ReadAll would expose all data; model RLS only filters the model.

SQL granular security (warehouse and SQL analytics endpoint)

The warehouse (and SQL analytics endpoint in delegated mode) supports the familiar SQL Server security model. A user first needs control-plane access (workspace role or at least Read on the item) to connect; then T-SQL permissions apply.

Object- and column-level security

-- custom role and object permissions
CREATE ROLE SalesReaders;
ALTER ROLE SalesReaders ADD MEMBER [analyst@contoso.com];
GRANT SELECT ON SCHEMA::sales TO SalesReaders;
DENY SELECT ON dbo.Payroll TO SalesReaders;
GRANT EXECUTE ON dbo.usp_LoadSales TO [etl@contoso.com];

-- column-level security: allow-list columns ...
GRANT SELECT ON dbo.Employee (EmployeeID, Name, Department) TO SalesReaders;
-- ... or deny a sensitive column to users who already read the table (e.g. via db_datareader)
DENY SELECT ON dbo.Employee (Salary) TO SalesReaders;
  • DENY overrides GRANT. If a user already reads the whole table through a role such as db_datareader, a column GRANT adds nothing – use DENY on the sensitive column.
  • With a column denied, SELECT * fails; users must list allowed columns. A view exposing only permitted (and friendly-named) columns with GRANT SELECT on the view is a common alternative.
  • Fixed database roles exist (db_owner, db_datareader, db_datawriter, db_ddladmin). Workspace Admin/Member/Contributor have full control of the warehouse anyway.

Row-level security with security policies

CREATE SCHEMA Security;
GO
CREATE FUNCTION Security.fn_rls_region(@SalesRepEmail AS varchar(256))
    RETURNS TABLE
WITH SCHEMABINDING
AS
    RETURN SELECT 1 AS allowed
           WHERE @SalesRepEmail = USER_NAME()          -- signed-in user (UPN)
              OR IS_MEMBER('SalesManagers') = 1;       -- managers see all
GO
CREATE SECURITY POLICY Security.SalesFilter
    ADD FILTER PREDICATE Security.fn_rls_region(SalesRepEmail) ON dbo.Sales
    WITH (STATE = ON);
  • RLS = an inline table-valued function (the predicate, created WITH SCHEMABINDING) bound to tables by a security policy with a FILTER predicate. Fabric Warehouse supports filter predicates (block predicates aren't supported).
  • Enforced by the engine for every T-SQL query (including from Power BI DirectQuery and Direct Lake fallback with SSO).
  • Effect on Direct Lake on SQL endpoint: tables with SQL RLS make queries fall back to DirectQuery.
  1. Create a schema to hold security objects
  2. Create an inline table-valued predicate function WITH SCHEMABINDING that compares a column to USER_NAME()
  3. Create a security policy that adds the function as a FILTER PREDICATE on the target table
  4. Turn the policy on (STATE = ON)
  5. Test by querying as a restricted user (for example, a Viewer or a user with item access only)

Dynamic data masking (DDM)

ALTER TABLE dbo.Customer ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()');      -- aXXX@XXXX.com
ALTER TABLE dbo.Customer ALTER COLUMN Phone ADD MASKED WITH (FUNCTION = 'partial(0,"XXX-XXX-",4)');
ALTER TABLE dbo.Customer ALTER COLUMN CreditLimit ADD MASKED WITH (FUNCTION = 'random(1, 100)');
ALTER TABLE dbo.Customer ALTER COLUMN BirthDate ADD MASKED WITH (FUNCTION = 'default()');

GRANT UNMASK TO [FraudTeam];       -- privileged users see real values
  • Masks values in query results; the stored data is unchanged – one copy serves both masked and unmasked users.
  • Mask functions: default(), email(), random(a,b) (numeric), partial(prefix,"padding",suffix).
  • Users with elevated rights (workspace Admin, Member, Contributor; UNMASK holders) see unmasked data.
  • DDM is not a strong security boundary: users can infer values with WHERE predicates. Combine with RLS/CLS for real protection.
  • Not available through OneLake security; not applied when data is read via Spark/OneLake.

Support staff must query a Customer table but see only obfuscated email addresses; the fraud team must see them in full. Which approach needs the least duplication?

  • A second table with hashed emails for support
  • Column-level security denying Email to support
  • A OneLake security role with CLS
  • Dynamic data masking on Email, with UNMASK granted to the fraud team

DDM shows masked values by default and real ones to UNMASK holders, from one copy. CLS would hide the column entirely; a second table duplicates data; OneLake security doesn't do masking.

Semantic model row-level security (RLS)

RLS in a semantic model filters rows with DAX table filter expressions defined in roles.

  • Create roles in Power BI Desktop (Modeling → Manage roles), in Tabular Editor/TMDL, or in the web modeling experience; each role has a DAX filter per table returning TRUE/FALSE per row.
  • After publishing, add members (users or, better, security groups) to roles in the service (semantic model → Security).
  • Static RLS: hard-coded values, e.g. [Region] = "Germany" – one role per region.
  • Dynamic RLS: one role whose filter uses the user identity, typically a mapping table: 'Security'[UserEmail] = USERPRINCIPALNAME(), with the Security table related to the dimension (one-to-many) so the filter propagates. Changes in the mapping table flow in with the next refresh – no model change needed.
  • USERPRINCIPALNAME() returns the UPN (e.g. anna@contoso.com) in Desktop and the service; USERNAME() returns DOMAIN\user in Desktop and the UPN in the service – prefer USERPRINCIPALNAME. CUSTOMDATA() is for embedded scenarios.
  • Filters propagate along relationships from the one side to the many side. To propagate across a bidirectional relationship, enable Apply security filter in both directions.
  • A user in several roles sees the union of the rows each role allows (roles are additive, never subtractive).
  • RLS applies only to users with Read on the model (Viewers, app/report consumers). Users with Write (workspace Admin, Member, Contributor) are not filtered.
  • Validate with View as in Desktop (choose roles and "Other user" to test dynamic RLS) and Test as role in the service.
  • A composite model with DirectQuery to another semantic model passes the user identity: the source model's RLS is enforced and users need Build on the source.
-- Role "Sales managers" on table 'UserRegion' (hidden, related to 'Region' 1:* on RegionKey)
'UserRegion'[Email] = USERPRINCIPALNAME()

-- Role "Germany" (static) on table 'Customer'
'Customer'[Country] = "Germany"

A user belongs to two RLS roles: Role1 filters Country = "France", Role2 filters Country = "Spain". What does the user see?

  • No data, because the filters intersect
  • Only France, because the first role wins
  • France and Spain, because role permissions are combined as a union
  • All countries, because multiple roles disable RLS

Semantic model roles are additive: the user sees rows allowed by any of the roles.

During testing, a user with the Contributor role sees all rows although they are a member of a restricted RLS role. Why?

  • Users with edit (Write) rights on the model, such as Admin, Member and Contributor, aren't restricted by RLS
  • RLS only works in Import mode
  • Contributors need Build permission for RLS to apply
  • RLS roles must be assigned to groups, not users

RLS constrains read-only consumers. Workspace Admins, Members and Contributors have Write on the model and bypass it – test with a Viewer or item-level user.

Object-level security (OLS)

  • OLS secures tables or columns in a semantic model for a role (metadata permission None): the object disappears from the model for role members – they can't see that it exists or query it.
  • Typically configured with Tabular Editor (or TMDL/TMSL via XMLA) on the role's Table permissions / Column permissions.
  • Visuals that reference a secured object return an error for restricted users – design reports (or use field parameters/separate reports) accordingly.
  • A user can't combine RLS and OLS coming from different roles (it raises an error); define both in the same role when needed.
  • Like RLS, OLS restricts only Read users, not Write holders.
  • Defense in depth: for an Import model over a SQL endpoint, CLS in SQL protects the T-SQL path and OLS protects the model path – duplicate the rule in both.
  • Viewers may read only one folder of a lakehouse from Spark
  • Same row filter must apply in Spark and in Direct Lake on OneLake
  • Obfuscate email addresses for T-SQL users except the fraud team
  • T-SQL users see only their department's rows in a warehouse
  • Deny the Salary column to warehouse query users
  • Each sales manager sees only their regions in reports, via USERPRINCIPALNAME
  • Report users must not even know the Salary column exists in the model
  • A developer can create notebooks but can't add users
  • An analyst may build reports on a certified semantic model

Direct Lake and security

A Direct Lake model reads Delta tables in OneLake. Which identity is checked depends on the model's connection:

SSO (Microsoft Entra ID) – defaultFixed identity (cloud connection, SSO disabled)
Identity used to read dataThe current report userA fixed identity: service principal, workspace identity or OAuth account
Users need source permissions?Yes – Read on the item plus SELECT (DL on SQL) or a OneLake security role/ReadAll (DL on OneLake)No – only Read (or Build) on the semantic model/report
Where to put row rulesOneLake security (applies everywhere) or SQL endpoint RLS (DL on SQL → DirectQuery fallback)Semantic model RLS/OLS
Use whenPer-user authorization at the source; users may query the lakehouse anywayConsumers must not be able to query the lakehouse/SQL endpoint directly
  • Direct Lake on SQL endpoint: if a queried table has SQL RLS (or the table is a SQL view), queries fall back to DirectQuery so the SQL engine applies the rules; SQL CLS/OLS on a referenced column returns an error. With fallback disabled (DirectLakeOnly) such queries fail.
  • Direct Lake on OneLake: enforces OneLake security (RLS/CLS/table roles) of the effective identity in memory – no fallback exists; if access is denied, visuals error. With OneLake security and model roles both present, OneLake roles are unioned first, then intersected with model roles.
  • The model owner must also have read access to the source tables, otherwise framing (refresh) fails.
  • Semantic model rules only protect the model: with SSO, users who can query the lakehouse directly bypass model RLS – so pair model RLS with a fixed identity and no source permissions.

Report consumers of a Direct Lake model must see only permitted rows and must not be able to query the lakehouse directly; data engineers keep full lakehouse access. What do you configure?

  • OneLake security roles for consumers and keep SSO
  • Semantic model RLS roles, a fixed-identity connection (SSO disabled), and access to the model/app only for consumers
  • SQL RLS on the SQL analytics endpoint and Direct Lake on OneLake
  • Give consumers the Contributor role and model RLS

With a fixed identity, the model reads the lakehouse on behalf of users, so they need no lakehouse permissions; model RLS filters their rows. SSO would require source access; Contributors bypass RLS.

Sensitivity labels

Fabric integrates Microsoft Purview Information Protection sensitivity labels (e.g. Public, General, Confidential, Highly Confidential).

  • Prerequisites: labels published in Purview, the tenant setting Allow users to apply sensitivity labels for content, edit permission on the item; applying labels to Power BI content requires a Pro or PPU license.
  • Labels can be applied to Fabric items (lakehouse, warehouse, semantic model, report, notebook, pipeline…) in the item settings, the header flyout or Power BI Desktop.
  • Inheritance:
    • Downstream inheritance – a label on an upstream item (e.g. lakehouse → semantic model → report/dashboard) flows to downstream items. It never overwrites a manually applied label and only applies a label that is at least as restrictive.
    • Inheritance on creation – a new report built on a labeled model gets its label.
    • Inheritance from data sources – labels of sources such as Azure SQL Database (classified in Purview) can be applied to semantic models.
  • Exports to Excel, PowerPoint, PDF and .pbix downloads carry the label – and, if the label has encryption (protection), the file stays encrypted so only authorized users can open it.
  • Default label policy labels new items automatically; mandatory labeling forces users to choose a label.
  • Data loss prevention (DLP) policies in Purview scan Fabric items (e.g. semantic models, lakehouses) for sensitive information types such as credit-card numbers and raise alerts or policy tips.
  • Labels classify and protect exports; they don't restrict who can open the item inside Fabric (permissions do that). Purview protection policies can additionally restrict access based on labels.

Users must be able to export Report1 to Excel and download it as .pbix, but the exported files must remain encrypted and readable only by authorized users. What do you do?

  • Disable export in the tenant settings
  • Apply RLS to the semantic model
  • Apply a sensitivity label with encryption (protection) settings to the model and report
  • Endorse the report as Certified

A label with protection settings travels with supported exports (Excel, PowerPoint, PDF, .pbix) and keeps them encrypted. Disabling export breaks the requirement; RLS and endorsement don't protect files.

Purview hub, lineage and impact analysis

  • Microsoft Purview hub (in Fabric settings): a governance dashboard. Admins get tenant-wide insights (sensitivity label coverage, endorsement, items by workspace/domain); data owners get insights about their own items. Links lead to the Purview portal (Unified Catalog, Information Protection, DLP, Audit).
  • OneLake catalog – Govern: owner-oriented insights and recommended actions (unlabeled, undescribed or unendorsed items).
  • Lineage view (workspace): diagram of data sources → pipelines/dataflows/notebooks → lakehouse/warehouse → semantic models → reports/dashboards/apps, including cross-workspace links.
  • Impact analysis (from an item such as a lakehouse, warehouse, dataflow or semantic model): shows the downstream items and workspaces affected by a change, with viewer counts, and lets you notify contacts by email before renaming a column or changing a schema.
  • Purview Unified Catalog can scan the Fabric tenant for metadata and lineage across the estate.

Domains

  • A domain groups workspaces belonging to a business area (Finance, Sales…) to support data-mesh, federated governance. Subdomains refine them.
  • Created by a Fabric admin; domain admins manage settings and assign workspaces; domain contributors can assign workspaces they administer to the domain.
  • A workspace belongs to at most one domain; workspaces can be assigned by name, by workspace admin, or by capacity.
  • Delegated settings at domain level, e.g. certification reviewers per domain, default sensitivity label; domain branding (image) in the OneLake catalog.
  • Users can filter the OneLake catalog by domain to find relevant data.

Workspace identity and service principals

Workspace identity

  • An automatically managed service principal (managed identity) tied to the workspace. Created (and deleted) by a workspace Admin in workspace settings; credentials are managed by Fabric – no secrets to rotate. Deleted when the workspace is deleted.
  • Use it as the authentication of connections (e.g. ADLS Gen2 shortcuts, pipelines, Dataflow Gen2, semantic models) and grant it RBAC roles on Azure resources.
  • Trusted workspace access: lets Fabric reach an ADLS Gen2 account with public access disabled (firewall) by adding a resource instance rule for the workspace and granting the workspace identity access – requires the workspace on an F SKU capacity.

Service principals

  • Microsoft Entra app registrations used for automation (REST APIs, CI/CD, XMLA, deployment pipelines) and as non-personal identities for connections.
  • Prerequisites: tenant setting Service principals can call Fabric public APIs (often scoped to a security group – the SPN must be in it) and a workspace role (Contributor or higher to create/update items) or item permission.
  • Service principals/shared connections avoid broken refreshes when an employee leaves. If an owner leaves, take over the semantic model and rebind credentials to a non-personal identity.

A lakehouse shortcut to an ADLS Gen2 account fails because the storage account has public network access disabled. You must not enable public access. What do you configure?

  • Trusted workspace access with a resource instance rule authorizing the workspace identity
  • An on-premises data gateway
  • A OneLake security role on the shortcut
  • Change the shortcut to use a SAS token

Trusted workspace access lets the workspace (via its workspace identity) through the storage firewall using a resource instance rule. A gateway is for on-premises/private sources in dataflows/pipelines, not shortcuts; OneLake roles and SAS don't bypass the firewall.

Only a small review board should be able to mark semantic models as Certified. What must be done?

  • Give the review board the workspace Admin role in every workspace
  • A Fabric administrator specifies the review board's security group in the certification tenant setting
  • Apply a Certified sensitivity label
  • Grant the board Write permission on each model

Certification is restricted to users named in the tenant (or delegated domain) setting. Write permission only allows promotion; labels are unrelated to endorsement.

Scenario

Lakehouse HR contains an Employee table with a Salary column. Group Analysts (Viewers) query it with T-SQL through the SQL analytics endpoint (delegated mode) and use reports on an Import semantic model built on that endpoint. Data scientists (group DS, Read on the lakehouse) use Spark notebooks and may read only the telemetry table. Nobody outside HR may see Salary. Design the security.

  • T-SQL path (Analysts): column-level security on the SQL endpoint – DENY SELECT ON dbo.Employee(Salary) TO [Analysts] (or GRANT on allowed columns / a view).
  • Model path (Analysts): the Import model refreshes with the owner's identity, so SQL CLS doesn't protect it – add OLS on Salary in a role containing Analysts (they are Viewers, so OLS applies).
  • Spark path (DS): a OneLake security role granting Read on Tables/telemetry only; edit/remove the DefaultReader role so ReadAll doesn't expose everything.
  • Don't give either group Contributor – that would bypass OneLake security and model OLS.
  • Optionally label the lakehouse Confidential with downstream inheritance so the model, reports and exports carry the label.

Key takeaways & exam tips

  • Roles: Admin (delete workspace, add admins, Git, workspace identity, capacity), Member (add users, share, publish app, OneLake security roles), Contributor (create/edit/run items), Viewer (read; T-SQL ReadData; no Spark/OneLake data unless a OneLake security role grants it).
  • Item permissions: Read (connect), ReadData (SQL), ReadAll (OneLake/Spark), Build (create content on a model), Write, Reshare. Least privilege for one table = share with Read + T-SQL GRANT.
  • OneLake security: defined by Admin/Member on the item, Read/ReadWrite, tables/folders + RLS + CLS, enforced across engines for Viewers/Read users; DefaultReader grants ReadAll users everything; no DDM, no dynamic RLS.
  • SQL endpoint modes: delegated (default; SQL GRANT/RLS/CLS/DDM) vs user identity (OneLake security governs tables).
  • Warehouse RLS = predicate function + CREATE SECURITY POLICY … ADD FILTER PREDICATE; CLS = column GRANT/DENY; DDM = MASKED WITH + UNMASK. All only on the SQL path.
  • Model RLS: DAX filters, dynamic via USERPRINCIPALNAME(), roles union, Write holders bypass, test with View as. OLS hides tables/columns (visuals error), via Tabular Editor.
  • Direct Lake: SSO = users need source access; fixed identity = users need only model access → put rules in the model. DL on SQL falls back to DirectQuery for SQL RLS/views; DL on OneLake enforces OneLake security and never falls back.
  • Labels: Purview, downstream inheritance, travel with exports (encryption); DLP detects sensitive data. Endorsement: Promoted (Write), Certified and Master data (tenant-designated).
  • Impact analysis before breaking changes; audit log for "who did what"; domains for federated governance; workspace identity + trusted workspace access for firewalled storage; service principals need the tenant setting and a workspace role.
